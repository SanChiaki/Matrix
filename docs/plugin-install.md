# 插件自己装：来源、信任与安装流程

2026-10-31 定、同日实现。之前带服务的插件只能从部署方目录装（`--plugins` 指定的 `plugins.json`），加一个插件要改文件；
主持人上传的包一带 `service` 就被拒绝。原因是托管的插件进程和 Matrix 在同一台机器、同一个系统用户下，能读整个数据目录
（[plugin-hooks.md](plugin-hooks.md#isolation-debt)）。这篇定：主持人能自己装哪些插件、在哪里跑，部署方怎么管，Agent 怎么参与。

实现：`matrix/plugin_sources.py`（策略、按地址取包、后台目录、上架申请）、`matrix/sandbox.py`（沙箱）、
`matrix/plugin_service.py`（依赖环境、每个安装的密钥）、`matrix/engine.py`“插件”几节；测试 `tests/test_plugin_install.py`。

## 1. 按“代码在哪里跑”分三档

| | 谁能装 | 代码在哪里跑 | 要什么 |
| --- | --- | --- | --- |
| 不带服务（页面、表、技能、触发） | 主持人上传，或从目录装 | 页面在每个人的浏览器沙箱里，网络不执行 | 和以前一样 |
| 远程服务（`service.url`） | 主持人填地址或上传，或从目录装 | 插件作者自己的机器上；Matrix 不执行任何插件代码 | 部署方策略放行这个主机；主持人看过确认卡；每个安装一把签名密钥 |
| 托管代码（`service.command`） | 主持人上传，或从目录装 | 本部署：主持人装的一律进沙箱；目录里的有沙箱时也进 | 部署方有可用的沙箱；不能联网；只能用 python 运行 |

部署方目录是部署方审核过的东西，信任最高：目录里的托管插件可以按清单联网（`service.network`），远程服务用部署方配的密钥，
安装时不出确认卡。主持人自己装的，网络按部署方的策略放行，并在确认卡上把数据去向写清楚。

## 2. 部署方的策略

`<data>/plugin-policy.json`，管理后台“插件”页可改（`PUT /api/admin/plugins/policy`）。没有这个文件就是默认值；文件写坏了按最严处理
（不许远程、不许上传托管插件）。

```json
{
  "remote": "public",
  "allow": ["plugins.corp.example", "10.20.0.0/16"],
  "deny": ["bad.example.com"],
  "hosted_upload": true,
  "sandbox_catalog": true
}
```

- `remote`：`public`（默认）公网主机都行，再加上 `allow` 里的；`listed` 只许 `allow` 里的；`off` 不许主持人装远程插件。
- `allow`：域名（含子域名）、IP 或网段。写进来的可以是内网、可以用 http；没写的只许 https、必须解析到公网地址（同抓取白名单的校验，`web_fetch.plan`）。
- `deny`：域名（含子域名），优先于 `allow`。
- `hosted_upload`：主持人能不能上传托管插件（还要有沙箱）。
- `sandbox_catalog`：目录里的托管插件也进沙箱（有沙箱时；默认是）。

策略每次调用远程服务前都按主机名与解析出的地址再查一遍：管理员关掉远程插件、或把某个主机加进 `deny`，已经装上的立即停用（不删，策略改回来就恢复）。

## 3. 远程服务插件：填地址安装

插件作者把服务跑起来，给出一个地址：`.zip` 插件包，或只有清单的 `plugin.json`。主持人在项目的插件页填这个地址。

1. 网络按策略检查这个地址（主机、https、解析出的地址），取回内容（同样的校验，每一跳重定向都重查，最多 2 MB），校验清单。
   清单里的 `service.url` 必须和插件地址在**同一个主机**上：确认卡上写的主机就是数据会去的地方。
2. 确认卡（`409`，带 `confirm`：一条条要确认的事、`digest`：这个包的指纹）。内容由 `plugin_sources.disclosure` 按清单生成：
   插件服务在哪个主机、不由本部署运行、它那边的数据由作者保管；Agent 调哪些工具时参数会发过去；有 `route` 挂点时项目群聊里的
   每条新消息（正文、作者、@ 了谁）和成员名单会发过去；有 `after` 工具挂点时验收后的任务标题与摘要会发过去；`context` / `mount`
   从它那里读内容进提示词与工作目录；每次调用带项目 id 和调用者。
3. 主持人确认，带回 `digest` 再发一次。包在这期间变了（指纹对不上）就再出一次确认卡。
4. 网络生成这个安装的签名密钥（`ps_…`，存在保管库 `vault/plugin-<项目>-<插件>.bin`），只在这一次的返回里给明文。
   主持人连同项目 id 配到插件服务上；服务按项目 id 找密钥、验签（`v1.<项目>.<过期>.<签名>`，同部署方的远程服务）。
   插件卡上可以重置密钥，旧的立即失效。卸载时密钥一起删。
5. 安装记进项目群聊（“插件服务在 x，项目内容会按挂点发到那里（主持人确认过）”），项目里的人都看得到。

之后插件卡上有“检查更新”：按同一个地址再取一次，内容没变就说“已是最新”，变了按升级走（同样要确认）。

**发给第三方的调用者**：自己装的远程插件，人调用时 `_meta.matrix/caller` 只带成员 id（`{"kind": "user", "id": …}`），不带邮箱；
Agent 调用时带 Agent 的 id 与名称。目录里的远程服务照旧带邮箱（部署方的服务）。

示例：`examples/plugins/llm-wiki/service/wiki_engine.py --http 8780 --root <目录> --secrets secrets.json --package examples/plugins/llm-wiki`
在 `GET /matrix-plugin.zip` 给出插件包（服务地址指回自己），`secrets.json` 是 `{"项目 id": "密钥"}`，改了立即生效。

## 4. 托管代码：沙箱

`matrix/sandbox.py`，第一期只有 Linux 的 bubblewrap（`bwrap`）：

- 新的挂载、进程、IPC、UTS 命名空间；默认也是新的网络命名空间（不能联网），只有目录里声明了 `service.network` 的插件共享网络。
- 文件系统里只有：系统目录（`/usr` 等，只读）、少数 `/etc` 文件、Python 解释器与依赖环境（只读，解释器路径上的符号链接按原样重建）、
  插件包（只读）、这个安装的数据目录（读写，`plugin-data/<插件>/service/`）、空的 `/tmp`。Matrix 的数据目录、别的项目、别人的私有目录、
  保管库密钥在沙箱里不存在。
- 资源上限（`setrlimit`，bwrap 和插件进程都继承）：地址空间 4 GB、打开文件 256 个、单个文件 256 MB、CPU 时间 3600 秒（用完被系统停掉，
  下次调用时网络重新拉起）、不生成 core。
- 第一次用时真跑一次探测（沙箱里起一个 Python），失败就当作没有沙箱（比如容器禁了用户命名空间）。`MATRIX_PLUGIN_SANDBOX=off` 关掉。

没有可用沙箱的部署：主持人上传托管插件时拒绝，并提示改成远程服务或提交上架；目录里的托管插件照旧由网络直接运行（部署方审核过）。
macOS、Windows 的沙箱以后再做。

主持人上传的托管插件还要满足：不联网（`service.network` 不能是 true）、`service.command` 是 `python`。

### 依赖

清单可以写 `service.requirements`：包里的一个锁文件（如 `service/requirements.txt`），每个包都带 `--hash`
（`uv pip compile --generate-hashes` 生成）。安装时网络按它建一个独立的 Python 环境（`<data>/plugin-envs/<锁文件与解释器版本的哈希>/`，
同一份锁文件只建一次），`python` 就是这个环境的解释器，沙箱里只读挂上：

- `uv`（没有就用 `venv` + `pip`），`--require-hashes --no-deps --only-binary :all:`：锁文件要列全，只装预编译的 wheel，安装过程不执行包里的代码。
- 不是目录里的插件，锁文件不能引用本机文件（`file:`、路径）、可编辑安装、别的需求文件。
- 建环境时的进程环境去掉名字带 KEY / TOKEN / SECRET / PASSWORD 的变量。

## 5. 部署方目录：后台管理

目录 = `plugins.json`（文件，部署方维护，同名以它为准）+ 管理后台加的（`<data>/plugin-catalog/<名字>/`，`index.json` 记来源、版本、
包的指纹、谁加的）。后台加的不用重启：

- **从 git 仓库添加**：仓库地址、分支或标签、插件在仓库里的路径。浅克隆，不拉子模块，只许 https 与本机路径（`GIT_ALLOW_PROTOCOL`），
  不用环境里的 git 配置（可能带凭证），不运行仓库里的任何东西；记下提交号。之后可以“重新拉取”。
- **上传插件包**。
- **批准上架申请**（下一节）。
- **移出目录**：已经装进项目的是那一版的拷贝，照常可用，只是没有升级来源了。

项目里装的是安装时那一版的拷贝；目录里的版本号变了，主持人在插件卡上看到“升级到 x”。管理后台的目录表还列出每个插件有几个项目在用（只给数量）。

## 6. 上架申请

任何登录的人都可以把插件包交给管理员审核（项目插件页“提交上架…”，`POST /api/plugin-submissions`），写一句说明。
管理员在后台看申请：说明、包里的每个文件（点开看内容）、体检结果（`plugin_check.lint`），批准就进目录（来源记作“上架申请 · 谁”），
拒绝写理由。提交的人在插件页看到自己的申请和结果。一个人最多同时有 5 个待审核的申请、一共 50 个。

适合走这条路的：要联网的托管插件、要给所有项目用的插件、部署方没有沙箱时的托管插件。

## 7. Agent 提议装插件

项目成员（Agent）有一个档案类工具 `propose_plugin`（`name`：目录里的插件名，或 `url`：插件地址；`reason`）。网络取回包、按策略检查，
生成一张提议卡（`Proposal.kind = "plugin"`，带插件的标题、版本、来源、确认卡上的那些条目和包的指纹），由**主持人**审核：

- 在群聊里看到卡片：谁提议、为什么、插件做什么、数据去向（目录里的写“部署方审核过”）。
- 批准 = 以主持人的身份安装提议时看到的那一份（`POST /api/proposals/<id>/install`，指纹对不上就要求重新确认）；拒绝可以写意见。
- 结果作为通知送回提议的 Agent（“已装进项目，下一轮起可用” / “没有装”）。

和提议新建 Agent 一样：Agent 只能提议，装不装由人决定（不变量 9 的同一个思路）。`propose_plugin` 算会让别人看到内容的工具
（`OUTBOUND_TOOLS`）：会话读过越界的来源时不放行。

## 8. 不变量 24 的新写法

服务端执行的插件代码只在三处之一：部署方目录（部署方审核，含后台加的与批准的上架申请）、本部署的沙箱（主持人自己装的托管插件：
不能联网、只读写自己的数据目录、有资源上限；没有沙箱的部署拒绝）、插件作者自己的远程服务（主持人在确认卡上看过会把什么发到哪个主机后安装，
部署方的策略放行，每个安装一把单独的签名密钥）。其余（挂点、工具分级、留痕、调用者由网络认定）不变。见 [invariants.md](reference/invariants.md)。

## 9. 没做 / 以后

- macOS（`sandbox-exec`）与 Windows 的沙箱；cgroup 级的进程数与内存上限（现在是 rlimit）。
- 托管插件的出网走出口代理、按域名放行（和 #60 的出口代理一起做），之后自己装的托管插件也可以声明要联网的域名。
- 远程服务的连接没有固定到校验过的地址（DNS 重绑定）：安装时与每次调用前按主机名和解析出的地址校验，但调用时由 `RemoteMCP` 自己再解析一次，中间有窗口。
- 插件签名（作者身份）、目录的版本历史与回滚。
- Matrix 本身与云侧 Agent 的隔离仍是 #59：这里只把主持人自己装的插件代码放进了沙箱。
