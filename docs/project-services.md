## 1. 要解决什么

在 Matrix 上把项目配置好以后，项目能**向外提供服务**：Matrix 里的其他用户和公司的外部系统来提问、办事，项目里的成员（Agent 和人）
替他们做完。数据不用拷走，用的是项目的实时数据。

项目现在对外只有两种发布物，都要把东西拿走：

| 发布物 | 对外拿出什么 | 消费的人得到什么 |
| --- | --- | --- |
| 对外页面（已有） | 档案文件的快照 | 只读查看，自己的 Agent 可以订阅 |
| 模板（已有） | 做法 | 一份拷贝，在自己名下建项目 |
| **服务（新）** | **项目的能力** | 提问、办事，项目替他做完 |

2026-10-28 没有做“项目的公共 Agent 服务外人”，原因是 Agent 不跨信任域、所有者能看到全部过程（project-publishing.md 第 6 节）。
公共 Agent（不变量 27）之后，服务面已经有了受控的做法，这里把它推广到项目。

## 2. 已定的事（2026-11-18）

| # | 决策 |
| --- | --- |
| 1 | 服务给 **Matrix 用户**和**外部系统**用 |
| 2 | 服务可以**调动项目成员**，不只是一个 Agent 自己答 |

| 13 | 收件目录有新文件**不通知**任何人 |
| 14 | 服务会话**不设期限**：属于调用方，一直留着，调用方自己能删；服务撤回或入口不在了变成只读，重新发布后接着用新配置；删除项目时一起删。长会话续接越来越贵，这部分用量也记在项目下；想重来就开新会话 |

### 为什么不新增“服务 Agent”

讨论过一个“归项目所有的服务 Agent”（第三条轴：归属）。它的好处是行为完全由主持人控制、生命周期跟着项目走；
代价是要照着成员复制一份，复制出来的会和原来的分叉，还要从头调教，而“项目配好就能服务”正是要用现有的成员。
个人 Agent 的信息会不会说出去，由所有者自己负责，网络不兜底。

### 为什么要指定入口

另一种做法是：服务请求像一条新消息一样进项目，靠投递（`route`）和认领决定谁来接。这样做有三个问题：
每个请求都要付 N 轮被动投递的钱（研发小队里多数成员回“略过”）；调用方会看到好几个 Agent，HTTP 流不知道什么时候结束，追问也不知道该找谁；
最后还是要定一条“谁收口”的规则，而这条规则就是入口。入口是服务的一项设置，和蓝图的“谁接外部来的新需求”是同一种东西。

## 3. 网络守什么

网络不管岗位会不会说出所有者的东西，只管**这一轮在替谁做事、谁来买单**：

| 守什么 | 怎么守 |
| --- | --- |
| 调用方是谁 | 由网络认定：Matrix 用户凭登录；外部系统凭服务密钥（以及以后的 SSO 身份）。不信请求或模型自报 |
| 业务授权 | 要用户鉴权的连接器、外部平台的 `caller` 透传，一律用**调用方自己的**授权。不用入口或岗位所有者的，也不用主持人的；调用方没有就不做，并说明原因 |
| 档案 | 只读发布时圈定的目录（在不变量 26 的可见范围之内再收窄）；只写收件目录；`record_decision`、`propose_brief` 这类改档案的动作不给 |
| 委托 | 只沿项目里的 Agent 走（发布时可以收窄成一份岗位名单），不出项目，不委托给人 |
| 权限 | 有效权限 = 自身权限 ∩ 服务授予的权限（发布时冻结）∩ 运行时能强制的（不变量 1） |
| 成本 | 记在项目下（不设上限，决策 11）；外部接入方乱用时，主持人重签或删掉它的服务密钥 |
| 主持人看到的 | 用量：每天的会话数、轮数、模型用量，按调用方汇总（外部系统按接入方）；看不到内容 |

**谁看得到调用方的请求**：调用方自己；这次调用经过的个人 Agent 的所有者（照常看到过程）。服务名片上要写明
“请求可能经过哪些人的 Agent”，调用方进来前就能看到。服务会话和它引出的委托**不进项目群聊、不上任务板**，项目里别的参与者看不到。

**不变量 29：服务调用替调用方做事、由项目付费**（全文见 [reference/invariants.md](reference/invariants.md)）。一次服务调用沿途的每一轮都以调用方为 `principal`：业务授权只用调用方自己的；
档案只读圈定范围、只写收件目录；委托不出项目；用量记在项目下；主持人只看用量。

## 4. 发布一个服务

主持人在项目页“对外”标签里新建服务（`ProjectService`，和发布物分开存：服务没有快照），定这些：

1. **名字和说明**：调用方看到的名片，包括说明里写的“能办什么”和“请求可能经过谁的 Agent”。
2. **入口**：一个项目成员。
3. **岗位**（可选）：入口能委托的 Agent，默认是项目里全部的 Agent。
4. **数据范围**：可读的档案目录与文件，可用的项目技能与插件工具；**收件目录**（可选，一个目录）。
5. **服务授予的权限**：在入口和岗位各自权限之内再收窄，发布时冻结。
6. **给谁用**：点名的读者、所有登录用户，和 / 或外部接入方（第 6 节）。

配置有版本：改了入口、岗位、范围、权限、读者，要重新发布才对外生效。档案**内容**是实时的，改了马上生效，这是决策 3 的代价。
撤回、归档项目时服务下线；入口不在项目里了（退出、删除），服务暂停并告诉主持人。

## 5. Matrix 用户怎么用

- 从“项目”的“给你看的”里找到服务，**私聊**它：开一个服务会话（属于调用方，类似和公共 Agent 的私聊），这个会话里的每一轮都是入口在服务面跑。
- **追问**落回同一个会话、同一个入口席位，续接上下文。
- 入口按需**委托**岗位。委托在服务会话里，结果回给入口，由入口回复调用方。
- 以后再做：把服务拉进调用方自己的项目，让那边的成员委托它（它在那边像一个外部成员）。

## 6. 外部系统怎么用

和接外部平台对称，Matrix 自己提供**标准 HTTP 形状**（`remote_agents.py` 开头的那一套），别的平台可以像我们接它们一样接 Matrix：

```
GET  /svc/agents/{service}               名片：名称、说明
POST /svc/agents/{service}/chat          {message, session_id?} → SSE: session → delta → done / error
POST /svc/sessions/{session_id}/interrupt 中断
```

路径和事件与 `remote_agents.py` 开头的标准形状一字不差：另一个 Matrix 部署用内置的 `standard` 驱动、`url` 填 `…/svc` 就能把它接成外部平台 Agent。

- **服务密钥**：主持人在服务里给每个接入方签一把（`msk_…`，只显示一次，只存 sha256），重签即作废。密钥只证明“是哪个接入方”。
- **终端用户身份**：SSO 改造之前只有**系统身份**，调用方就是这个接入方，只能用不需要用户鉴权的能力（基于档案答问、写收件目录），
  要用户授权的工具一律拒绝。SSO 改造之后，接入方带上终端用户的 SSO 凭证，Matrix 验证后按那个 Matrix 用户处理（第 5 节的规则全部适用）。
- 外部任务不带进任何内部权限（research: acp-vs-a2a#external-task-authority）；Caddy 里和 `/mcp/remote` 一样不加 basic auth，靠服务密钥。

**第一期的限制**：

- 个人 Agent 的所有者看得到它在服务里的那几轮（交给它的消息、它的回复与过程、工作目录：Agent 设置里的“在服务里”，
  `service_rounds`，回复的 `private_to` 带上所有者），看不到整个服务会话；在那里不能终止它，终止由调用方做。
