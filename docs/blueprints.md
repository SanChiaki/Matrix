# 蓝图：把跑通的项目交付出去（设计）

> 状态：设计，2026-10-31 定，未实现。需求 #62。
> 相关：插件与挂点见 [plugin-hooks.md](plugin-hooks.md)，插件怎么装见 [plugin-install.md](plugin-install.md)，
> 现有的发布物（技能包 / 交付件）见 [project-publishing.md](project-publishing.md) 与 [reference/releases.md](reference/releases.md)，
> 连接器的定义见 [connectors-and-skills.md](connectors-and-skills.md) 第 11 节。

## 1. 要解决什么

Agent 协作类产品（Raft、Multica 等）交付的多是**过程**：怎么分派、怎么认领、怎么接力。Matrix 要交付的是**拿到就能用的东西**：

- 简单的：一套构建、发布看板的项目。把看板系统的连接器配进来，准备好技能，交付出去；拿到的人直接就能做看板。
- 复杂的：一套研发流程。issue / PR 事件触发任务，五个专职 Agent 按岗位接力完成“反馈 → 方案 → 编码 → 审查 → 部署”，
  人只在接口、验收和高风险节点介入。交付出去就是一套能跑的研发流程；拿到的人建出自己的 Agent，按流程接需求、做任务。

这个“交付出去的东西”叫**蓝图**。

已经定的（2026-10-30、10-31）：

1. 对外交付只有一种东西：蓝图。**技能包并进蓝图**（第 7 节）；交付件快照改成项目的对外页面，不是蓝图，另写设计。
2. 插件是蓝图的部件；插件跑在 Matrix 上，和 harness 解耦（plugin-hooks.md 第 1 节）。
3. 蓝图本身是一个文件；第一期只在本部署内发布与使用，跨部署导入放第二期。
4. 岗位由人担任放第二期；第一期岗位都由 Agent 担任。
5. 蓝图的目录和插件目录一样：部署方目录（管理后台管）加上按读者分享或公开。

## 2. 蓝图是什么

**一个跑通了的项目，去掉数据、人和凭证之后剩下的配方。** 别人拿去建项目，补上自己的人、模型和账号，就得到一个同样能干活的项目。

| 带 | 不带 |
| --- | --- |
| 纲要（可以带参数占位） | 群聊、决定、记录、委托、用户任务：项目里发生过的事 |
| 项目技能 | 具体的 Agent 与人 |
| **岗位**：名称、职责、能力、建议权限、建议模型 | 模型的密钥、连接器的凭证 |
| 插件：目录里的插件名与版本，或打包进来的插件包；连同安装设置 | 插件里的数据（表的记录、服务的数据目录） |
| **连接器槽位**：要连哪个系统、读还是写、给哪些岗位用、拿来做什么 | 谁的账号 |
| **参数**：建项目时要填的空（公司名、仓库地址、指标口径…） | |
| 模板文件：项目一开始就该有的资料 | 运行中产生的文件 |
| **人在哪里介入**（第 5 节） | |

律所类比（research: project-publishing#method-vs-fact）里，蓝图是“方法”的完整形态：技能包只是方法里的技能那一部分。

## 3. 形状

一个蓝图是一个目录，导出时打成 zip：

```
blueprint.json          清单
README.md               给人看的说明：这个蓝图能做什么、建出来之后怎么用（蓝图页面展示它）
brief.md                纲要模板
skills/<名字>/SKILL.md   项目技能（同项目技能格式）
files/...               模板文件，建项目时放进项目档案
plugins/<名字>/...       打包进来的插件包（可选；也可以只引用目录里的）
```

`blueprint.json`：

```json
{
  "name": "dev-pipeline",
  "version": "1.0.0",
  "title": "研发流程",
  "description": "issue / PR 触发，五个岗位接力：反馈 → 方案 → 编码 → 审查 → 部署；人只在验收和高风险节点介入",
  "params": [
    {"key": "repo", "label": "GitHub 仓库", "example": "org/app", "required": true},
    {"key": "team", "label": "团队名", "required": false}
  ],
  "roles": [
    {"key": "triage", "name": "反馈分析", "description": "把 issue 理成需求：复现、影响面、优先级",
     "capabilities": ["需求分析"], "authority": ["web.research"], "model": "balanced"},
    {"key": "design", "name": "方案", "description": "...", "authority": ["file.write"]},
    {"key": "coder", "name": "编码", "description": "...", "authority": ["file.write", "shell.exec", "connector.use"]},
    {"key": "reviewer", "name": "审查", "description": "...", "authority": ["connector.use"]},
    {"key": "deployer", "name": "部署", "description": "...", "authority": ["shell.exec", "connector.use"]}
  ],
  "connectors": [
    {"slot": "github", "connector": "github", "access": "write", "roles": ["coder", "reviewer", "deployer"],
     "purpose": "读 issue、开分支与 PR、评审、合并"}
  ],
  "plugins": [
    {"name": "dev-relay", "version": "1.0.0", "source": "bundled",
     "settings": {"intake": "{role:triage}", "repo": "{param:repo}"}}
  ],
  "checkpoints": [
    {"at": "方案", "kind": "accept", "role": "design", "who": "requester", "note": "方案由提出需求的人验收后才进入编码"},
    {"at": "合并", "kind": "human_step", "plugin": "dev-relay", "note": "PR 合并前由人在群聊里说“#N 通过”"},
    {"at": "部署", "kind": "approve", "role": "deployer", "grant": "connector.use", "note": "部署岗位每次用 GitHub 都问它的所有者"}
  ],
  "files": ["files/开发规范.md"]
}
```

- `name` 同技能名规则；`version` 同插件。
- **占位符**：纲要、技能正文、模板文件、插件设置里可以写 `{param:<key>}`（建项目时填的值）与 `{role:<key>}`（担任这个岗位的成员名）。
  建项目时网络替换一次；插件设置里的 `{role:…}` 不替换成名字，而是存成岗位，见第 9 节。
- `roles[].model`：部署方模型目录里的预设 id；没有就用默认。`authority` 只是建议，建项目的人可以收窄。
- `connectors[].connector`：连接器目录 id，或电脑上的服务名、自定义连接器（同项目连接器面板的 `ConnectorNeed`）。
- `plugins[].source`：`catalog`（引用部署方目录里的同名插件，版本不够时提示）或 `bundled`（包在 `plugins/` 下）。

## 4. 发布

在项目里跑通以后，主持人点“发布为蓝图”：

1. **勾选部件**：纲要、哪些项目技能、哪些插件（带上当前的安装设置）、哪些档案文件当模板、连接器面板里哪些当槽位。
2. **岗位**：从项目成员生成，每个成员 Agent 一个岗位（名称、职责、能力、权限、模型来自那个 Agent），主持人可以合并、改名、删掉。
3. **参数**：主持人把纲要、技能、模板里具体的值换成 `{param:…}`，界面帮着找候选（仓库地址、公司名这类重复出现的字符串）。
4. **可移植检查**（网络做，不用模型）：
   - 纲要、技能、模板、插件设置里还写着项目成员的名字 → 提示改成 `{role:…}`；
   - 插件触发、`after` 的 @ 对象写死了名字 → 要插件支持岗位（第 9 节），否则标“建出来要手动改”；
   - 技能或模板引用了没被选进来的档案文件、`project/` 下的路径 → 提示；
   - 插件是上传的、按地址装的 → 只能打包进来（`bundled`），并说明接收方会看到插件确认卡；
   - 纲要、技能里像是项目事实的内容（日期、金额、客户名）→ 提示“蓝图不带数据，确认这是方法不是事实”（同技能包发布时的确认）。
5. **读者**：名单，或部署里所有登录用户（公开）。和技能包一样：蓝图去掉了数据，所以可以公开。
6. 发布后按版本固定（快照 `blueprints/<id>/v<N>/`，保留最近几个版本），是档案变化（`archive_rev` +1、`log.jsonl`、群聊里一条说明）。
   之后主持人可以“按项目现在的样子再发一版”。

也可以不从项目来：写好目录直接上传（管理员加进部署方目录，或主持人上传后发布）。

## 5. 人在哪里介入

不做流程描述语言。“五个岗位接力”由已有的东西拼出来：纲要和技能讲清楚每个岗位怎么做；插件负责推进（`route` 决定交给谁、外部回调把
issue / PR 事件带进来、`after` 在验收后交给下一棒）；人介入的点落到已有机制上。`checkpoints` 是这些机制的**声明**：建项目时网络按它设置，
蓝图页面与建好的项目页上按它列出“人在哪里介入”。

| `kind` | 落到什么机制上 | 建项目时网络做什么 |
| --- | --- | --- |
| `accept` | 用户任务由下发人验收（不变量 10） | 不用设置：现有行为；只在页面上列出 |
| `approve` | 权限每次问所有者：连接器授权 `ask`（`Project.connector_grants`），工作区外操作的审批 | 给担任这个岗位的 Agent 设成每次问 |
| `human_step` | 插件里只有人能做的一步（如「队友协作」的“#N 完成”只认人发的消息） | 不用设置：插件自己的规则；只列出 |
| `notify` | 插件触发 / `after` 代表某人 @ 成员 | 列出“代表谁”：建项目的人启用触发时确认 |

不支持的东西（比如“必须两个人都同意”）不在蓝图里硬造，等哪个插件需要时作为插件的规则做。

## 6. 用蓝图建项目

接收方在“蓝图”里挑一个，点“用它建项目”：

1. **总确认卡**，一次看全：
   - 要建的岗位，每个岗位的权限（可以去掉某项）；
   - 要装的插件：目录里的写“部署方审核过”；打包进来的带服务插件，列出 plugin-install.md 的确认条目（在哪里跑、拿到什么）；
   - 连接器槽位：每个槽位你有没有这个连接器的授权，没有就提示去连接（不连也能建，用到时 Agent 会提醒）；
   - 要配的外部回调（插件的 webhook 触发）；
   - 人在哪里介入（第 5 节的列表）。
2. **填空**：
   - 参数；
   - 每个岗位由谁担任：默认按岗位新建 Agent（归建项目的人、用他的模型、名字可改），也可以选自己已有的 Agent。
3. **建**（一个操作，失败整体回滚）：建项目（主持人是建项目的人）→ 纲要、模板文件、项目技能（替换占位符）→ 建或加入岗位的 Agent →
   记下岗位 → 装插件（带设置，岗位换成成员）→ 连接器槽位加进连接器面板（`ConnectorNeed`，`purpose` 写明给哪些岗位）→
   按 `checkpoints` 设授权 → 群聊里一条说明“由蓝图「x」v1 建立”。
4. **剩下的手工步骤**：项目页顶部一张清单，比如“去 GitHub 仓库设置里填这个回调地址”（触发的回调地址此时生成，只显示一次）、
   “部署岗位要用你的 GitHub 授权”。做完逐条勾掉。

建出来的项目是**一份拷贝**，和蓝图之后的变化无关；`Project.blueprint = {id, version}` 记来源。

## 7. 只取技能（原来的技能包）

蓝图的第二种用法：“把它的技能加到我的 Agent 上”，等于以前订阅技能包。语义照旧（[reference/releases.md](reference/releases.md) 的订阅）：
技能进 Agent 的技能层（项目技能 > 插件自带 > **蓝图的技能** > 连接器自带 > 我的技能），只在这一轮能到达的人都看得到这个蓝图时生效，
跟着蓝图的新版本走。占位符：技能里的 `{param:…}` 保留原样，`{role:…}` 换成岗位名。

迁移：现有的技能包（`kind: method`）原样变成只有技能的蓝图（没有岗位、插件、槽位），订阅关系保留；发布物里只剩交付件，
交付件之后改成项目的对外页面（另写设计）。

## 8. 升级

蓝图出了新版本，用它建的项目在项目页上看到“蓝图有新版本 v2”，打开是按部件的对比：

- 技能、模板文件：按内容对比；项目里改过的（和建项目时的那一版不一样）标“本地改过”。
- 插件：版本变化走插件升级（结构变化、数据去向照样要确认）。
- 岗位、连接器槽位、checkpoints：新增的、去掉的、改了的。

主持人逐项勾选要应用的；本地改过的默认不勾。网络不自动覆盖任何东西。第一期只做提示和“重新应用技能 / 插件”，逐项合并第二期做。

## 9. 依赖：岗位与插件设置

蓝图要可移植，插件里就不能写死成员名字。要先补两样（第一期的第一步）：

**项目岗位**：`Project.roles = {key: {name, description, members: [agent_id]}}`。不只为蓝图：插件、触发引用岗位而不是名字，成员改名、换人都不用改插件。
项目页“成员”里可以给成员挂岗位；蓝图建出来的项目自动有。

**插件设置**（`hooks.settings`，plugin-hooks.md 里一直没做的那项）：清单声明安装时要填的设置：

```json
"settings": [
  {"key": "intake", "label": "谁接新 issue", "type": "role"},
  {"key": "repo", "label": "仓库", "type": "text"}
]
```

- `type`：`text`、`select`、`role`（选项目里的一个岗位）、`member`（选一个成员）。
- 触发的 `notify.to`、`after.notify.to`、模板文本里可以写 `{setting:intake}`；`role` 类设置在每次触发时解析成那个岗位当前的成员。
- 插件服务通过 `_meta.matrix/settings` 拿到设置（`role` 类给出岗位与成员），`route` 的建议可以写岗位。
- 安装时主持人填；从蓝图装时由蓝图的 `plugins[].settings` 填好。

## 10. 目录与可见性

- **部署方目录**：管理后台“蓝图”页，和插件目录一样能从 git 仓库添加、上传、批准上架申请（同一套 `plugin_sources` 的形状）。
  目录里的蓝图对所有登录用户可见。
- **项目发布的**：读者名单或公开（第 4 节）。读者看得到蓝图页面（README、部件清单、人在哪里介入），看不到发布它的项目。
- 蓝图引用的目录插件在本部署没有时，蓝图页面标“缺插件 x”，建项目时不能继续（第二期跨部署导入时，打包的插件按插件自己装的规则走）。

## 11. 安全与不变量

候选不变量 25：**蓝图只带配方，不带数据、凭证与人；用蓝图建项目由人确认，建出来的一切归建项目的人。**

- 蓝图里没有记录、群聊、决定、用户任务、插件数据、任何凭证；发布时的可移植检查与“这是方法不是事实”的确认同技能包。
- 建项目只能由人在总确认卡上确认；新建的 Agent 归建项目的人，权限不超过他在确认卡上留下的；Agent 不能用蓝图建项目
  （第二期可以加 `propose_blueprint`，同 `propose_plugin` 由人批准）。
- 打包的插件按不变量 24：带服务的走沙箱或远程确认；目录里引用的按部署方目录。
- 蓝图的技能、纲要会进 Agent 的提示词：和项目技能一样是提示注入的入口。公开蓝图在目录里的由管理员审核；按读者分享的，接收方在确认卡上能看到全部技能正文。
- 建出来的项目和蓝图的发布方没有任何联系：发布方看不到谁用了（只看得到次数），接收方的运行不经过发布方。

## 12. 两个验证用的蓝图

**研发流程**（第一期的端到端验证）：第 3 节的清单。要一个新插件「研发接力」（`examples/plugins/dev-relay/`，在「队友协作」的基础上）：

- webhook 触发：issue 开了 → @ `{setting:intake}`（反馈分析）；PR 开了 → @ 审查岗位；
- `route`：按任务所处阶段建议下一棒（反馈分析 → 方案 → 编码 → 审查 → 部署），每条人发的消息 3 次预算照旧；
- `after`：用户任务验收后，代表验收的人 @ 下一阶段的岗位；
- 只有人能做的一步：“#N 通过”（合并前），“#N 上线”（部署后确认）。

GitHub 连接器先用演示服务代替（同 `examples/delivery-dashboard/delivery_data_mcp.py` 的做法），等 #60 的出口代理做好换成 skill + API。

**看板**：从 `examples/delivery-dashboard` 改出来。岗位“看板设计师”；槽位“交付数据（读）”；插件「交付看板」（页面、表、定时刷新）；
技能“做看板”与连接器自带的查数口径；参数“指标口径说明”“区域”。验证“只取技能”与原技能包的迁移。

## 13. 分期

**第一期**（本部署内）：

1. 项目岗位（`Project.roles`）与插件设置（`hooks.settings`、`{setting:…}`、`role` 类设置），「队友协作」改用岗位。
2. 蓝图的格式、发布（从项目生成、可移植检查、版本快照）、读者与公开、部署方目录（管理后台“蓝图”页）。
3. 用蓝图建项目（总确认卡、填空、整体回滚、剩下的手工步骤清单）。
4. 只取技能；技能包迁移成蓝图，发布物里只剩交付件。
5. 示例：研发流程蓝图与「研发接力」插件（脚本运行时跑通，再用 dsh 实测），看板蓝图。

**第二期**：导出文件、跨部署导入（打包的插件走 plugin-install.md）；岗位由人担任；升级的逐项合并；`propose_blueprint`。

**不做**：流程描述语言；蓝图带数据或凭证；建出来的项目和蓝图保持实时联动。

## 14. 参照

凭公开文档的印象，没有做调研笔记；要落实细节时补 `research:` 笔记。

- Dify 的应用导出：导出整个应用，依赖的插件在导入时提示安装，不带密钥 → 取“依赖在导入时补齐”。
- n8n 模板：凭证只是占位，导入时绑定 → 连接器槽位。
- Helm chart：参数（values）+ 版本 + 升级 → 参数与第 8 节的升级。
- GitHub 模板仓库、Notion 模板：纯复制、没有升级 → 我们多一层来源版本与升级提示。
- 不取任何一家的工作流描述语言：Matrix 不硬编排流程（第 5 节）。
