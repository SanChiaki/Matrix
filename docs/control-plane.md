# 控制面：重启不丢、故障可接管、可分片扩容（设计，未实现）

2026-11-16 定方向。对应需求 #76。执行面（沙箱）的方案在 [cloud-runtime.md](cloud-runtime.md)，那边第 12 节列了控制面挡住的问题，
这篇是它们的解法。登录的加固（[reference/security.md](reference/security.md) 第一条）也放在这里，因为它是“生产级”缺的另一块。

## 0. 结论

1. **不做“无状态、多实例同时写”。** 引擎是一把全局锁加内存里的对象图（`engine.py` 里 275 处 `with self._lock`、92 处整份保存），
   改成每个请求都读写数据库等于重写引擎。改成：**一个租户同一时刻只有一个核心实例在写（单写者），状态增量落库，另有备机随时接管。**
2. **重启不再打断云侧运行。** 一轮运行拆成“派出去”和“收回来”两段，中间不靠一个阻塞的线程；沙箱客户端断线后重连认领原来的轮次，
   回调带编号、可重发。
3. **扩容分三层，按需要做到哪层。** 执行面与出口网关本来就能加节点；核心靠备机解决可用性，不靠多实例解决容量；
   容量真的不够时按租户分片，每个租户一个单写者核心。
4. **状态进数据库，单机用 SQLite，要备机时用 PostgreSQL**，同一套表。事件落库，网页断线重连不丢事件。
5. **登录按生产要求补齐**：会话过期与轮换、令牌只存哈希、CSRF 校验、登录限流、企业单点登录。

业界把“大脑”做成无状态、会话存成外部事件日志（research: cloud-agent-isolation#brain-hands-session）。Matrix 的核心不照搬的原因在第 9 节。

## 1. 现状（代码里核对过）

| 方面 | 现在怎么做 | 后果 |
| --- | --- | --- |
| 持久化 | `Store.save` 每次把全部状态序列化成一个 `state.json`，写临时文件再替换 | 状态越大每次保存越慢；只能有一个进程写 |
| 一轮运行 | `_round_safe` 提交到 16 个线程的池，`_invoke` 阻塞到运行时返回结果，然后才写回私有目录、交付、记用量 | 同时最多 16 轮；进程一退出，“收回来”那一半永远不会执行 |
| 执行上下文令牌 | `_invoke` 里现生成，放在内存的 `_contexts` | 重启后在途的回调全部认不出 |
| 等待中的审批、提问 | 记录在库里，但等待方是内存里一个阻塞的线程（`_approval_waits`、`_question_waits`） | 重启即作废 |
| 客户端断线 | `DeviceRuntime.abort_all`：在途的轮次立刻按传输错误结束 | 控制面重启等于全部云侧轮次失败 |
| 事件 | `EventBus` 在内存里留最近 5000 条；SSE 支持 `Last-Event-ID`，但序号不持久化 | 重启后网页要整页重新拉；重启期间的事件丢失 |
| 定时 | 进程里一个循环线程，`last_fired` 在库里 | 两个实例会各触发一次 |
| 长连接 | 端侧设备（以后还有沙箱客户端）的连接注册在内存的 `_runtimes` | 只有接受连接的那个进程能给它派活 |
| IM 机器人 | 每个机器人一条出站长连接 | 两个实例的连接互相顶掉 |
| 文件 | 项目档案、私有目录、附件、发布物、工作目录都在本机数据卷 | 备机读不到 |
| 登录 | 令牌明文作键存在状态里，30 天 cookie，不过期不轮换；cookie 没有 `Secure`；没有 CSRF 令牌与登录限流 | 只适合内网演示 |

## 2. 目标与不做的

目标：

- 确认过的写入不丢（进程被杀、机器断电后都在）。
- 发版、重启不打断云侧在途的轮次，网页不丢事件。
- 核心所在的机器坏了，一分钟内由备机接管，不需要人工操作。
- 保存一次的耗时不随总状态变大而变大。
- 一个租户的规模上限由实测给出（第 10 节），不够时有分片这条路。

不做：

- 一个租户内多个核心同时写。
- 跨地域多活。
- 跨租户协作（CHARTER 已定：A2A 只在网络边界）。

## 3. 结构

```
        浏览器 / IM / 端侧客户端 / 沙箱客户端（经出口网关）
                          │
                     入口（反向代理）：只把流量给持有租约的那个核心
                          │
   ┌──────────────────────▼───────────────────────┐      ┌──────────────────────┐
   │ 核心（主）：引擎、对象图在内存、单写者        │      │ 核心（备）：不接流量，│
   │ 每次保存只把变了的行写进数据库，带租约代数    │◀─租约─▶│ 租约到期就加载状态接管│
   └───────┬───────────────────────┬──────────────┘      └──────────┬───────────┘
           │                       │                                │
   ┌───────▼────────┐      ┌───────▼─────────┐              （同一个数据库、
   │ 数据库          │      │ 文件：内容存储、 │                同一份文件）
   │ 实体、消息、事件│      │ 档案、私有目录   │
   └────────────────┘      └─────────────────┘
```

单机部署就是只有“主”、数据库用 SQLite、文件在本机卷：和现在一样是一个进程，只是存储换了。

## 4. 存储

### 4.1 表

不为每种对象设计一套列，沿用现在的 dataclass 与 `store._known`（丢弃未知字段、缺失取默认）的兼容办法：

| 表 | 内容 | 写法 |
| --- | --- | --- |
| `entity(kind, id, data, rev)` | 一行一个对象（Agent、项目、对话、委托、审批……），`data` 是现在 `to_dict` 的 JSON | 变了才写 |
| `message(conversation_id, seq, data)` | 对话消息。现在整段塞在对话对象里，对话越长每次保存越大 | 只追加 |
| `event(seq, ts, type, data)` | 现在的事件总线 | 只追加，按保留期清理 |
| `run(id, unit_id, state, token_hash, session_id, last_event_seq, …)` | 在途与结束的轮次（第 5 节） | 状态变化时写 |
| `call(run_id, call_id, kind, result)` | 轮次里每一次工具、审批、提问回调的结果（第 5.2 节） | 只追加 |
| `lease(tenant, holder, epoch, expires)` | 谁是主（第 6 节） | 续约时写 |

### 4.2 增量保存，不改 92 处调用

`Store.save()` 的调用点不动，实现换掉：保存时把每个对象序列化、算哈希，和上次落库时的哈希比，只把变了的行放进**一个事务**写下去；
新消息按序号追加进 `message`。CPU 开销和现在同量级（现在也是全部序列化），省掉的是整份重写磁盘。之后再给最热的路径
（收消息、写事件）加显式的“这个对象变了”标记，跳过全量比对。

一次保存一个事务：要么全部落下，要么都没落，和现在“写临时文件再替换”的保证一样。

### 4.3 两种数据库

- **SQLite（WAL 模式）**：单机默认，零运维，标准库就有。
- **PostgreSQL**：要备机时用（主备要读写同一个库）。

两者只用到最基本的 SQL，薄薄一层自己写，不引 ORM。

### 4.4 事件落库

事件总线写进 `event` 表，序号全局递增且持久。SSE 的 `Last-Event-ID` 续接从表里读，所以重启、切换主备之后网页自动接上，不丢事件。
内存里仍留一段最近的事件做缓存。事件表和状态一样敏感、一样保护，保留期默认 7 天。

### 4.5 文件

| 内容 | 性质 | 放哪 |
| --- | --- | --- |
| 附件、发布物快照、模板版本、产物检查点、材料 | 写一次不再改，按内容或版本寻址 | 内容存储接口：本机目录，或 S3 兼容的对象存储 |
| 项目档案文件、私有目录、插件数据 | 会改，私有目录还要三方合并 | 单机在本机卷；要备机时放共享卷（云盘或 NFS）。不拆进对象存储：合并逻辑依赖文件系统语义，改动大、收益小 |
| 工作目录 | 执行面的，见 cloud-runtime.md | 沙箱的卷 + 检查点 |

### 4.6 从 `state.json` 迁过来

第一次用新版本启动时，发现有 `state.json` 而库是空的，就整份导入（走现有的 `Store._load`，旧数据的兼容逻辑照用），
然后把 `state.json` 改名留作备份。回退：`matrix export-state` 把库导回一份 `state.json`，旧版本直接能读。

## 5. 重启不打断运行

### 5.1 一轮拆成两段

现在 `_run` 是一个从头阻塞到尾的函数。拆成：

- **派出去**：算好提示词、材料清单、权限，建一条 `run` 记录（状态 `running`），把请求发给运行时，返回。不占线程等结果。
- **收回来**：运行时的结果到了（或超时、被终止），按 `run` 记录找到这一轮，做现在 `_run` 的后半段：写回私有目录、更新会话、
  交付、记用量、清只读副本、把没回答的提问转给人。

两段之间的全部信息在 `run` 记录里，所以核心重启后，结果照样有人收。线程池不再是并发上限。

端侧设备与沙箱都走这条路。`ScriptedRuntime` 是进程内同步的，“派出去”之后立刻“收回来”，测试不受影响。

### 5.2 回调可以重发，结果只算一次

沙箱客户端发给核心的每个请求（工具调用、审批、提问、事件）都带 `run_id` 和递增的 `call_id`。核心处理完把结果记进 `call` 表再回。
客户端没收到回执（断线、核心重启）就在重连后原样重发；核心看到记过的 `call_id`，直接回上次的结果，不再执行一遍。
这样工具的副作用（委托、写档案、调连接器）不会因为重发而发生两次。做法同持久化执行的“已完成的步骤从日志读”
（research: cloud-agent-isolation#durable-execution）。

审批与提问不再需要一个阻塞着的线程：请求到了就建记录、回“等待中”；人回答时写进 `call` 表，客户端下次来问（或经长连接推给它）就拿到。
所以重启不再让它们作废。

### 5.3 重连认领

- 执行上下文令牌的哈希记在 `run` 里，重启后还认。
- 客户端断线后不再放弃在途的轮次：dsh 继续跑，事件在本地按序号排队，工具回调阻塞着等。重连后先报“我这里有哪些 `run_id` 在跑、
  各自发到第几个事件”，核心核对后让它从缺的那一个事件补发。
- 核心启动后给在途的轮次一个宽限期（默认 60 秒）。期内客户端回来就接着跑；没回来的，按现在的不变量 12 判失败、可续接。

### 5.4 不变量 12 的改写

> **重启语义**：控制面重启不打断在途的轮次。云侧轮次在宽限期内由沙箱客户端重连认领，期满没人认领的判失败、可续接；
> 端侧任务照旧回到等待。等待中的审批、提问在重启后仍然有效。

## 6. 故障接管

- **租约**：`lease` 表里一行，持有者每 5 秒续约，15 秒没续就算过期，备机把自己写成持有者并把代数加一。
- **防止两个主**：每个写事务都带条件“代数等于我拿到的那个”。旧主如果只是卡住了没死，它醒来后的第一次写入会失败，随即自己退出。
  这比“靠超时猜对方死了”可靠，租约只负责“谁来接”，代数负责“旧的不能再写”。
- **接管要做的**：从库里加载状态（和现在启动时读 `state.json` 一样，只是来源换了），接上定时、IM 连接，开始接流量。
  之后走 5.3：客户端重连认领轮次，网页凭 `Last-Event-ID` 续上。
- **入口**：反向代理按健康检查只把流量给主（主返回 200，备返回 503）。端侧客户端与沙箱客户端本来就会断线重连，重连时自然到新主。
- **定时不重复**：只有主跑定时循环；触发时在同一个事务里更新 `last_fired`，接管后的新主看到已经触发过就不再触发。
  主挂掉期间错过的定时，接管后补触发一次（只补最近一次，不把积压的全部补上）。
- **IM**：只有主持有机器人的长连接，“两个实例互相顶掉”的问题随单写者一起消失。

SQLite 的单机部署没有备机：进程被拉起后同样走 5.3，在途的轮次不丢，只是机器本身坏了要靠备份恢复。

## 7. 扩容

| 层 | 怎么扩 | 什么时候需要 |
| --- | --- | --- |
| 执行面：沙箱节点 | 加节点（cloud-runtime.md 12.4） | 并发的执行单元多了 |
| 出口网关 | 无状态，每个节点一个或前面加负载均衡；鉴权时向核心查这个执行单元当前的权限，结果短时缓存 | 模型调用与出网的流量大了 |
| 核心 | 换大机器 + 备机。核心不跑 Agent 的代码、不转发模型流量，负载是消息、调度与落库 | 先实测（第 10 节）再说 |
| 租户分片 | 每个租户（一家企业、一个部署单元）一个单写者核心、各自的库或 schema；入口按域名路由；沙箱节点与网关共用，执行单元凭证里带租户 | 一套服务给很多互不相干的组织用 |

私有化部署一家企业就是一个租户，用不到分片。分片是给“一套服务托管很多组织”准备的，那时租户之间本来就不协作，天然可分。

## 8. 登录与会话

| 现在 | 改成 |
| --- | --- |
| 登录令牌明文作键存在状态里 | 只存 SHA-256（和设备令牌一样），库泄露不等于会话泄露 |
| 30 天 cookie，不过期、不轮换 | 闲置 7 天过期、最长 30 天；登录、改密码时换新令牌，改密码后其余会话全部作废；“我的会话”页可以逐个下线 |
| cookie 是 `HttpOnly` + `SameSite=Lax` | 经 HTTPS 时加 `Secure`；改状态的请求（非 GET）校验 `Origin` / `Referer` 是自己的站点，再加双提交的 CSRF 令牌 |
| 登录、注册没有限流 | 按账号与按来源地址分别限流，连续失败后指数退避；设备配对已有的上限（`auth.PAIR_*`）保留 |
| 只有邮箱 + 密码 | 加 OIDC 单点登录，企业部署推荐只开它：密码策略、多因素、离职回收都交给企业自己的身份系统。本地密码保留给单机与演示 |
| 没有邮箱验证、找回密码 | 配了发信服务才开；没配时由管理员在后台重置 |
| 管理操作不留痕 | 后台的改动（模型目录、插件策略、IM 机器人、重置密码）记审计日志，只追加 |

做完之后 `security.md` 第一条“只监听 127.0.0.1、不要暴露到公网”改成“对外只经带 TLS 的反向代理”，Caddy 前面那层 basic auth 不再是必需的。

## 9. 为什么不照搬“无状态大脑 + 会话日志”

托管 Agent 的做法是 harness 完全无状态，每一步写会话日志，崩了由任何一个新实例读日志接着干。Matrix 的核心不这么做，原因有三：

- **它不是一个会话的循环，而是一张关系网**：项目、成员、委托链、收件箱、信息流标签互相引用，一次操作常常同时改好几个对象并检查不变量。
  现在靠一把锁加内存里的对象图保证一致；拆成多个实例各自读写，每条不变量都要重新证明一遍。
- **核心的负载轻**：重的是模型调用与 Agent 执行，它们已经在核心之外（网关与沙箱）。为了容量把核心做成多实例，投入和收益不成比例。
- **要的其实是“崩了不丢、能接管”**，单写者加落库加备机就能给到。

学过来的是它的另外两点：要活下来的状态都不放在进程里（第 4、5 节），执行程序对上层只是一个可以重试的调用（5.2）。

## 10. 待验证

1. **一个核心能撑多大**：用 `ScriptedRuntime` 写压测（同时在途的轮次数、每秒消息数、总对象数），看全局锁的等待时间与保存耗时。
   这决定第 7 节“核心”那一行什么时候不够用。
2. **加载时间**：状态有几万个对象、几十万条消息时，从库里加载要多久。超过接管目标（一分钟）就要让备机提前加载、跟着事件表追。
3. **SQLite 的写入**：每条消息、每个事件一次事务提交，在机械盘与云盘上的吞吐。不够就把事件合并提交（事件丢最后几百毫秒可以接受，实体与消息不行）。
4. **dsh 在回调长时间不返回时的表现**：核心重启的几十秒里，沙箱里的工具调用阻塞着等。网络工具的超时是 1800 秒，应当没问题，
   但提问、审批插件与 MCP 桥各自的超时要逐个确认。
5. **哈希比对的开销**：对象很多时每次保存全量序列化要多久，决定显式“变了”标记要做到多细。

## 11. 分阶段

每个阶段单独可上线。C0、C1 不依赖执行面的改造，可以和 cloud-runtime.md 的阶段 0、1 并行。

| 阶段 | 内容 | 验收（能变红的） |
| --- | --- | --- |
| C0 登录加固 | 第 8 节，除单点登录。**已做**：令牌只存哈希、闲置 / 最长过期、`Secure`（`MATRIX_COOKIE_SECURE`）；**未做**：CSRF、限流、“我的会话”页 | 令牌过期后请求被拒；跨站的改状态请求被拒；连续输错后被限流；库里找不到明文令牌 |
| C1 存储 | SQLite、增量保存、消息与事件落库、从 `state.json` 导入与导出 | 压测中随机杀进程再启动：确认过的消息与委托都在，不变量测试全过；保存耗时不随总状态增长；网页重连不丢事件 |
| C2 重启不打断 | 一轮拆两段、回调带编号可重发、重连认领、不变量 12 改写。依赖 cloud-runtime.md 阶段 1（沙箱客户端） | 轮次进行中重启核心：轮次正常结束；重发的工具调用只生效一次；等待中的审批在重启后批准仍然有效 |

## 12. 对现有约定的影响

- 不变量 12 改写（5.4）。
- 新增一条：**一个租户同一时刻只有一个核心在写**，由租约代数在每个写事务里保证。
- AGENTS.md 工作方式第 6 条（`Store._load` 要能读旧的 `state.json`）继续有效：导入走的就是它；之后的结构变化仍靠 `_known` 兼容。
- `deploy/` 多一种部署：主 + 备 + PostgreSQL + 共享卷。单机部署不变，只是数据卷里 `state.json` 换成一个 SQLite 文件。

## 13. 明确不做的

- 不引入消息队列、分布式锁服务、持久化执行框架：租约和幂等用数据库就够，少一个要运维的组件。
- 不把私有目录、项目档案拆进对象存储。
- 不做一个租户内的多写。
