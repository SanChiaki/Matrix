# 云侧执行面：生产级方案（设计，未实现）

2026-11-10 定方向。解决需求 #59（Matrix 与云端 Agent 隔离、云端 Agent 之间隔离）与 #68（材料不再每轮整份拷贝、资源上限、
模型密钥不进执行面），并为 #60（出口代理注入连接器凭证）提供前提。现状与逐条欠账见
[reference/device-runtimes.md](reference/device-runtimes.md#cloud-debt)，风险见 [reference/security.md](reference/security.md)。

## 0. 结论

1. **控制面不再执行任何 Agent 代码。** Matrix 服务（网络、存储、凭证）只做调度；云侧 Agent 一律跑在沙箱里。
2. **一个执行单元一个沙箱。** 执行单元 = 一个席位或一个委托（Agent × 场合）。沙箱的边界是独立内核级的（gVisor 或 microVM），
   不是路径、不是同一内核上的普通容器。
3. **云侧沙箱就是一台“网络托管的设备”。** 沙箱里跑的是现有端侧客户端（`matrix/connector/`）的同一套代码，说同一套协议。
   端侧已经是“执行面只拿网络给的副本、只经令牌回调”的形状，云侧对齐它，而不是另造一套。
4. **沙箱里没有任何长期凭证，出网只有一条路。** 模型调用、网页访问、以后的连接器请求都经出口网关；模型密钥留在控制面。
5. **沙箱可以随时丢。** 工作目录的产物每轮结束在控制面留检查点；沙箱或节点没了，只损失正在跑的那一轮和可重建的缓存。

选型：单机用 Docker + gVisor（`runsc`），集群用 Kubernetes + RuntimeClass（gVisor，或有 KVM 时用 Kata Containers）。
两者在同一个 `SandboxProvider` 接口后面，引擎不关心是哪一个。

## 1. 现状的问题

云侧现在是 Matrix 服务用子进程起 dsh，同一台机器、同一个系统用户，隔离只靠 dsh 的 bwrap“写只能写工作目录”：

| 被诱导的 Agent（有 `shell.exec`）现在能做什么 | 原因 |
| --- | --- |
| 读整个数据目录：别人的私有目录、对话、任务产物、项目档案、`state.json`（含密码哈希）、`vault.key` | 沙箱只管写不管读 |
| 读所有用户的 dsh 会话记录与 dsh 里配的模型凭据 | `~/.dsh` 是全体云侧 Agent 共用的一个目录 |
| 访问部署机能到的任何内网地址、云厂商元数据接口、本机的 Matrix 端口 | 共用宿主的网络，没有出网限制（`fetch.json` 只管 `web_fetch` 工具，管不到 `curl`） |
| 拖垮整台服务器 | 没有 CPU、内存、进程数、磁盘上限 |
| 可能读到模型密钥 | 密钥在 dsh 进程的环境变量里，只靠 dsh 按变量名过滤 |
| 利用内核漏洞拿到宿主 | Matrix 容器为了让 bwrap 能跑，关掉了 seccomp（`seccomp=unconfined`） |

所以不变量 7、8、13、16、22 目前只在提示词、网络工具与 API 层成立。下面的方案让它们在文件、进程、网络三层都由结构保证。

## 2. 威胁模型

- **对手**：云侧 Agent 执行的任何代码。Agent 读到的内容（群聊里别人的消息、网页、附件）都可能带注入，所以把“沙箱里的进程”
  整体当作不可信，包括 dsh 自己和沙箱里的客户端。
- **要保护的**：控制面的状态与凭证（`state.json`、vault、模型密钥、连接器凭证）；别的执行单元的工作目录、会话、私有目录；
  宿主机与部署方内网。
- **可信的**：控制面、沙箱管理器、出口网关、宿主内核与沙箱运行时。
- **不在本方案内**：模型经**允许的**通道把本场合的内容带出去（由不变量 21、22 与出口策略管，见 6.4）；侧信道；
  部署方管理员读数据（现在只靠政策）。

## 3. 总体结构

```
浏览器 / IM / 端侧客户端
        │
┌───────▼────────────────────────── 控制面（可信） ───────────────────────────┐
│ Matrix 服务：网络、状态、vault、调度                                         │
│   ├─ 沙箱管理器 matrix-sandboxd：唯一能创建 / 销毁沙箱的组件                 │
│   ├─ 出口网关 matrix-gateway：模型代理、网页出网、（以后）连接器凭证注入     │
│   └─ 内容存储：材料（按 sha）、产物检查点、私有目录的权威副本                │
└───────┬─────────────────────────────────────────────▲──────────────────────┘
        │ 创建沙箱（镜像、配额、一次性启动令牌）       │ 沙箱只连得到网关：
        ▼                                             │ 客户端长连接、模型、网页
┌──────────────── 执行面（不可信，每个执行单元一个沙箱） ────────────────────┐
│ 沙箱客户端（connector 代码）→ dsh → Agent 的命令（dsh 自己的 bwrap 照旧）  │
│ /workspace：这个执行单元的卷（读写）   /state：dsh 会话（只属于这个单元）   │
│ 只读根文件系统、非 root、独立 PID / 网络命名空间、cgroup 配额               │
└────────────────────────────────────────────────────────────────────────────┘
```

三个新组件，各管一件事：

| 组件 | 职责 | 为什么单独一个 |
| --- | --- | --- |
| 沙箱管理器 `matrix-sandboxd` | 按规格创建、停止、销毁沙箱与卷；上报状态与资源用量 | 创建容器的权限等于宿主 root（Docker socket）。Matrix 服务不持有它，只能经一个窄接口提请求，参数只有标识与配额，镜像与安全选项写死 |
| 沙箱客户端（`matrix/connector/` 复用） | 在沙箱里接收一轮运行、补齐材料、起 dsh、把工具 / 审批 / 提问 / 事件回传 | 已有代码与协议，端侧每天在用 |
| 出口网关 `matrix-gateway` | 沙箱唯一的网络出口：鉴别是哪个沙箱、按这一轮的权限放行、注入密钥、记账留痕 | 密钥与出网策略必须在执行面之外 |

## 4. 沙箱

### 4.1 隔离单位

一个执行单元（席位或委托）一个沙箱，不是一个用户一个、也不是一轮一个：

- 比“一个用户一个”细：不变量 22 要求私有目录按来源场合挂载，同一个人的两个场合之间也不能互相读，一个用户一台机器做不到文件层的强制。
- 比“一轮一个”粗：dsh 会话续接、工作目录里装好的依赖要跨轮保留。沙箱在这一轮结束后空闲一段时间（默认 10 分钟）才停，
  卷留着；下一轮来了再起。

参照 Meta Muse“Agent 在隔离单元里，凭据与授权在外面的服务里，Agent 只拿替身令牌”（research: meta-muse#vm、
meta-muse#credentials-injection），粒度按 Matrix 的场合收细。

### 4.2 运行时选型

| 部署形态 | 沙箱运行时 | 说明 |
| --- | --- | --- |
| 单机（现在的 compose） | Docker + gVisor（`--runtime=runsc`） | 不需要 KVM。私有化部署常见的云主机没有嵌套虚拟化，gVisor 仍能用 |
| 集群 | Kubernetes，Pod 指定 RuntimeClass：gVisor；节点有 KVM 时可选 Kata Containers | 接口相同，只换 RuntimeClass |
| 本机开发、测试 | `process`：现在的子进程方式 | 只给单人本机用；多用户部署拒绝启动云侧运行（4.5） |

不选的：

- **普通容器（runc）当安全边界**：和宿主共用内核，Agent 能执行任意代码时不够。只在部署方显式写 `insecure-runc` 时允许，后台长期标红。
- **直接基于 Firecracker 自建**：镜像、网络、快照、调度都要自己做。需要 VM 级边界时用 Kata，它把这些包在容器接口后面。
- **第三方托管沙箱服务**：Matrix 的部署多在企业内网，数据不能出去。`SandboxProvider` 接口留着位置，不作为默认。

### 4.3 沙箱里有什么

镜像由部署方构建、带版本：dsh（钉版本）、沙箱客户端、Python 与 Node、常用命令行工具；部署方可以在它之上加自己的工具
（#60 的 CLI 连接器就装在这里）。镜像里没有任何密钥。升级 dsh 时 `matrix-dsh-check` 在这个镜像里跑。

每个沙箱：

- 非 root 用户、去掉全部 capabilities、默认 seccomp、`no-new-privileges`、只读根文件系统，`/tmp` 是有上限的 tmpfs。
- 独立的 PID、挂载、IPC、网络命名空间。Agent 的命令看不到沙箱之外的任何进程。
- 挂载只有两处：`/workspace`（这个执行单元的卷）和 `/state`（dsh 的会话与配置，同一个卷的另一个子目录，`HOME` 指向它）。
  不挂宿主目录，不挂 Docker socket，不挂数据目录。
- 配额（cgroup，默认值，部署方可调）：2 核、4 GB 内存、512 个进程、卷 10 GB、出网流量与速率上限。超了只影响这个沙箱。
- dsh 自己的 bwrap 沙箱**照旧开着**：`build_patch_yaml` 的权限覆盖层、“写只能写工作目录”、外溢审批（不变量 14）都不变。
  外层沙箱负责读隔离与爆炸半径，内层负责权限词表，两层各管各的。

控制面的 Matrix 容器不再需要 `seccomp=unconfined` 与 `systempaths=unconfined`，一并去掉。

### 4.4 生命周期

```
没有 ──创建──▶ 运行中 ──空闲超时──▶ 已停（卷保留）──执行单元结束后保留期满──▶ 已销毁（卷删除）
                  ▲                    │
                  └────有新一轮────────┘
```

- **创建**：管理器起沙箱，注入一次性启动令牌；沙箱客户端用它连回控制面，令牌换成这条连接的身份（绑定执行单元、Agent、所有者），
  用过即废。之后这条连接上只接受派给这个执行单元的运行。
- **容量不够时是等待，不是失败**：沿用端侧“不可达是等待”的语义（任务进 `WAITING`、不消耗重试），按用户并发上限与全局上限排队。
- **冷启动**：gVisor 容器起动在秒级；需要时管理器保持少量预热好的空沙箱（未绑定任何单元，绑定时才挂卷、发令牌）。
- **销毁**：委托验收或作废、对话归档或删除、Agent 删除后，过保留期删卷。删之前产物已有检查点（5.2）。
- **重启语义（不变量 12）第一期不变**：控制面重启时，云侧运行中的轮次判失败可续接；管理器在重连后结束没人认领的运行。
  执行面独立之后可以做到“控制面重启不打断运行”，留到以后。

### 4.5 失败时关闭

- 启动参数 `--isolation required`（多用户部署的默认）：没有可用的沙箱后端、或后端是 `process` / `insecure-runc` 时，
  云侧运行一律拒绝并在后台写明原因，不退回子进程方式。端侧运行不受影响。
- `RuntimeCapabilities` 加一项 `isolation`（`none` / `sandbox` / `vm`），Agent 页与管理后台显示当前云侧的隔离等级。

## 5. 数据怎么进出沙箱

原则：沙箱拿到的都是控制面按这一轮的可见性算好、主动给的副本；沙箱交回来的都经控制面校验后才进入网络的状态。

### 5.1 进：材料

复用端侧的“清单 + 缓存”（[reference/device-runtimes.md](reference/device-runtimes.md)“材料”）：

- 项目档案文件、这个席位看得到的附件、订阅的发布物、技能、插件挂载：`run.request` 只带清单（路径、sha、大小），
  沙箱客户端按 sha 补齐缺的，控制面只回这一轮清单里的 sha。
- 缓存在这个执行单元自己的卷里。第二轮起没变的文件一个字节都不传，#68 的“每轮整份拷贝”随之消失。
- 以后的优化（不在第一期）：节点上一份按 sha 的只读存储，由管理器只读挂进沙箱，免去沙箱内的拷贝。缓存由管理器管、沙箱只读，
  所以沙箱拿不到清单之外的内容。

### 5.2 出：产物检查点

每轮结束，沙箱客户端按 `workdir.outputs` 的口径报产物清单（路径、sha、大小），控制面取回有变化的文件，存进内容存储，
记为这个执行单元的最新检查点。每个单元的检查点有总量上限（默认 1 GB，超出的文件只记清单、需要时再向沙箱取）。

这样委托交付（`deliveries/`）、人浏览与下载工作目录、`publish_file` / `send_file` 都读检查点，不需要沙箱还活着，
也不需要控制面去读执行面的磁盘。沙箱或节点丢了，从检查点恢复产物，依赖目录（`node_modules`、`.venv` 等，本来就不算产物）重装。

### 5.3 私有目录

权威副本留在控制面（`<data>/agents/<id>/`），语义不变（不变量 8、15、22）：

- 进：这一轮按来源场合算出的可挂部分作为材料下发到 `agent-home/`，没挂的文件沙箱里不存在。
- 出：轮次结束，沙箱客户端上报 `agent-home/` 里改过、删过的文件，控制面用现有的三方合并（`homedir.sync_back`）写回并更新来源标签。
  有别人的场合里技能改动照旧不写回。

端侧协议里私有目录是“留在设备上、客户端自己合并”；云侧多一种方式“由网络持有、材料进、改动出”，是协议上唯一要新增的东西。

### 5.4 dsh 会话

每个执行单元的 `/state` 里只有它自己的会话。共用的 `~/.dsh`（`dsh-home` 卷）退役：模型供应商一律用平台配置
（`models.json` + vault），不再读 dsh 自己存的凭据。

## 6. 出口网关

### 6.1 网络形状

每个沙箱的网络只有一条路由：到网关。沙箱之间、沙箱到宿主、到内网、到云厂商元数据地址、到控制面的 `/api` 都不通。

- Docker：沙箱接在 `internal` 网络上（没有对外路由），关掉容器间互通，只有网关同时接这张网与外网。
- Kubernetes：命名空间默认拒绝全部出入流量的 NetworkPolicy，只放行到网关。
- DNS 也只经网关解析，避免用 DNS 查询带数据出去。

网关用两样东西认定请求来自哪个沙箱：来源地址（管理器登记的）与沙箱令牌（创建时下发，只在网关有用）。
再由控制面查到执行单元当前这一轮的权限。不信任请求里自报的任何身份（不变量 10）。

### 6.2 三类流量

| 流量 | 怎么走 | 网关做什么 |
| --- | --- | --- |
| 沙箱客户端 ↔ 控制面 | 出站长连接（和端侧一样的 WebSocket 协议），经网关转到控制面的专用端点 | 只转发到这一个端点。网络工具、审批、提问、连接器代调用都在这条连接里，沙箱不需要直接访问 `/internal/*` |
| 模型调用 | dsh 的供应商地址指向网关（`/llm/<供应商>`），密钥位置填沙箱令牌 | 核对供应商与模型是控制面给这一轮定的那个；换上 vault 里的真密钥转发；流式透传；按响应记用量 |
| 网页与包下载 | 沙箱里设 `HTTPS_PROXY` 指向网关（没有别的路，所以不理它的进程只是连不上） | 有 `web.research` 才放行公网；内网目标只认 `fetch.json` 的 `allow`；包仓库只认部署方配的镜像源；每个请求记一行（主机、方法、状态、字节数、执行单元），不记内容 |

模型密钥从此不进执行面，“密钥经 dsh 进程环境变量”这条欠账与 `key-hidden` 检查的前提一起消失
（检查保留，改为确认沙箱里确实没有密钥）。用量由网关按实际响应记，不再只依赖 dsh 自报。

### 6.3 连接器凭证（#60）

`connectors-and-skills.md` 第 11.3 节的出口代理就是这个网关的第四类流量：按“执行单元 + 目标域名”把占位值换成 vault 里的凭证，
写请求逐次确认。它要求网关终止 TLS、沙箱信任网络的 CA，放在本方案第三阶段，前提（只能经网关出网）由第二阶段提供。

### 6.4 允许的通道上的外泄

隔离做完以后，剩下的外泄途径是允许的出网本身：读过别人内容的会话把内容发到公网。这是策略问题，不是隔离问题，沿用不变量 21 的思路：
网关可以对“这一轮读过越界来源或共享项目内容”的执行单元收紧出网（只读请求、或只到白名单）。是否启用、默认值是什么，实施第二阶段时另定。

## 7. 引擎里怎么接

改动集中在运行时这一层，席位、委托、审批、提问、信息流的语义都不动：

```python
class SandboxProvider(Protocol):
    def ensure(self, spec: SandboxSpec) -> SandboxHandle: ...   # 幂等：按执行单元 id，已在运行就返回它
    def stop(self, unit_id: str) -> None: ...                   # 停沙箱，卷保留
    def destroy(self, unit_id: str) -> None: ...                # 连卷一起删
    def status(self, unit_id: str) -> SandboxStatus: ...
```

- `SandboxSpec`：执行单元 id、所有者、Agent、镜像版本、配额、启动令牌。没有路径、没有命令、没有挂载参数，这些由管理器按固定模板生成。
- 新的云侧运行时 `SandboxRuntime`：`ensure` 沙箱，等它的客户端连上，然后把这一轮交给现有的 `DeviceRuntime`（同一套
  `run.request` / `material.fetch` / `file.fetch` / 工具与审批回传）。`engine._run` 里云侧的 `_mount_*` 与 `_sync_home`
  分支换成端侧已有的材料分支。
- 后端：`process`（现状，开发用）、`docker`、`kubernetes`。测试用内存里的假后端加 `ScriptedRuntime`，不依赖 Docker。
- 插件服务迁到同一个接口：一个安装一个沙箱，默认不联网，替换 `matrix/sandbox.py` 的 bwrap（`plugin-install.md` 第 4 节）。
  没有沙箱后端时主持人上传的托管插件照旧拒绝。
- 实现后新增一条不变量（暂定第 26 条）：**云侧执行面与控制面分离**。云侧 Agent 的代码只在沙箱里运行；沙箱里没有网络的状态
  与任何长期凭证；出网只经出口网关。

## 8. 分阶段

每个阶段单独可上线，后一个依赖前一个。

**阶段 0：单机止血（不新增部署组件）。** 在做完阶段 1 之前先把最糟的一条堵上：

- Matrix 起 dsh 时外面再包一层 bwrap（复用 `matrix/sandbox.py`）：文件系统里只有系统目录、dsh 与 Python 环境（只读）、
  这个执行单元的工作目录、它自己的 dsh 状态目录；新的 PID 命名空间；`setrlimit` 上限。
- dsh 状态按执行单元分目录，共用的 `~/.dsh` 停用；模型供应商只用平台配置；`vault.key` 只从 `MATRIX_VAULT_KEY` 读、不落数据卷。
- 解决：读整个数据目录、读别人的会话、读 `vault.key`。**不解决**：共用内核与网络、没有 cgroup 配额、密钥仍在 dsh 环境变量里。
  所以它不是生产方案，只是缩小阶段 1 上线前的风险。

**阶段 1：执行面独立。** `SandboxProvider`、`matrix-sandboxd`、沙箱镜像、沙箱客户端（connector 复用）、`docker` 后端 + gVisor、
执行单元卷、材料清单、产物检查点、私有目录“材料进、改动出”、配额、`--isolation required`、旧工作目录迁移。
控制面容器去掉 `seccomp=unconfined`。这一阶段沙箱还能直接出网（过渡）。

**阶段 2：出口网关。** 沙箱网络默认全拒，客户端连接、模型调用、网页出网全部改经网关；模型密钥离开执行面；用量由网关记。
做完这一阶段，`security.md` 的“沙箱只管写、不管读”与信息流那条“可绕过 `open_note` 直接读磁盘”才能删掉，#59 关闭。

**阶段 3：收尾与 #68、#60。** 插件服务迁入；节点级只读内容存储；预热池；管理后台的沙箱页（数量、配额、排队、出网记录）；
连接器凭证注入（#60）。

**阶段 4：集群。** `kubernetes` 后端、多节点调度。注意控制面自己还是单进程 + `state.json`，登录也还是最简实现
（`security.md` 第一条）：这两件是“生产级”的另外两块，不属于执行面，要单独立项。

### 每个阶段的验收：能变红的检查

规则不靠记忆（AGENTS.md 工作方式第 8 条）。`matrix-dsh-check` 加一组在真实沙箱里跑的检查，让 Agent 的 `bash` 去试，试成了就是失败：

| 检查 | 让 Agent 去做 | 从哪个阶段起必须通过 |
| --- | --- | --- |
| `read-isolation` | 读数据目录里的标记文件、另一个执行单元的工作目录、别人的 dsh 会话、`vault.key` | 0 |
| `proc-isolation` | 列出沙箱之外的进程、读它们的环境变量 | 0 |
| `resource-limit` | 无限起进程、申请超额内存、写满磁盘；宿主与别的沙箱不受影响 | 1 |
| `net-isolation` | 连控制面的 `/api`、别的沙箱、内网地址、元数据地址、不经网关的公网 | 2 |
| `key-absent` | 在环境变量、文件、进程里找模型密钥；用沙箱令牌调一个没分配给这一轮的模型 | 2 |

引擎层的测试（假后端）：沙箱容量不够时任务进 `WAITING`；启动令牌只能用一次；一条沙箱连接只收得到自己执行单元的运行与材料；
`--isolation required` 下没有后端时拒绝云侧运行；私有目录的三方合并与来源标签在新通道下不变（不变量 15、22 的现有测试改跑两种通道）。

## 9. 迁移

- **工作目录**：`<data>/conversations/<id>/…`、`<data>/tasks/<id>/` 在该执行单元第一次进沙箱运行时导入它的卷（只导产物口径内的文件），
  同时生成第一份检查点；导完原目录留一个保留期再删。
- **dsh 会话**：从共用的 `~/.dsh` 里把这个执行单元的会话文件搬进它的 `/state`。搬不了（见下面第 3 项）就开新会话，
  网络照“续接失败”的现有流程补发上下文。
- **部署**：`compose.yml` 增加 `sandboxd` 与 `gateway` 两个服务和一张 `internal` 网络；宿主要装 gVisor。`deploy/README.md` 同步改。
- **本机开发不变**：`uv run matrix` 仍用 `process` 后端，界面标明“未隔离，仅限单人本机”。

## 10. 待验证（动手前先回答）

1. **dsh 的 bwrap 能否在 gVisor 里运行**（嵌套用户命名空间）。能：方案照上面走。不能：先看 dsh 有没有不依赖 bwrap 的沙箱方式；
   都没有就要在“换 Kata（完整内核）”与“沙箱里关掉内层沙箱、不变量 14 改由外层边界承担”之间选，后者要改不变量，需单独决定。
2. 阶段 0 的外层 bwrap 套内层 bwrap，在现在的部署容器里能否运行。
3. dsh 的会话文件能否按会话 id 单独搬到另一个 `HOME` 下续接。
4. dsh 的供应商配置把地址指向网关、密钥填占位值时，流式响应、重试、各 `compat` 开关是否正常。
5. gVisor 下 Node、Python、常见构建工具的兼容性与 I/O 开销（装依赖这类重文件操作的场景）。
6. 单机能同时跑多少个沙箱：按默认配额实测一轮运行的常驻内存，定出默认并发上限。

## 11. 明确不做的

- 不把 Docker socket、Kubernetes 凭证交给 Matrix 服务进程。
- 不做“同一个用户的沙箱可以互相读”的优化：不变量 22 在同一个人的不同场合之间也成立。
- 不在沙箱里放任何能长期使用的凭证，包括部署方自己的内网账号。需要的访问一律经网关按次注入。
- 不保留“没有沙箱就悄悄退回子进程”的路径。
