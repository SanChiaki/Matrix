# 云侧执行面：生产级方案（阶段 0、1a、1b、2a、2b 已实现，1a 起都在开关后面；其余是设计）

2026-11-10 定方向。2026-11-16 实现了阶段 0（单机止血）与云侧取消外溢审批，实现与设计的出入见第 8 节“阶段 0 的实现”；同日实现了阶段 1 的前半（1a：云侧 Agent 改走端侧客户端的协议、在沙箱里运行、数据进出做成材料清单与检查点，开关后面、默认关），见第 8 节“阶段 1a 的实现”。解决需求 #59（Matrix 与云端 Agent 隔离、云端 Agent 之间隔离）与 #68（材料不再每轮整份拷贝、资源上限、
模型密钥不进执行面），并为 #60（出口代理注入连接器凭证）提供前提。现状与逐条欠账见
[reference/device-runtimes.md](reference/device-runtimes.md#cloud-debt)，风险见 [reference/security.md](reference/security.md)。

## 0. 结论

1. **控制面不再执行任何 Agent 代码。** Matrix 服务（网络、存储、凭证）只做调度；云侧 Agent 一律跑在沙箱里。
2. **一个执行单元一个沙箱。** 执行单元 = 一个席位或一个委托（Agent × 场合）。沙箱的边界是独立内核级的（gVisor 或 microVM），
   不是路径、不是同一内核上的普通容器。
3. **云侧沙箱就是一台“网络托管的设备”。** 沙箱里跑的是现有端侧客户端（`matrix/connector/`）的同一套代码，说同一套协议。
   端侧已经是“执行面只拿网络给的副本、只经令牌回调”的形状，云侧对齐它，而不是另造一套。
4. **沙箱里没有任何长期凭证，出网只有一条路。** 模型调用、网页访问、以后的连接器请求都经出口网关；模型密钥留在控制面。
5. **沙箱可以随时丢。** 工作目录的产物与 dsh 会话每轮结束在控制面留检查点；沙箱或节点没了，只损失正在跑的那一轮和可重建的缓存。

选型：单机用 Docker + gVisor（`runsc`），集群用 Kubernetes + RuntimeClass（gVisor，或有 KVM 时用 Kata Containers）。
2026-11-11 实测确认：dsh 的 bwrap 在 gVisor 里能运行，而且不用放开任何安全选项（第 11 节），所以默认用 gVisor，不需要 Kata。
两者在同一个 `SandboxProvider` 接口后面，引擎不关心是哪一个。

## 1. 现状的问题

云侧现在是 Matrix 服务用子进程起 dsh，同一台机器、同一个系统用户，隔离只靠 dsh 的 bwrap“写只能写工作目录”：

| 被诱导的 Agent（有 `shell.exec`）现在能做什么 | 原因 |
| --- | --- |
| 读整个数据目录：别人的私有目录、对话、任务产物、项目档案、`state.json`（含密码哈希）、`vault.key` | 沙箱只管写不管读 |
| 读所有用户的 dsh 会话记录与 dsh 里配的模型凭据 | `~/.dsh` 是全体云侧 Agent 共用的一个目录 |
| 访问部署机能到的任何内网地址、云厂商元数据接口、本机的 Matrix 端口 | 共用宿主的网络，没有出网限制（`fetch.json` 只管 `web_fetch` 工具，管不到 `curl`） |
| 拖垮整台服务器 | 没有 CPU、内存、进程数、磁盘上限 |
| 可能读到模型密钥 | 密钥在 dsh 进程的环境变量里，只靠 dsh 按变量名过滤 |
| 利用内核漏洞拿到宿主 | Matrix 容器为了让 bwrap 能跑，关掉了 seccomp（`seccomp=unconfined`） |

所以不变量 7、8、13、16、22 目前只在提示词、网络工具与 API 层成立。下面的方案让它们在文件、进程、网络三层都由结构保证。

## 2. 威胁模型

- **对手**：云侧 Agent 执行的任何代码。Agent 读到的内容（群聊里别人的消息、网页、附件）都可能带注入，所以把“沙箱里的进程”
  整体当作不可信，包括 dsh 自己和沙箱里的客户端。
- **要保护的**：控制面的状态与凭证（`state.json`、vault、模型密钥、连接器凭证）；别的执行单元的工作目录、会话、私有目录；
  宿主机与部署方内网。
- **可信的**：控制面、沙箱管理器、出口网关、宿主内核与沙箱运行时。
- **不在本方案内**：模型经**允许的**通道把本场合的内容带出去（由不变量 21、22 与出口策略管，见 6.4）；侧信道；
  部署方管理员读数据（现在只靠政策）。

## 3. 总体结构

```
浏览器 / IM / 端侧客户端
        │
┌───────▼────────────────────────── 控制面（可信） ───────────────────────────┐
│ Matrix 服务：网络、状态、vault、调度                                         │
│   ├─ 沙箱管理器 matrix-sandboxd：唯一能创建 / 销毁沙箱的组件                 │
│   ├─ 出口网关 matrix-gateway：模型代理、网页出网、（以后）连接器凭证注入     │
│   └─ 内容存储：材料（按 sha）、产物检查点、私有目录的权威副本                │
└───────┬─────────────────────────────────────────────▲──────────────────────┘
        │ 创建沙箱（镜像、配额、一次性启动令牌）       │ 沙箱只连得到网关：
        ▼                                             │ 客户端长连接、模型、网页
┌──────────────── 执行面（不可信，每个执行单元一个沙箱） ────────────────────┐
│ 沙箱客户端（connector 代码）→ dsh → Agent 的命令（dsh 自己的 bwrap 照旧）  │
│ 工作目录：这个执行单元的卷（读写）     /state：dsh 会话（只属于这个单元）   │
│ 只读根文件系统、非 root、独立 PID / 网络命名空间、cgroup 配额               │
└────────────────────────────────────────────────────────────────────────────┘
```

三个新组件，各管一件事：

| 组件 | 职责 | 为什么单独一个 |
| --- | --- | --- |
| 沙箱管理器 `matrix-sandboxd` | 按规格创建、停止、销毁沙箱与卷；上报状态与资源用量 | 创建容器的权限等于宿主 root（Docker socket）。Matrix 服务不持有它，只能经一个窄接口提请求，参数只有标识与配额，镜像与安全选项写死 |
| 沙箱客户端（`matrix/connector/` 复用） | 在沙箱里接收一轮运行、补齐材料、起 dsh、把工具 / 审批 / 提问 / 事件回传 | 已有代码与协议，端侧每天在用 |
| 出口网关 `matrix-gateway` | 沙箱唯一的网络出口：鉴别是哪个沙箱、按这一轮的权限放行、注入密钥、记账留痕 | 密钥与出网策略必须在执行面之外 |

## 4. 沙箱

### 4.1 隔离单位

一个执行单元（席位或委托）一个沙箱，不是一个用户一个、也不是一轮一个：

- 比“一个用户一个”细：不变量 22 要求私有目录按来源场合挂载，同一个人的两个场合之间也不能互相读，一个用户一台机器做不到文件层的强制。
- 比“一轮一个”粗：dsh 会话续接、工作目录里装好的依赖要跨轮保留。沙箱在这一轮结束后空闲一段时间（默认 10 分钟）才停，
  卷留着；下一轮来了再起。

参照 Meta Muse“Agent 在隔离单元里，凭据与授权在外面的服务里，Agent 只拿替身令牌”（research: meta-muse#vm、
meta-muse#credentials-injection），粒度按 Matrix 的场合收细。业界的云端 Agent 也都是一个会话或任务一个可丢的沙箱、
凭证不进沙箱、出网经代理（research: cloud-agent-isolation#common-patterns）。和它们不同的一点：那里一个会话只属于一个人，
Matrix 的共享群聊里几个人的消息进同一个席位、同一个沙箱，沙箱不隔离同一席位里不同人的消息，这一层仍靠不变量 22。

### 4.2 运行时选型

| 部署形态 | 沙箱运行时 | 说明 |
| --- | --- | --- |
| 单机（现在的 compose） | Docker + gVisor（`--runtime=runsc`） | 不需要 KVM。私有化部署常见的云主机没有嵌套虚拟化，gVisor 仍能用 |
| 集群 | Kubernetes，Pod 指定 RuntimeClass：gVisor；节点有 KVM 时可选 Kata Containers | 接口相同，只换 RuntimeClass |
| 本机开发、测试 | `process`：现在的子进程方式 | 只给单人本机用；多用户部署拒绝启动云侧运行（4.5） |

不选的：

- **普通容器（runc）当安全边界**：和宿主共用内核，Agent 能执行任意代码时不够。只在部署方显式写 `insecure-runc` 时允许，后台长期标红。
- **直接基于 Firecracker 自建**：镜像、网络、快照、调度都要自己做。需要 VM 级边界时用 Kata，它把这些包在容器接口后面。
- **第三方托管沙箱服务**：Matrix 的部署多在企业内网，数据不能出去。`SandboxProvider` 接口留着位置，不作为默认。

### 4.3 沙箱里有什么

镜像由部署方构建、带版本：dsh（钉版本）、沙箱客户端、Python 与 Node、常用命令行工具；部署方可以在它之上加自己的工具
（#60 的 CLI 连接器就装在这里）。镜像里没有任何密钥。升级 dsh 时 `matrix-dsh-check` 在这个镜像里跑。

每个沙箱：

- 非 root 用户、去掉全部 capabilities、默认 seccomp、`no-new-privileges`、只读根文件系统，`/tmp` 是有上限的 tmpfs。
- 独立的 PID、挂载、IPC、网络命名空间。Agent 的命令看不到沙箱之外的任何进程。
- 挂载只有两处：工作目录（这个执行单元的卷）和 `/state`（dsh 的会话与配置，同一个卷的另一个子目录，`HOME` 指向它）。
- **工作目录挂在和现在完全相同的绝对路径上**（`/data/conversations/<对话>/<Agent>`、`/data/tasks/<任务>`），而且一个执行单元的路径永远不变。
  原因是实测（第 11 节第 3 项）：dsh 的会话绑死了记录时的工作目录绝对路径，路径一变就续接不了，符号链接也不行；
  同一个路径还让 `process` 后端与沙箱之间来回切换（灰度、回退）时会话照样能接上。沙箱里只有这一个执行单元的目录，别的路径不存在。
- 进程环境里 `TMPDIR` 必须指向沙箱里可写的 `/tmp`：dsh 每次起 bash 前要在 `$TMPDIR` 下建临时目录，建不了 bash 就起不来（实测）。
  不挂宿主目录，不挂 Docker socket，不挂数据目录。
- 配额（cgroup，默认值，部署方可调）：2 核、内存上限 2 GB、512 个进程、卷 10 GB、出网流量与速率上限。超了只影响这个沙箱。
  内存是上限不是预留：实测一轮普通运行（dsh + 网络工具的 MCP 服务）峰值约 250 MB，dsh 每轮一个进程、轮次之间不占内存（第 11 节第 6 项）。
  gVisor 下一轮（委托时同时两个 dsh）宿主看到的峰值约 440 MB，比 runc 多约 90 MB；装依赖、跑测试这类重活峰值 300–420 MB；
  空闲沙箱约 10–17 MB 一个（第 11 节）。全局并发默认按 `(宿主内存 − 2 GB) / 512 MB` 估（16 GB 的机器约 28 个）。
  默认值由沙箱管理器的配置定（控制面不指定配额）。管理器启动时按宿主内存核对：单个沙箱的 `memory_mb` 与 `max_memory_mb` 都不能超过“宿主内存 − `host_reserve_mb`（默认 1024 MB）”，超了拒绝启动并写明怎么改；`max_memory_mb` 不写时自动取这个值（最多 8 GB）。只核对单个沙箱，不核对“配额 × 并发”：配额是上限，按它乘并发会把并发压得过低；几个沙箱同时用满配额仍可能压垮宿主，靠并发上限与宿主余量兜底（2026-11-17：一台 1.8 GB 的测试机在默认 2 GB 配额下被 `resource-limit` 探针压垮，才加的这项核对）。
- dsh 自己的 bwrap 沙箱**照旧开着**：`build_patch_yaml` 的权限覆盖层、“写只能写工作目录”都不变；外溢审批在云侧取消（7.1）。
  外层沙箱负责读隔离与爆炸半径，内层负责权限词表，两层各管各的。

控制面的 Matrix 容器不再需要 `seccomp=unconfined` 与 `systempaths=unconfined`，一并去掉。沙箱容器也不需要：
实测 gVisor 里在默认 seccomp、`no-new-privileges`、去掉全部 capabilities 下，dsh 的 bwrap 照样能建命名空间、挂 `/proc`
（gVisor 自己实现这些系统调用，不经宿主内核）。普通容器（runc）里则必须放开这两项，否则 dsh 退到更弱的沙箱（第 11 节补充）。

### 4.4 生命周期

```
没有 ──创建──▶ 运行中 ──空闲超时──▶ 已停（卷保留）──执行单元结束后保留期满──▶ 已销毁（卷删除）
                  ▲                    │
                  └────有新一轮────────┘
```

- **创建**：管理器起沙箱，注入一次性启动令牌；沙箱客户端用它连回控制面，换到一份**执行单元凭证**（绑定执行单元、Agent、所有者），
  启动令牌用过即废。凭这份凭证建立的连接上只接受派给这个执行单元的运行。
- **重连与重签**：执行单元凭证绑定的是执行单元，不是某条连接或某个控制面进程（参照托管 Agent 的会话令牌，
  research: cloud-agent-isolation#brain-hands-session）。它只在沙箱客户端的内存里：网络抖动、网关或控制面重启后，客户端凭它重连。
  沙箱客户端是沙箱的 1 号进程，它崩溃就是沙箱退出，管理器按“沙箱没了”处理：重建时发新的启动令牌，旧凭证随之吊销。
  凭证被沙箱里别的进程拿到，也只能做这个执行单元本来能做的事。
- **台账以控制面为准**：控制面持久记录每个执行单元“应该是什么状态”（运行中 / 已停 / 已销毁）、卷和当前的代数；管理器不存意图，
  只给容器与卷打上执行单元 id 与代数的标签，并上报实际状态。控制面启动时、之后定期对账：没有记录或代数过期的容器结束掉
  （留一个宽限期，免得误杀刚建的）；记录是运行中而容器不在的，那一轮判失败可续接；没有执行单元的卷过保留期删除。
  做法同 Kubernetes 的声明式对象加控制器（research: cloud-agent-isolation#k8s-agent-sandbox）。
- **容量不够时是等待，不是失败**：沿用端侧“不可达是等待”的语义（任务进 `WAITING`、不消耗重试），按用户并发上限与全局上限排队。
- **冷启动**：gVisor 容器起动在秒级；需要时管理器保持少量预热好的空沙箱（未绑定任何单元，绑定时才挂卷、发令牌）。
- **销毁**：委托验收或作废、对话归档或删除、Agent 删除后，过保留期删卷。删之前产物已有检查点（5.2）。
- **重启语义（不变量 12）第一期不变**：控制面重启时，云侧运行中的轮次判失败可续接；对账时结束没人认领的运行。
  “控制面重启不打断运行”还缺什么，见第 12 节。

### 4.5 失败时关闭

- 启动参数 `--isolation required`（多用户部署最终的默认；过渡期先是 `preferred`，见 9.1）：没有可用的沙箱后端、或后端是 `process` / `insecure-runc` 时，
  云侧运行一律拒绝并在后台写明原因，不退回子进程方式。端侧运行不受影响。
- `RuntimeCapabilities` 加一项 `isolation`（`none` / `sandbox` / `vm`），Agent 页与管理后台显示当前云侧的隔离等级。
  阶段 0 已加（外层 bwrap 记 `sandbox`，另有一句 `isolation_note` 说明用的什么、为什么没有）；开关是环境变量 `MATRIX_CLOUD_ISOLATION`，
  阶段 0 默认 `preferred`。

## 5. 数据怎么进出沙箱

原则：沙箱拿到的都是控制面按这一轮的可见性算好、主动给的副本；沙箱交回来的都经控制面校验后才进入网络的状态。

### 5.1 进：材料

复用端侧的“清单 + 缓存”（[reference/device-runtimes.md](reference/device-runtimes.md)“材料”）：

- 项目档案文件、这个席位看得到的附件、订阅的发布物、技能、插件挂载：`run.request` 只带清单（路径、sha、大小），
  沙箱客户端按 sha 补齐缺的，控制面只回这一轮清单里的 sha。
- 缓存在这个执行单元自己的卷里。第二轮起没变的文件一个字节都不传，#68 的“每轮整份拷贝”随之消失。
- 以后的优化（不在第一期）：节点上一份按 sha 的只读存储，由管理器只读挂进沙箱，免去沙箱内的拷贝。缓存由管理器管、沙箱只读，
  所以沙箱拿不到清单之外的内容。

### 5.2 出：产物检查点

每轮结束，沙箱客户端按 `workdir.outputs` 的口径报产物清单（路径、sha、大小），控制面取回有变化的文件，存进内容存储，
记为这个执行单元的最新检查点。每个单元的检查点有总量上限（默认 1 GB，超出的文件只记清单、需要时再向沙箱取）。

这样委托交付（`deliveries/`）、人浏览与下载工作目录、`publish_file` / `send_file` 都读检查点，不需要沙箱还活着，
也不需要控制面去读执行面的磁盘。沙箱或节点丢了，从检查点恢复产物，依赖目录（`node_modules`、`.venv` 等，本来就不算产物）重装。

**检查点里还有这个执行单元的 dsh 会话**（2026-11-16 定）。会话是 Agent 在这个场合的对话记忆，只放在卷上的话，节点一坏就丢，
执行单元也被钉死在有这个卷的那台机器上。每轮结束，沙箱客户端把当前会话的两处文件（10.2 第 3 步）打成一个包随检查点上传；
控制面当它是不透明的块，只存最新的两份，不解析、不展示、不算产物。恢复时连同产物一起放回新卷，工作目录路径不变（4.3），就能续接
（实测：打成包后在全新的容器里、以及换了操作系统与 Node 版本的另一个环境里解包，都能续接，第 11 节“检查点恢复”）。于是**卷只是缓存，检查点才是准**：执行单元可以在任何节点上重建。
业界的做法是会话存成沙箱之外的事件日志或快照（research: cloud-agent-isolation#brain-hands-session、cloud-agent-isolation#snapshots）；
Matrix 用的是别人的 harness，读不懂它的会话，所以整份当块存。

只在轮次结束时做检查点，长轮次中途沙箱没了会丢掉这一轮已经写出的产物。阶段 3 加轮次中的增量检查点（每隔几分钟报一次产物清单，
只传有变化的）；会话文件中途可能不完整，仍只在轮次结束时存。

### 5.3 私有目录

权威副本留在控制面（`<data>/agents/<id>/`），语义不变（不变量 8、15、22）：

- 进：这一轮按来源场合算出的可挂部分作为材料下发到 `agent-home/`，没挂的文件沙箱里不存在。
- 出：轮次结束，沙箱客户端上报 `agent-home/` 里改过、删过的文件，控制面用现有的三方合并（`homedir.sync_back`）写回并更新来源标签。
  有别人的场合里技能改动照旧不写回。

端侧协议里私有目录是“留在设备上、客户端自己合并”；云侧多一种方式“由网络持有、材料进、改动出”，是协议上唯一要新增的东西。

### 5.4 dsh 会话

每个执行单元的 `/state` 里只有它自己的会话，每轮结束随检查点存到控制面（5.2）。共用的 `~/.dsh`（`dsh-home` 卷）退役：
模型供应商一律用平台配置（`models.json` + vault），不再读 dsh 自己存的凭据。

## 6. 出口网关

### 6.1 网络形状

每个沙箱的网络只有一条路由：到网关。沙箱之间、沙箱到宿主、到内网、到云厂商元数据地址、到控制面的 `/api` 都不通。

- Docker：沙箱接在 `internal` 网络上（没有对外路由），关掉容器间互通，只有网关同时接这张网与外网。
- Kubernetes：命名空间默认拒绝全部出入流量的 NetworkPolicy，只放行到网关。
- DNS 也只经网关解析，避免用 DNS 查询带数据出去。

网关用两样东西认定请求来自哪个沙箱：来源地址（管理器登记的）与沙箱令牌（创建时下发，只在网关有用）。
再由控制面查到执行单元当前这一轮的权限。不信任请求里自报的任何身份（不变量 10）。

### 6.2 三类流量

| 流量 | 怎么走 | 网关做什么 |
| --- | --- | --- |
| 沙箱客户端 ↔ 控制面 | 出站长连接（和端侧一样的 WebSocket 协议），经网关转到控制面的专用端点 | 只转发到这一个端点。网络工具、审批、提问、连接器代调用都在这条连接里，沙箱不需要直接访问 `/internal/*` |
| 模型调用 | dsh 的供应商地址指向网关（`/llm/<供应商>`），密钥位置填沙箱令牌 | 核对供应商与模型是控制面给这一轮定的那个；换上 vault 里的真密钥转发；流式透传；按响应记用量 |
| 网页与包下载 | 沙箱里设 `HTTPS_PROXY` 指向网关（没有别的路，所以不理它的进程只是连不上） | 按 6.4 的分级放行：包镜像源（有 `shell.exec`）、公网只读（有 `web.research`）、公网写默认不允许；内网目标只认 `fetch.json` 的 `allow`；每个请求记一行（主机、方法、状态、字节数、执行单元），不记内容 |

模型密钥从此不进执行面，“密钥经 dsh 进程环境变量”这条欠账与 `key-hidden` 检查的前提一起消失
（检查保留，改为确认沙箱里确实没有密钥）。用量由网关按实际响应记，不再只依赖 dsh 自报：实测 dsh 每轮另有一个
生成标题的小请求，它的用量不在 dsh 报的数里，现在的用量台账少记了这部分；网关在每个请求上都能读到 `usage`
（dsh 请求时带 `stream_options.include_usage`）。

### 6.3 连接器凭证（#60）

`connectors-and-skills.md` 第 11.3 节的出口代理就是这个网关的第四类流量：按“执行单元 + 目标域名”把占位值换成 vault 里的凭证，
写请求逐次确认。它要求网关终止 TLS、沙箱信任网络的 CA，放在本方案第三阶段，前提（只能经网关出网）由第二阶段提供。

注入之前网关要**按操作核对**，不只按域名放行：这一次请求的方法、路径（git 的话是仓库与分支）在不在这个连接允许的范围里，
在才换上真凭证。参照 Claude Code 网页版的 git 代理（research: cloud-agent-isolation#scoped-credentials）。

### 6.4 允许的通道上的外泄：出网分级（2026-11-16 定）

隔离做完以后，剩下的外泄途径是允许的出网本身。网关不自己判断“这个会话干不干净”，只认引擎算出的这一轮的有效权限：
不变量 22 已经规定，会话读了越界来源就去掉联网、执行命令、连接器三种能力；不变量 21 规定助理读到共享项目内容的那一轮不能用连接器。
权限收窄了，网关那里自然就没有对应的出口，判断只有一处。

在此之上，出网分四级：

| 级别 | 能到哪 | 条件 |
| --- | --- | --- |
| 基本 | 控制面（经网关）、分配给这一轮的模型 | 所有云侧运行 |
| 装依赖 | 部署方配的包镜像源（PyPI、npm 等），只读请求 | 有 `shell.exec` |
| 公网读 | 任意公网主机，只允许 GET / HEAD、不带请求体、URL 不超过 2 KB；内网目标只认 `fetch.json` 的 `allow` | 有 `web.research` |
| 公网写 | 带请求体的请求（POST / PUT 等） | 默认不允许。只到部署方白名单里的主机；要调外部系统的接口走连接器（6.3） |

理由：调研要的是读；往任意主机发带内容的请求是成批外泄的主要通道，而正当用途（调接口）本来就该走连接器，那里有凭证、按操作核对与逐次确认。

剩下的是把内容塞进 GET 的 URL 里带出去。挡不干净，做两件事压低它：

- **出网预算**：每一轮发往非白名单主机的 URL 与请求头，累计字节数有上限（默认 64 KB，够正常浏览几百个页面，不够搬走一份文档）。
  超了这一轮的公网读即停，并通知所有者。
- **留痕加细**：场合里有别人、或会话记过别处来源的执行单元，公网请求记完整 URL（平时只记主机）。事后查得到带出去了什么。

接受的风险：有 `web.research` 的 Agent 仍能经 URL 带出少量内容。范围：预算以内；复查时机：出现第一起经此途径的外泄，或要服务对外泄零容忍的客户时
（那时把有别人的场合的公网读改成只到白名单）。

**分阶段出网不单独做。** Codex 云端把一轮分成能联网、有密钥的准备阶段和默认断网的 Agent 阶段（research: cloud-agent-isolation#two-phase）。
Matrix 的轮次是对话式的，没有一个固定的“准备步骤”，依赖是 Agent 干活过程中按需装的；硬加一个阶段要新造“谁来写准备脚本、写在哪”这套概念。
它要达到的效果（装依赖不等于放开公网、密钥不在 Agent 手里）由上面的分级给到：装依赖只到镜像源且只读，密钥本来就不进沙箱。

## 7. 引擎里怎么接

改动集中在运行时这一层，席位、委托、审批、提问、信息流的语义都不动：

```python
class SandboxProvider(Protocol):
    def ensure(self, spec: SandboxSpec) -> SandboxHandle: ...   # 幂等：按执行单元 id，已在运行就返回它
    def stop(self, unit_id: str) -> None: ...                   # 停沙箱，卷保留
    def destroy(self, unit_id: str) -> None: ...                # 连卷一起删
    def status(self, unit_id: str) -> SandboxStatus: ...
```

- `SandboxSpec`：执行单元 id、所有者、Agent、镜像版本、配额、启动令牌。没有路径、没有命令、没有挂载参数，这些由管理器按固定模板生成。
- 新的云侧运行时 `SandboxRuntime`：`ensure` 沙箱，等它的客户端连上，然后把这一轮交给现有的 `DeviceRuntime`（同一套
  `run.request` / `material.fetch` / `file.fetch` / 工具与审批回传）。`engine._run` 里云侧的 `_mount_*` 与 `_sync_home`
  分支换成端侧已有的材料分支。
- 后端：`process`（现状，开发用）、`docker`、`kubernetes`。测试用内存里的假后端加 `ScriptedRuntime`，不依赖 Docker。
- 插件服务迁到同一个接口：一个安装一个沙箱，默认不联网，替换 `matrix/sandbox.py` 的 bwrap（`plugin-install.md` 第 4 节）。
  没有沙箱后端时主持人上传的托管插件照旧拒绝。
- 实现后新增一条不变量（暂定第 26 条）：**云侧执行面与控制面分离**。云侧 Agent 的代码只在沙箱里运行；沙箱里没有网络的状态
  与任何长期凭证；出网只经出口网关。

### 7.1 外溢审批：云侧取消、端侧保留（2026-11-11 定）

不变量 14 改写为：

> **工作区外溢**：云侧 Agent 只能写自己的工作目录，工作目录以外一律不可写，也不审批，由沙箱的边界保证。端侧 Agent 写工作目录以外时
> 由 **Agent 的所有者**逐次批准（只对那一次调用生效，不按时间作废，只在设备断连时结束）；harness 没有审批上行的，工作目录以外的写
> 按 harness 自己的沙箱处理，做不到强制的权限记 `advisory`（不变量 1）。

为什么云侧取消：

- 云侧的“工作目录以外”是服务器的磁盘。以前批准的就是“写服务器上的任意位置”，这正是本方案要堵的口子。
- 沙箱里工作目录以外要么不存在、要么只读，实测审批或者不触发、或者批了也写不进（9.2），留着只会让人批一个不生效的申请。
- 审批卡上只有工具名和模型自己写的理由，看不到实际命令，被诱导的 Agent 可以写一个无害的理由；云侧没有非批不可的场景，不值得承担这个风险。
  Agent 的产物本来就该在工作目录里，交付、发文件都从那里取。

为什么端侧保留：那是所有者自己的电脑，改工作目录以外的本机文件可能正是所有者想要的，逐次批准仍有意义。现状：

| 端侧 harness | 工作目录以外的写 |
| --- | --- |
| dsh | 沙箱拒绝 → 模型带理由申请升权 → `approval.mjs` → 本机小桥 → `approval.request` → 网络通知所有者 → 批准后只放行这一次 |
| Codex | 沙箱拒绝，这一步失败，不上行 |
| Claude Code | 没有沙箱，`file.write` 只靠工具白名单，记 `advisory`，不进有效权限 |

要改的（从阶段 0 起生效，因为阶段 0 的外层已经让云侧审批失效；2026-11-16 已做，只有“端侧驱动的审批另做检查”还没有：
`matrix-dsh-check` 跑的是云侧，端侧 dsh 驱动的审批靠 `tests/test_device.py`、`tests/test_users.py` 的端侧一组与连接器实测）：

- `build_patch_yaml`：云侧运行不再插入审批应答者（`matrix-approval`）。dsh 在没有应答者时以 `unavailable` 拒绝升权，Agent 得到明确的“不允许”，
  不会等人。端侧 dsh 驱动照旧插入。
- 云侧运行时的能力报告 `approval` 改为 `sandbox-only`；提示词里说明云侧只能写工作目录、产物放在工作目录里。
- `/internal/approval` 对云侧执行上下文一律回 `unavailable`（防御：覆盖层万一带上了应答者也批不了）。端侧的 `approval.request` 不变。
- `docs/reference/invariants.md` 第 14 条按上面改写，不变量 14 的测试分成云侧（申请被拒、不产生审批记录）与端侧（照旧转给所有者）两组。
- `matrix-dsh-check` 的 `approval`：云侧检查改为“工作目录以外写不进、也没有产生审批”；端侧驱动的审批另做检查。
- 已有的云侧待批审批在升级时作废（和重启时一样，不变量 12）。

端侧保留的这条路还有一个已知弱点：所有者看到的是工具名和模型写的理由，不是实际要执行的命令与路径
（research: always-on-personal-agents#matrix-takeaways）。改进方向是查 dsh 的 `approval/request` 是否带调用参数，带就一并转给所有者，
界面上把“实际调用”和“Agent 的理由”分开。不在本方案内，单独立项。

## 8. 分阶段

每个阶段单独可上线，后一个依赖前一个。

**阶段 0：单机止血（不新增部署组件）。** 在做完阶段 1 之前先把最糟的一条堵上：

- Matrix 起 dsh 时外面再包一层 bwrap（复用 `matrix/sandbox.py`）：文件系统里只有系统目录、dsh 与 Python 环境（只读）、
  这个执行单元的工作目录、它自己的 dsh 状态目录；新的 PID 命名空间；`setrlimit` 上限。
- dsh 状态按执行单元分目录，共用的 `~/.dsh` 停用；模型供应商只用平台配置。~~`vault.key` 只从 `MATRIX_VAULT_KEY` 读、不落数据卷~~
  **不做**（2026-11-16）：外层沙箱里本来就读不到 `vault.key`，而改成只认环境变量会让现有部署（密钥在数据卷里的）丢掉保管密钥、
  解不开已存的凭证。留到控制面与执行面分开之后（阶段 1 起控制面不再执行 Agent 代码）再看。
- 解决：读整个数据目录、读别人的会话、读 `vault.key`。**不解决**：共用内核与网络、没有 cgroup 配额、密钥仍在 dsh 环境变量里。
  所以它不是生产方案，只是缩小阶段 1 上线前的风险。
- 已在部署镜像里实测可行（第 11 节第 2 项）。实现时要注意：`TMPDIR` 指向外层的 `/tmp`；`--patch` 指向的覆盖层文件要读得到；
  外溢审批（不变量 14）在外层里基本失效，所以从阶段 0 起云侧就不再审批（7.1）。

**阶段 0 的实现（2026-11-16，已上线）。** 代码在 `matrix/runtime.py`（`DshRuntime` 的 `hosted`、`outer_argv`、`outer_ro`、
`adopt_dsh_session`）、`matrix/sandbox.py`（`wrap(nested=True)`、`available("nested")`、`dsh_limits`）与 `engine._adopt_dsh_state`；
检查在 `matrix-dsh-check`（`isolation`、`read-isolation`、`proc-isolation`、改过的 `approval`）。和上面的设计不一样的地方：

| 设计 | 实现 | 原因 |
| --- | --- | --- |
| `setrlimit` 上限 | 只设不生成 core、单个文件最大 4 GB | 地址空间上限会让 Node/V8 起不来（它预留很大的虚拟地址空间）；CPU 秒数会停掉长轮次；打开文件数 Node 与 MCP 服务要得多。进程数、内存、磁盘总量要 cgroup，阶段 1 做 |
| `vault.key` 只从环境变量读 | 不做 | 见上一条 |
| 外层去掉全部特权 | 非 root 照旧；**以 root 运行时**外层显式建一个用户命名空间（uid 0 映射到自己），不去掉特权 | root 下 bwrap 不建用户命名空间，去掉特权后内层 bwrap 建不了命名空间（实测）；特权只在沙箱自己的用户命名空间里有效，碰不到设备与宿主内核接口。部署镜像以非 root 运行，不走这条 |
| 外层可用就套 | 先真跑一次“外层里再起一层 bwrap”探测（`available("nested")`），能跑才套 | 外层能起、内层起不来时，dsh 会退到更弱的内层沙箱（第 11 节补充），比不套更糟 |
| 只挂系统目录、dsh 与 Python | 另外只读挂环境变量（`NODE_EXTRA_CA_CERTS`、`SSL_CERT_FILE` 等）指向的 CA 证书；dsh 与 node 的安装位置按真实路径解析（镜像里在 `/usr` 下，本机常在 `/opt/dsh`、`/opt/node22`）；包含工作目录或状态目录的只读目录一律不挂 | 经代理、内网 CA 出网时 dsh 要读证书；位置因部署而异不能写死；防止把整个数据目录带进去 |
| 状态目录放在执行单元的卷里 | `<data>/dsh-state/{seats/<对话>/<Agent>,tasks/<任务>}/`，在数据目录下、不在任何工作目录里 | 阶段 0 还没有卷；到阶段 1 搬进卷的 `/state` |
| 旧会话“搬” | 拷贝（原处不删），第一次在新方式下运行（状态目录还不存在）时做；搬不了清会话 id | 回退到共用 `~/.dsh` 时还能续接（10.4）；`purge-legacy` 之前不删旧数据 |
| 端侧、云侧同一个 `DshRuntime` | 端侧驱动用 `DshRuntime(hosted=False)`：不套外层、不换 HOME、照旧插审批应答者 | 端侧读的是所有者自己的电脑，审批保留（7.1） |
| `read-isolation` 要真模型 | 用假模型服务驱动 Agent 的 bash（同 `key-hidden`），不加 `--live` 也跑；数据目录放在主目录下而不在 `/tmp` | 结果确定、不花 token；dsh 内层把 `/tmp` 换成空 tmpfs，标记放在 `/tmp` 下没有外层也读不到，检查会失真 |

验证：本机（root，bwrap 0.9）与部署镜像（以 `matrix` 用户、compose 的安全选项）里 `matrix-dsh-check --live` 全部通过，
含 `read-isolation`、`proc-isolation` 与新的 `approval`；`MATRIX_CLOUD_ISOLATION=required` 在不放开 seccomp 的容器里按预期拒绝运行。
旧会话迁移用真模型验证过：旧代码（共用 HOME）让 Agent 记住一个编号，换成新代码后同一个会话续接、记得编号。

**阶段 1a 的实现（2026-11-16，开关后面，默认关）。** 阶段 1 拆成两半：1a 先用本机子进程当“沙箱”把完整链路跑通
（不碰 Docker / gVisor），1b 再换成 `docker` 后端 + gVisor、配额与控制面容器收紧。开关 `MATRIX_CLOUD_SANDBOX=off`（默认）| `local`
（或 `matrix --sandbox local`），关着时引擎的路径与原来完全一样。打开后云侧 Agent 的一轮：

1. 引擎（`_kick`）先给这个执行单元占一个沙箱的位置：全局与每用户并发上限，满了先停最久没用的空闲沙箱，没有空闲的就等
   （委托进 `WAITING`、不失败、不消耗重试；席位排队并告诉所有者；有位置时重新调度）。
2. `SandboxRuntime` 向 `SandboxProvider` 要沙箱（`ensure`，按执行单元 id 与代数幂等）；沙箱不在了就新建一代：发新的一次性启动令牌，
   旧凭证作废。沙箱里的客户端从 stdin 读令牌，连新端点 `/api/sandbox/connect`，换到执行单元凭证（`SandboxHub`）。
3. 这一轮经 `DeviceRuntime` 的协议派给它：`run.request` 带材料清单，客户端按 sha 取缺的；工具、提问、事件照端侧的方式回传，
   云端连接器多一条 `connector.call`。沙箱连接只接受派给自己执行单元的运行（`DeviceRuntime.unit`），控制面对它发来的请求只按这个单元认定身份。
4. 轮次结束客户端经 `blob.put` 交内容、在 `run.result` 里报产物清单、私有目录的改动、当前会话包；控制面校验后存检查点、三方合并私有目录。

**阶段 1b 的实现（2026-11-16，开关后面，默认关）。** `MATRIX_CLOUD_SANDBOX=docker`：每个执行单元一个容器，由沙箱管理器
`matrix-sandboxd`（`matrix/sandboxd.py`）创建与销毁。部署用 `deploy/compose.sandbox.yml` 叠在 `compose.yml` 上（默认部署不变），
镜像在 `deploy/Dockerfile.sandbox`（`sandbox` 与 `sandboxd` 两个目标）。

- **管理器**是唯一挂 docker.sock 的进程。Matrix 服务经共享卷里的 Unix socket 调它（本地 HTTP：ensure / stop / destroy / status / list / report），
  请求只有执行单元 id、所有者、Agent、代数、配额、启动令牌、逻辑工作目录；逻辑工作目录必须落在配置允许的前缀下（compose 里是 `/data/conversations/`、
  `/data/tasks/`）。镜像、运行时、安全选项、网络、挂载模板、命令写死在管理器的配置（`sandboxd.json`）里，请求带别的字段一律拒绝（`validate_ensure`）。
  管理器不存意图，只给容器与卷打部署名、执行单元 id、代数、起动时间的标签；对账照旧由控制面做：控制面不认识的运行中沙箱过宽限期停掉、卷保留，
  不认识的卷过保留期（`MATRIX_SANDBOX_RETAIN`，默认 7 天）才删，从第一次发现算起（记进 `state.json` 的 `sandbox_orphans`，重启不重新计时），
  删之前打一行日志（`state.json` 从备份恢复后，备份之后新建的执行单元没有记录，它们的卷不能立刻清掉）。
  管理器的 socket 是 0660、属组给 Matrix 服务的用户组（gid 1000），管理器进程用 `group_add` 加进这个组。
  部署名（`namespace`）是本机实测补上的：同一个 Docker 上跑着两套控制面时，一套的对账把另一套正在用的沙箱当成“没有记录”删掉，
  那一轮报 `TRANSPORT device disconnected`；现在管理器只列、只管自己名下的。
- **容器**（`run_argv`，纯函数）：uid 1000、`--cap-drop ALL`、`no-new-privileges`、只读根、`/tmp` 是 512 MB 的 tmpfs、独立 PID / 挂载 / IPC 命名空间、
  `--cpus 2`、`--memory 2g`（不给 swap）、`--pids-limit 512`；挂载只有这个单元的两个卷：工作目录挂在原来的绝对路径上，dsh 状态挂在 `/state`。
  不挂宿主目录、docker.sock、数据目录。运行时默认 `runsc`；部署方写 `insecure-runc` 才用 runc，这时只多放开 seccomp 与 `/proc` 遮挡两项
  （runc 里内层 bwrap 要；gVisor 不要），能力报告与管理后台写“未达到生产隔离”。配置的运行时不在时拒绝云侧运行（`ISOLATION`），不退回别的。
- **网络**：沙箱接在专用的 `matrix-sandbox` 网络上（`enable_icc=false`，容器之间不通），Matrix 只在这张网络的网关上开放 8765，沙箱客户端经它连回
  `/api/sandbox/connect`。不用 host 网络。阶段 2 把这张网络改成只通出口网关。
- **Matrix 容器**不再跑 dsh，叠加文件把它的安全选项改成只有 `no-new-privileges`（去掉 `seccomp=unconfined` 与 `systempaths=unconfined`）。

验证（本机，Docker 29、cgroup v1、overlayfs，**没有 gVisor**——这台机器的策略不允许装 runsc）：`insecure-runc` 档下
`matrix-dsh-check --live --sandbox docker` 全部通过，含新加的 `resource-limit`（Agent 申请 3 GB 内存被结束、起 900 个进程被挡在 512 以内、之后别的
执行单元照常）与 `isolation` 里的内层 bwrap 核对（这两项 2026-11-17 起由假模型驱动：真模型常把探针当攻击拒绝执行，结果时好时坏）；工具包 `t8` 在本机按同样的方式跑过（早先几遍偶有一项报 `TRANSPORT device disconnected`，查明是同一个 Docker 上另一套控制面的对账删了沙箱，加了部署名后不再出现）；
compose 形态（`matrix` + `sandboxd` + 沙箱网络）起来后经 HTTP API 跑通两轮真实对话（续接记得编号、产物进检查点），Matrix 容器里没有 docker.sock、
经 socket 发带镜像 / 挂载 / 特权的请求都被拒。**`runsc` 档没在本机验证**，要在装了 gVisor 的机器上跑工具包的 `t8`。

和设计不一样的地方：

| 设计 | 1b 的实现 | 原因 |
| --- | --- | --- |
| 沙箱客户端是容器的 1 号进程 | `--init`：1 号进程是 Docker 的 tini，客户端是它唯一的子进程 | 收孤儿进程；客户端退出 tini 跟着退出，“客户端退出即沙箱退出”不变 |
| 卷 10 GB 上限 | **没有**：Docker 的 local 卷做不到大小上限（overlayfs 上的 `--storage-opt size` 只管容器根，而且要 xfs + pquota），能力报告写 `volume_quota: false` | 以后可选：支持大小上限的卷驱动（XFS + pquota）、或者定期统计、超了停沙箱 |
| 卷 | 每个执行单元两个卷（工作目录、`/state`），新的工作目录卷先用一个只有 CHOWN 特权、不联网的一次性容器交给沙箱用户，挂载加 `volume-nocopy` | 卷挂在镜像里没有的路径上时归 root；不加 nocopy 时 Docker 会照搬临时建的挂载点的属主（root） |

| 控制面容器去掉 `seccomp=unconfined` | 只在叠加 `compose.sandbox.yml` 时去掉；默认的 `compose.yml` 不变（还在跑 dsh） | 不破坏现有部署 |

**阶段 1：执行面独立。** `SandboxProvider`、`matrix-sandboxd`、沙箱镜像、沙箱客户端（connector 复用）、`docker` 后端 + gVisor、
执行单元卷、材料清单、产物检查点、私有目录“材料进、改动出”、配额、`--isolation`（先默认 `preferred`，见 9.1）、旧数据迁移（第 10 节）。
控制面容器去掉 `seccomp=unconfined`。这一阶段沙箱还能直接出网（过渡）。

**阶段 2a 的实现（2026-11-17，开关后面）。** 出口网关 `matrix/gateway.py`：核心进程里的一个模块、单独的监听（`MATRIX_GATEWAY_LISTEN`），
沙箱方式的 local 与 docker 后端都起它。沙箱到控制面与外面的全部流量都只到它，它只认四种请求：`/api/sandbox/connect`（原样转给核心这一个端点）、
`/llm/<供应商>/…`（模型代理）、`CONNECT`（网页与包下载的隧道，不解 TLS）、绝对地址的明文 HTTP。

- **身份**：每一轮核心签一张网关令牌（执行单元、有效权限、供应商、模型；真密钥只在核心进程里），轮次结束作废；docker 后端另核对来源地址
  是管理器报的那个沙箱的地址。沙箱里 dsh 的“密钥”位置填令牌，Agent 的命令的 `HTTP(S)_PROXY` 也带它（`http://sbx:<令牌>@<网关>`）。
- **模型代理**：核对路径里的供应商与请求里的模型是这一轮定的，不是就 403；换上真密钥转发，流式透传（分块回给 dsh），从流里读用量。
  用量台账用网关记的（`usage_source: gateway`），和 dsh 自报的口径对齐（输入不含缓存命中）。实测 dsh 0.2.1-rc.5 headless 在平台供应商下
  每轮没有另发“生成标题”的请求：网关记到的请求数等于 dsh 的步数，用量与 dsh 自报一致（设计里说的“少记的标题请求”这一版没看到）。
- **只支持平台供应商**：沙箱方式下用 dsh 自带供应商（靠服务进程环境里的 `DEEPSEEK_API_KEY` 之类）的 Agent 这一轮报错，提示在后台配成平台供应商；
  不再把服务进程环境里的密钥放进沙箱。按主机注入凭证（2b）做完后再评估。
- **出网**（`gateway.decide`，纯函数）：公网要 `web.research`、只到 80 / 443、解析出来的地址都得是公网（私有、回环、链路本地、元数据地址都拒），
  连接固定在校验过的地址上；包镜像源（`MATRIX_GATEWAY_MIRRORS`）要 `shell.exec`；内网目标只认 `fetch.json` 的 `allow`。网关自己要经上游代理出网时公网交给上游代理。
  每个请求在 `<data>/gateway/egress.jsonl` 记一行（执行单元、主机、端口、字节数、结果），不记内容。
- **网络形状（docker 后端）**：管理器配了 `gateway_container`（网关所在的容器）时，每个执行单元一张自己的 internal 网络（`--internal`：没有对外路由；
  `inhibit_ipv4`：网桥上没有地址，宿主不在这张网络上），只接这个沙箱和网关所在的容器，从 `subnet_pool` 切 /28；沙箱连回的是网关在这张网络上的地址。
  核心只监听内部网络的地址（compose 里 `MATRIX_HOST=matrix`），所以网关所在容器接上执行单元网络后，沙箱也连不到核心。Docker 的内置 DNS 在 internal 网络上
  不解析外部名字（实测），DNS 带不出数据。没有特权容器，也不改宿主防火墙。
- **local 后端**：模型代理照样生效（密钥不进沙箱），但共用宿主网络，做不到强制断网：能力报告 `net_enforced: false`，`net-isolation` 是提醒。

检查：`matrix-dsh-check` 加 `net-isolation`（假模型驱动：不经代理连控制面 `/api`、网关地址上的核心端口、网关的其他接口、别的沙箱、内网、元数据地址、公网，查 DNS；
经网关去元数据地址与内网）与 `key-absent`（在环境变量、各进程环境、主目录 / 工作目录 / `/tmp` 里找真密钥；拿沙箱的令牌请求没分配的模型）。
沙箱方式下 `key-hidden` 照旧只查服务器上直接起的 dsh（阶段 0 的口径），沙箱里有没有密钥看 `key-absent`。验证（本机，`insecure-runc`，核心在容器里、经网关与本机代理出网）：
`--live --sandbox docker` 27 项全过；`--sandbox local` 除 `resource-limit`、`net-isolation` 两项提醒（这个后端做不到）外全过；compose 形态两轮真实对话通过。

和设计不一样的地方：网关不是独立进程（这一步的要求就是核心里的模块，以后能拆）；网络形状是“每个执行单元一张 internal 网络 + 网关所在容器接上去”，
不是设计里的“一张 internal 网络 + 双网卡网关”（同一张网络上容器之间要么全通、要么连网关也不通，做不到只连网关）；只 GET / 预算 / 解 TLS 见下面的 2b。

**阶段 2b 的实现（2026-11-17，开关后面）。** 网关解开沙箱的 HTTPS，出网分级到方法与预算（6.4）：

- **出网 CA**（`matrix/egress_ca.py`）：第一次用到时生成，私钥只在控制面（`<data>/gateway/ca/ca.key`，0600），不进仓库、不进沙箱；按主机现签叶子证书
  （30 天，只说 HTTP/1.1），只用已有依赖 `cryptography`。轮换：删掉 `<data>/gateway/ca/` 重启。沙箱每轮从 `run.request.gateway_ca` 拿到 CA 证书，
  dsh 驱动把它和系统证书库合成一个包，设好 `SSL_CERT_FILE`、`REQUESTS_CA_BUNDLE`、`CURL_CA_BUNDLE`、`GIT_SSL_CAINFO`、`PIP_CERT`、`NODE_EXTRA_CA_CERTS`。
- **逐个请求放行**（`gateway.check_request`，纯函数）：包镜像源与 `fetch.json` 白名单只读（GET / HEAD）；公网读（要 `web.research`）只 GET / HEAD、不带请求体、
  URL ≤ 2 KB；公网写默认不允许，只到写白名单（`MATRIX_GATEWAY_WRITE_HOSTS`）。镜像源上 git 的 `git-upload-pack` POST 认作只读的取包请求（公网主机不认）。
  转给目标时用真的 TLS、校验目标证书。解不开的流量（证书固定的客户端、非 TLS / 非 HTTP 协议）这条连接直接断。明文 HTTP 同样按方法放行。
- **出网预算**：每一轮发往非白名单主机的请求行与请求头累计（`MATRIX_GATEWAY_BUDGET`，默认 64 KB），超了这一轮的公网读即停，并在对话里告诉所有者一次。
- **留痕加细**：场合里有别人、或会话记过别处来源的执行单元，公网请求在 `egress.jsonl` 记完整 URL，平时只记主机。
- 代理请求没带凭证时回 407 质询（git 等客户端等质询才带凭证）。沙箱里各家工具的缓存放到 `/tmp`（Agent 的命令里 HOME 只读）。
- `MATRIX_GATEWAY_TLS=off` 退回 2a 的按主机隧道。

检查：`net-isolation` 另查公网 GET 经网关放行、POST 被拒、超过预算后公网读被拒；新增 `egress-tools`（只有 `shell.exec`，经网关访问包镜像源：
curl、git clone、pip、uv、npm、Node 的 fetch 都要通，公网要被拒）。验证（本机）：`--live --sandbox docker`（insecure-runc，工具包 t8 的方式）28 项全过；
`--sandbox local` 除 `resource-limit`、`net-isolation`（这个后端做不到）两项提醒外全过；compose 形态两轮真实对话通过。
**没做的**：按主机注入凭证的最小形态（让 dsh 自带的供应商在沙箱方式下可用）这一版没做，沙箱方式下照旧只支持平台供应商；HTTP/2 只按 HTTP/1.1 说；
公网读预算只算请求行与请求头，不限响应大小。

**阶段 2：出口网关。** 沙箱网络默认全拒，客户端连接、模型调用、网页出网全部改经网关；模型密钥离开执行面；用量由网关记。
做完这一阶段，`security.md` 的“沙箱只管写、不管读”与信息流那条“可绕过 `open_note` 直接读磁盘”才能删掉，#59 关闭。

**阶段 3：收尾与 #68、#60。** 卷的用量：管理器定期统计每个执行单元卷的大小，超了上限停沙箱并通知所有者（docker 后端的 local 卷没有大小上限，1b 先接受）；插件服务迁入；节点级只读内容存储；预热池；管理后台的沙箱页（数量、配额、排队、出网记录）；
连接器凭证注入（#60）。

**阶段 4：集群。** `kubernetes` 后端、多节点调度。调度、预热池、休眠先评估 Kubernetes 的 agent-sandbox，不自己写
（research: cloud-agent-isolation#k8s-agent-sandbox；它的 API 还在变，用之前核对版本）。注意控制面自己还是单进程 + `state.json`，
登录也还是最简实现（`security.md` 第一条）：这两件是“生产级”的另外两块，不属于执行面，设计在 [control-plane.md](control-plane.md)（需求 #69）。

### 每个阶段的验收：能变红的检查

规则不靠记忆（AGENTS.md 工作方式第 8 条）。`matrix-dsh-check` 加一组在真实沙箱里跑的检查，让 Agent 的 `bash` 去试，试成了就是失败：

| 检查 | 让 Agent 去做 | 从哪个阶段起必须通过 |
| --- | --- | --- |
| `read-isolation` | 读数据目录里的标记文件、另一个执行单元的工作目录、别人的 dsh 会话、`vault.key` | 0 |
| `proc-isolation` | 列出沙箱之外的进程、读它们的环境变量 | 0 |
| `resource-limit` | 无限起进程、申请超额内存、写满磁盘；宿主与别的沙箱不受影响 | 1 |
| `net-isolation` | 连控制面的 `/api`、别的沙箱、内网地址、元数据地址、不经网关的公网 | 2 |
| `key-absent` | 在环境变量、文件、进程里找模型密钥；用沙箱令牌调一个没分配给这一轮的模型 | 2 |

引擎层的测试（假后端）：沙箱容量不够时任务进 `WAITING`；启动令牌只能用一次；一条沙箱连接只收得到自己执行单元的运行与材料；
`--isolation required` 下没有后端时拒绝云侧运行；私有目录的三方合并与来源标签在新通道下不变（不变量 15、22 的现有测试改跑两种通道）。

## 9. 破坏性影响

用户看到的协作语义（席位、委托、提问、信息流、端侧的审批）、`state.json` 里的数据、项目档案、私有目录、vault 都不变；不变量里只有第 14 条改写（云侧不再审批，7.1），另新增第 26 条（第 7 节）。
会变、而且有人会因此碰壁的是下面这些。

### 9.1 对部署方

| 变化 | 谁会碰壁 | 怎么办 |
| --- | --- | --- |
| 云侧运行要求宿主是 Linux 且装了 gVisor；compose 多两个服务 | 升级后没装 gVisor 的部署：`--isolation required` 下云侧 Agent 全部拒绝运行 | 先发一个版本默认 `--isolation preferred`（没有后端时照旧跑，后台标红），下一个版本才把默认改成 `required` |
| 共用的 `~/.dsh` 退役，云侧只认平台配置的供应商 | 用 `.env` 里的 `DEEPSEEK_API_KEY`、或进容器 `dsh` 登录的部署；没有 `models.json`、Agent 自由填 provider 的部署 | 升级前在后台“模型”页把供应商重配一遍。只能用账号登录、给不出地址加密钥的供应商，云侧不能再用 |
| Agent 不能再直接访问内网，出网只有 HTTP(S) 经网关 | Agent 用 `curl`、脚本直接调内网系统的用法（现在不受限）；走 SSH 的 `git clone`、直连数据库等非 HTTP 协议；不认 `HTTPS_PROXY` 的工具 | 内网目标写进 `fetch.json` 的 `allow`；包仓库在网关配镜像源；非 HTTP 协议不支持，要用就包成连接器 |
| 沙箱里只有镜像里的东西 | 往 Matrix 容器里另装过工具、挂过共享数据目录给 Agent 用的部署 | 工具装进沙箱镜像；数据改成项目档案文件或连接器 |
| 备份范围变了 | 只备份 `matrix-data` 卷的部署 | 还要备份内容存储（产物检查点）；执行单元的卷可以不备份（能从检查点重建）；`dsh-home` 不用再备份 |
| 云侧只支持 Linux | 在 macOS、Windows 上直接跑服务端并用云侧 dsh 的 | 只剩 `process` 后端（未隔离，单人本机） |

### 9.2 对用户与 Agent

- **有了上限**：超过内存配额的运行被结束；并发超过上限时排队（`WAITING`），以前是立刻全跑。沙箱停着时第一轮多几秒启动时间。
- **轮次之间只留工作目录**：`/tmp`、工作目录外的文件、沙箱里装到系统位置的东西，沙箱一停就没了（现在整个容器是共用且常驻的）。
- **外溢审批（不变量 14）基本失效**：实测（第 11 节第 2 项）套上外层以后，目标路径在外层里不存在时，bash 报“没有这个文件或目录”，
  dsh 不把它当成沙箱拒绝，根本不发起申请；目标路径只读可见时，会申请、人也批了，写入照样报“只读文件系统”。
  以前批准的是“写服务器磁盘上的任意位置”，这本身就是这次要堵的口子，所以不能为了让审批生效而把外面的路径挂成可写。
  **已定（2026-11-11）**：云侧取消外溢审批，工作目录以外一律不可写；端侧保留（7.1）。对用户的影响：云侧 Agent 不会再弹出
  “申请在工作目录以外操作”的确认，它要写别处时直接被拒绝；端侧 dsh 照旧弹。
- **人看到的工作目录是上一轮结束时的检查点**，不是运行中的实时状态；超过检查点上限的大文件要沙箱在才取得到。
- **工作目录的绝对路径不变**（4.3）：会话、脚本、`.venv` 里写死的路径照样有效。这一条原先写的是“改成 `/workspace`、加一个旧路径的链接缓解”，
  实测推翻：dsh 会把链接解析成真实路径，和会话记录对不上，续接直接失败。
- **迁移时搬不动的 dsh 会话会丢上下文**（见 10.2）。

### 9.3 对代码

- `Seat.workdir`、`store.seat_dir` / `task_dir` 不再是云侧运行的工作目录，引擎里直接读写它们的地方（约 10 处）都要改走检查点或材料：
  委托产物快照（`_deliver`）、人浏览工作目录（`_workdir_of`）、`publish_file` / `send_file`、写进任务目录的 `DELEGATION.json`
  与 `shared/`（改成材料）、`dsh-events.jsonl`（改存控制面的运行日志）。
- 端侧现在是“产物留在设备上、不放进委托方工作目录”。云侧不能照搬这个分支，否则委托交付会退化，必须先有检查点（5.2）。
- 连接器协议只做加法（私有目录的新方式、产物清单），旧的端侧客户端不受影响。
- `state.json` 只加字段，旧文件照常能读（`store._known`）。**迁移后不能直接降级**：旧版本看不到沙箱里做的改动（回退办法见 10.4）。

## 10. 旧数据迁移

### 10.1 哪些要动

| 数据 | 现在在哪 | 迁移 |
| --- | --- | --- |
| `state.json`、项目档案、私有目录、vault、发布物、模板、插件数据、对话附件 | 数据卷 | 不动，仍归控制面 |
| 席位与委托的工作目录 | `<data>/conversations/<id>/…`、`<data>/tasks/<id>/` | 产物进检查点，再按需进卷（10.2） |
| dsh 会话 | 共用的 `dsh-home` 卷 | 按会话 id 搬进各执行单元的 `/state`（每个会话两处文件，见 10.2），搬不了就开新会话 |
| dsh 里配的供应商与凭据 | `dsh-home` 卷 | 不自动迁移，部署方在后台重配（密钥不该由迁移脚本读出来再写一遍） |

工作目录里只迁产物（`workdir.outputs` 的口径）和别人交来的 `deliveries/`。网络每轮放进去的只读副本（`project/`、`attachments/`、
`skills/`、`agent-home/`、`shared/`、`DELEGATION.json`、覆盖层）不迁，下一轮按清单重新下发；依赖与缓存目录不迁，重装。

### 10.2 步骤

1. **备份** `matrix-data` 与 `dsh-home` 两个卷。
2. **升级时批量建检查点**（`matrix migrate workdirs`，可重复执行、可中断）：控制面读自己的数据目录，给每个席位、每个委托的现有工作目录
   生成第一份检查点。已经结束、以后不会再运行的委托也在这一步覆盖到，之后浏览、下载都读检查点。这一步不需要沙箱，也不改动原目录。
   超过检查点上限的目录不截断：整份留在原处，列进迁移报告，由部署方决定调大上限还是放弃。
3. **第一次进沙箱时按需恢复**：执行单元第一次在沙箱里运行时，管理器建卷，沙箱客户端从检查点恢复产物，搬入它的 dsh 会话。
   一个会话是两处文件：`.dsh/sessions/--<工作目录路径，/ 换成 ->--/<会话 id>/`（去掉其中的 `session.lock`）与
   `.dsh/storages/session_projcache/sessions/<会话 id>.json`，原样拷进新的 `HOME` 就能续接（实测）；前提是工作目录的绝对路径不变（4.3）。
   会话搬不了的（格式不允许、或文件已不在），把 `dsh_session_id` 清空，走引擎现有的“没有会话”流程：委托重发完整委托说明，
   席位重发还没进会话的消息。代价是 Agent 丢掉这个场合里以前的对话记忆，产物都在。
4. **灰度**：沙箱后端先只对部署方点名的用户生效（其余人照旧走 `process`），跑过第 8 节的检查、观察一段时间再全量。
5. **清理**：原工作目录与 `dsh-home` 不自动删，保留到部署方执行 `matrix migrate purge-legacy`。

**实现（2026-11-17）。** 入口是 `matrix migrate <动作> [--data <目录>]`，服务停着时跑（都改 `state.json`）。只处理云侧 Agent 的执行单元。

- `workdirs`：和第一次在沙箱方式下运行时的按需导入是同一段代码（`Network._sandbox_import`）：产物、别人交来的 `deliveries/`、dsh 会话
  （阶段 0 的状态目录，或更早的共用 `~/.dsh`）进检查点，台账记成已导入；导入过的跳过，所以可重复、可中断；不动原目录；
  超过检查点上限的文件不截断，留在原处并列进报告。已结束的委托也覆盖到。
- `export`：最新检查点里的产物写回原工作目录（覆盖同名文件，不删别的），交给这个单元的委托产物写回它的 `deliveries/`，
  会话包解到这个单元的 dsh 状态目录（阶段 0 起旧方式用它当 HOME，不是 10.4 原写的共用 `~/.dsh`）。台账记成 exported：再打开沙箱方式时从原目录重新导入。
- `purge-legacy`：删原工作目录、阶段 0 的状态目录、共用 `~/.dsh` 里这个会话的两处文件；不带 `--yes` 只列出来。只删导入过、检查点完整
  （没有只记清单的文件）、而且原目录里没有比检查点新的产物（迁移之后旧方式又写过）的。

真实验证（本机、真模型、`local` 后端）：旧方式让 Agent 记住编号并写 `first.txt` → `matrix migrate workdirs` → 沙箱方式写 `second.txt` →
`matrix migrate export` → 关掉开关、旧方式续接：记得编号，两个文件都在。

### 10.3 升级那一刻正在进行的事

和现在重启一样（不变量 12）：云侧运行中的轮次判失败、可续接；等待中的审批与提问作废；端侧任务回到等待。没有新的损失。

### 10.4 回退

清理之前可以回退：`matrix migrate export` 把各执行单元的最新检查点写回原来的工作目录位置，再把开关关掉。
沙箱里产生的 dsh 会话按 10.2 的两处文件放回这个执行单元的 dsh 状态目录（阶段 0 起旧方式的 HOME）就能续接（工作目录路径没变）。执行过 `purge-legacy` 之后只能从备份恢复。

### 10.5 其余

- **部署**：`compose.yml` 增加 `sandboxd` 与 `gateway` 两个服务和一张 `internal` 网络；宿主要装 gVisor。`deploy/README.md` 同步改。
- **本机开发不变**：`uv run matrix` 仍用 `process` 后端，界面标明“未隔离，仅限单人本机”。

## 11. 验证记录

2026-11-10 在一台 4 核 16 GB 的 Linux 虚拟机上做（Docker 29、cgroup v1、没有 KVM），dsh 0.2.1-rc.5，部署镜像按 `deploy/Dockerfile` 构建，
容器按 `compose.yml` 的安全选项以 `matrix` 用户运行；真模型是 DeepSeek（`deepseek-chat`），其余用 `matrix-dsh-check` 的假模型服务驱动 Agent 的 bash。
**这台机器的 Docker 没有 seccomp 支持**，所以 `seccomp=unconfined` 在这里不起作用，默认 seccomp 会不会拦嵌套 bwrap 没测到。

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | dsh 的 bwrap 能否在 gVisor 里运行 | **能，而且不用放开安全选项**（2026-11-11，见下文“gVisor 实测”） |
| 2 | 阶段 0 外层 bwrap 套内层 bwrap，在部署容器里能否运行 | **能**，见下文 |
| 3 | dsh 会话能否搬到另一个 `HOME`、换路径后能否续接 | **换 `HOME` 能，换路径不能**；在旧路径上 bind 挂载能，符号链接不能。方案已改（4.3、9.2） |
| 4 | 供应商指向网关、密钥填占位值时是否正常 | **正常**：流式、工具调用、重试、`compat` 都没问题，见下文 |
| 5 | gVisor 下的兼容性与 I/O 开销 | **全部跑通**；总耗时约 1.6 倍，`uv sync` 慢得多（约 8 倍），见下文 |
| 6 | 一轮运行的内存 | 单个执行单元峰值约 **250 MB**（runc）；gVisor 下每轮多约 90 MB，冷启动 0.7–1.9 秒，见下文 |

**第 2 项。** dsh 内层沙箱的实际参数是 `--ro-bind / / --unshare-pid --proc /proc --tmpfs /tmp --bind <工作目录> <工作目录>`：
整个根目录只读可见，不开网络与用户命名空间。外层用 `matrix/sandbox.wrap`（共享网络），只挂系统目录、Python 环境与 Matrix 代码（只读）、
这个执行单元的工作目录和它自己的 dsh 状态目录。对比（Agent 的 bash 去读）：

| | 现状 | 阶段 0 |
| --- | --- | --- |
| `vault.key`、`state.json`、别人的私有目录、别的席位的产物、共用的 `~/.dsh` | 都读得到 | 都不存在 |
| 父进程环境里的模型密钥 | 读不到 | 读不到 |
| 写工作目录 / 写工作目录以外 | 能 / 不能 | 能 / 不能 |

套上外层后 `matrix-dsh-check --live` 里回复、续接、技能、委托、连接器、提问、密钥隔离都通过；外溢审批失效（9.2）。
实现时要做的两件事是包装原型踩出来的：`TMPDIR` 要指向外层的 `/tmp`，`--patch` 指向的文件要挂进去。

**第 3 项。** 会话存在 `HOME/.dsh/sessions/--<工作目录路径>--/<会话 id>/` 与 `HOME/.dsh/storages/session_projcache/sessions/<会话 id>.json`，
索引和压缩日志的头里都写着记录时的工作目录。用真模型让 Agent 记住一个编号再续接问它：

| 做法 | 结果 |
| --- | --- |
| 新 `HOME`，只拷这两处，工作目录不变 | 续接成功，记得编号 |
| 新 `HOME`，换工作目录 | 失败：会话“recorded in 旧路径, not 新路径” |
| 再把会话目录名改成新路径 | 失败：日志头校验不过，判为损坏 |
| 旧路径是指向新位置的符号链接 | 失败：dsh 用解析后的真实路径 |
| 新位置 bind 挂到旧路径上 | 续接成功 |

**第 4 项。** 网关原型（标准库，约 120 行）：核对沙箱令牌、只放行分配给这一轮的模型、换密钥、流式转发、从 SSE 里读 `usage`。

| 场景 | dsh 的表现 |
| --- | --- |
| 正常，纯回复 / 带 bash 工具调用 | 都成功；dsh 只见过沙箱令牌 |
| 网关先回 2 次 500，或 2 次 429 | dsh 自己重试，第 3 次成功 |
| 流式响应转发一段后断开 | dsh 自己重试成功 |
| 令牌不对 / 模型没分配 | 立即失败，报 `AUTH: 401` / `AUTH: 403`，不反复重试。`runtime.ERROR_CLASSES` 里没有 `AUTH`，现在会归到 `runtime_error`，实现时加一类 |
| 配 `compat`（`maxTokensField: max_tokens` 等） | 改过的请求体原样到上游，DeepSeek 正常返回 |

**第 6 项。** 每 0.2 秒采样整棵进程树的常驻内存：一个执行单元一轮峰值 252 MB（dsh 约 228 MB，网络工具的 MCP 服务约 23 MB），两次一致；
委托时委托方与执行方同时在跑，峰值 441 MB。这是 Node 22 上普通对话加工具调用的数字，装依赖、编译这类重活没测，也没算 gVisor 自己的开销。

**补充（2026-11-11，另一台开着 seccomp 的 Ubuntu 24.04，runc）：**

- 部署容器里，去掉 `seccomp=unconfined` 后 bwrap 不能建命名空间，去掉 `systempaths=unconfined` 后不能挂 `/proc`。所以只要容器里还要跑 bwrap
  （现状与阶段 0），这两项就不能收紧；阶段 1 控制面不再跑 dsh，才能去掉。
- **bwrap 起不来时 dsh 并不拒绝执行**，而是退到了别的沙箱方式（1 号进程不再是 bwrap，看得到容器里的其他进程）：`/data` 写不进，
  但 `matrix-dsh-check` 的 `approval` 报“没申请升权就写到了工作目录以外”（目标在 `/tmp` 下）。`deploy/README.md` 原来写的
  “没有可用沙箱时 fail closed”不准确，已改。对方案的影响：沙箱里内层 bwrap 起不来时不能默认当作“有沙箱”，`matrix-dsh-check`
  要加一项检查内层用的是 bwrap（`deploy/isolation-check` 的探针已经会报 `INNER=`）。
- runc 下重活与内存的基线见 [deploy/isolation-check/README.md](../deploy/isolation-check/README.md) 第 8 节。

### gVisor 实测（2026-11-11）

用 [deploy/isolation-check](../deploy/isolation-check/README.md) 在一台阿里云主机上跑：Alibaba Cloud Linux 4.0.6（RHEL 系，内核 6.6）、
2 vCPU / 1.8 GB（低于工具包要求的 4 核 8 GB，另有约 700 MB 的其他服务在跑）、没有 KVM、Docker 24.0.9（cgroup v2、seccomp 开）、
gVisor release-20261102.0（默认平台 systrap），真模型 `deepseek-flash`。

**第 1 项：能，而且不用放开安全选项。** 两组安全选项（默认 + `no-new-privileges`；compose 现在放开的两项）结果一样：

- 直接起 bwrap（dsh 的原样参数、带用户命名空间、外层套内层）都成功；Agent 的命令在 bwrap 里（`INNER=bwrap`），只看得到 5 个进程。
- 阶段 0 外层套内层同样有效：数据目录、别人的私有目录与会话、`vault.key` 都读不到，工作目录照常可写。
- `matrix-dsh-check --live` 除 `approval` 外全部通过（含 `key-hidden`）。`approval` 时好时坏，runc 下同样如此，原因是检查本身：
  目标目录放在 `/tmp` 下，而 dsh 的内层沙箱把 `/tmp` 换成空的 tmpfs，写入报“不存在”而不是“只读”，模型有时直接收尾、不申请升权。
  已把目标挪到主目录下（`matrix/dsh_check.py`），本机连跑 5 次全部通过。
- 对比同一台机器的 runc（第 2 项的组合）：和参考机一样，只有放开两项时 bwrap 能跑；默认选项下 dsh 退到更弱的沙箱，
  `approval` 报“没申请升权就写到了工作目录以外”。`matrix-dsh-check` 已加一项 `sandbox`：Agent 的命令不在 bwrap 里就变红。

**第 5 项：全部跑通，没有兼容性问题。** 各步秒数（runc → gVisor）：

| 小文件 2 万个 | 512 MB 大文件 | git clone | pip 装 3 个包 | npm 装 3 个包 | uv sync | pytest | tsc | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0.9 → 2.0 | 3.4 → 5.9 | 0.9 → 1.2 | 1.5 → 2.4 | 13.2 → 15.6 | **1.6 → 12.7** | 7.3 → 11.3 | 0.9 → 1.8 | 34 → 54 |

大多数操作慢 1.2–2.2 倍。`uv sync` 慢约 8 倍，是唯一明显的异常：它从缓存往虚拟环境里链接、拷贝大量小文件，正落在 gVisor 文件系统开销最大的地方。
Agent 装 Python 依赖很常见，阶段 1 要专门调（第 3 项）。

**第 6 项（gVisor 部分）。** 机器小、同机有别的服务，绝对值偏差大，看相对值：

| | runc | gVisor |
| --- | --- | --- |
| 一轮运行（委托时同时两个 dsh），宿主看到的峰值 | 344 MiB | 437 MiB |
| 重活，宿主看到的峰值 | 423 MiB | 309 MiB |
| 冷启动（5 次，毫秒） | 389–627 | 695–1936 |
| 10 个空闲沙箱（`docker stats` 合计 / 宿主已用内存增加） | 0 / 55 MiB | 96 / 174 MiB |

gVisor 每轮多约 90 MB，空闲沙箱约 10–17 MB 一个，冷启动 1–2 秒。按 4.4 的“空闲 10 分钟才停”，大多数轮次碰不到冷启动。

### 检查点恢复与并发基线（2026-11-16）

**检查点恢复：能。** 按 5.2 的做法，第一轮让 Agent 记住一个编号、写一个文件，把会话的两处文件与产物打成包（共 4 个文件、约 15 KB），
销毁容器；在全新的容器里解包到全新的 `HOME` 与同一路径的工作目录，续接同一个会话：记得编号，接着改了那个文件，会话 id 不变。
同一个包拿到另一个环境（Ubuntu 而不是 Debian、Node 22 而不是 24、root 而不是 `matrix` 用户）解包，同样续接成功。
所以“卷只是缓存、执行单元可以在任何节点上重建”成立。工具包里是 `t5`。

**并发基线（runc，16 GB 的机器）**：同时起 2、4、8 个执行单元，每个里一个 dsh 在跑命令，全部成功；宿主已用内存每个执行单元增加
253–260 MiB，随个数线性增长，和单个时的实测一致。工具包里是 `t7`。

**`uv sync` 拆开计时（runc）**：1500 个文件的虚拟环境，缓存已有时放文件只要 0.05–0.2 秒（硬链接最快），项目与缓存不在同一个文件系统时
退成拷贝、0.3–0.4 秒；冷缓存（含下载）0.6–1.2 秒。gVisor 下那 12.7 秒里下载与放文件各占多少，要在 gVisor 上跑 `t6` 才知道。

### 还要验证

只剩两项，都要在装了 gVisor 的机器上跑 [deploy/isolation-check](../deploy/isolation-check/README.md) 的 `t6`、`t7`：

1. `uv sync` 在 gVisor 下慢的原因与调法（`t6`）。结果怎么用：慢在放文件，就把 uv 缓存放进执行单元的卷、镜像里设 `UV_LINK_MODE`
   为最快的那种；慢在下载，就查 gVisor 的网络栈（`runsc-hostnet` 变体做对照）；两种 overlay 设置的变体用来定根文件系统怎么挂。
2. gVisor 下的并发与内存（`t7`），用来定内存上限与并发的默认值。在此之前沿用 4.3 的估算。

## 12. 横向扩容与重启恢复

2026-11-16。结论先说：**单机、几十个并发的规模，本方案够用**，重启沿用“判失败、可续接”，不比现状差。要多节点或多实例，卡点不在沙箱，
在控制面的状态。业界的共同做法是把要活下来的状态都搬出进程和沙箱，让两者都可以随时换
（research: cloud-agent-isolation#brain-hands-session）；本方案对沙箱做到了这一点，对控制面没有。

### 12.1 本方案内已经定的

| 问题 | 做法 | 在哪 |
| --- | --- | --- |
| 节点坏了丢 Agent 的对话记忆；卷把执行单元钉在一台机器上 | dsh 会话随检查点存到控制面，卷只是缓存 | 5.2 |
| 控制面重启后不知道哪些沙箱在跑，误杀或留下孤儿 | 台账以控制面为准，容器与卷带执行单元 id 与代数，定期对账 | 4.4 |
| 沙箱客户端断线、崩溃后连不回来（启动令牌是一次性的） | 执行单元凭证绑定执行单元，凭它重连；客户端崩溃即沙箱退出，重建时重签 | 4.4 |
| 长轮次中途沙箱没了，丢掉这一轮的产物 | 轮次中的增量检查点（阶段 3） | 5.2 |

### 12.2 控制面：现在只能跑一个实例

下面这些都在控制面，不属于执行面，归需求 #69，解法见 [control-plane.md](control-plane.md)（单写者核心 + 增量落库 + 备机，按租户分片）。
列在这里是因为不解决它们，加再多沙箱节点也只有一个控制面在调度。右边一列是需要的能力，具体怎么给见那篇：

| 现状（代码里核对过） | 多实例或重启不中断需要的 |
| --- | --- |
| 全部状态是一个整存整取的 `state.json`（`Store.save` 每次重写整份） | 数据库；消息、委托、工具调用、审批改成追加的事件记录，重启不丢、多实例共享（research: cloud-agent-isolation#durable-execution） |
| 执行上下文令牌只在内存（`Network._contexts`） | 持久化，任何实例都认 |
| 等待中的审批、提问是进程里阻塞的线程（`_approval_waits`、`_question_waits`） | 等待状态落库，回答到达时由任何实例唤醒 |
| 终止信号、私有目录写回锁、插件页面的令牌密钥、远程 MCP 会话只在内存 | 共享存储里的锁与密钥；会话按需重建 |

### 12.3 控制面重启不打断运行

沙箱里的 dsh 在控制面重启时其实还活着，是控制面按不变量 12 把那一轮判了失败。要改成不打断，需要三样
（设计见 [control-plane.md](control-plane.md) 第 5 节）：

1. 执行上下文令牌与在途轮次的记录持久化，重启后还认。
2. 沙箱客户端重连后能认领原来那一轮（现在的端侧协议里，断线后任务回到等待、重新来过）。
3. 重连期间沙箱里产生的事件与工具调用有地方缓冲（客户端本地排队，连上后补发，网络按序号去重）。

做到之前，每次发版都会中断全部云侧运行。缓解办法：发版前停止派新轮次，等在途的轮次结束（设上限时间）再重启。

### 12.4 执行面多节点

- **卷**：单机用本机卷。多节点不用网络盘（gVisor 下 I/O 本来就慢），执行单元换节点时从检查点重建，代价是依赖重装。
- **调度**：哪个节点有余量、排队的先后、每用户配额。集群阶段交给 Kubernetes 与 agent-sandbox（第 8 节阶段 4），单机只有并发上限与排队。
- **网关与管理器**：单机上各一个，是单点。网关重启会断开全部流式响应与长连接：dsh 对模型调用会自己重试（实测，第 11 节第 4 项），
  客户端凭执行单元凭证重连。多节点时网关按节点部署，长连接的路由回到 12.2。

### 12.5 不照搬的

- **会话就是网络自己的事件日志、执行程序完全无状态**（托管 Agent 的做法）：Matrix 用的是别人的 harness（dsh、Claude Code、Codex），
  对话记忆在它们各自的会话文件里，网络读不懂也重放不了。所以分两层：harness 的会话当不透明的块存（5.2），网络自己那一层改成事件记录（12.2）。
- **整机内存快照**（暂停后原样恢复，连进程一起）：各家成熟度不一；gVisor 自带的 checkpoint/restore 没验证过和 dsh 能否配合。
  先用“产物 + 会话文件”的检查点，中途被杀的那一轮靠续接补（research: cloud-agent-isolation#snapshots）。
- **引入持久化执行框架**：核心机制是“追加日志 + 幂等步骤”，先自己做，不为此多一个要运维的组件。

## 13. 明确不做的

- 不把 Docker socket、Kubernetes 凭证交给 Matrix 服务进程。
- 不做“同一个用户的沙箱可以互相读”的优化：不变量 22 在同一个人的不同场合之间也成立。
- 不在沙箱里放任何能长期使用的凭证，包括部署方自己的内网账号。需要的访问一律经网关按次注入。
- 不保留“没有沙箱就悄悄退回子进程”的路径。
