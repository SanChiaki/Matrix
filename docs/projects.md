# 项目与项目会话（设计）

> 当前实现要点见 [reference/projects.md](reference/projects.md)，不变量见 [reference/invariants.md](reference/invariants.md)。

## 1. 为什么只有一层

早先是两层：群组带一整套目标性质的档案（brief、决定、文件），项目又在上面套一层同样的东西，人要判断写进哪一层、
理解“挂载”“方面”“提升”这些只为连接两层而存在的操作；Agent 每轮拿两段背景，外加“项目决定为准”的优先级规则。
现在两层收敛为**项目**一层。

已定的取舍：

1. 委托边界就是项目，没有群组这一层。
2. 有别人的项目里所有参与方看得到项目的全部内容。
3. 纲要（原 brief）默认对项目里的所有人可见。
4. 不做“复制成员 / 模板”。
5. 没有“一个方面由多个群组承担”的用法，方面整个去掉。
6. 人在项目里通过**项目会话**和自己的助理 Agent 私下对话，助理的能力和群聊席位一致。

## 2. 模型

**项目** = 成员 Agent + 人（所有者 / 参与者）+ 一个项目群聊 + 项目档案。

- 项目没有类型。主持人随时可以邀请（参照 Raft 的 joint channel，research: raft#joint-channel），参与者接受后各自带上自己的 Agent，
  档案与群聊对所有参与者可见。有参与者或待接受的邀请就是**共享项目**（`Project.shared`，见第 6 节）。
- 项目档案：**纲要**（目标、范围、成功标准、当前阶段，≤4000 字）、决定、文件、资源引用、纲要修改建议（不变量 17）。
- 委托只发给项目成员；Agent 不跨信任域，委托可以跨（共享项目）。
- 私聊在项目之外。

**助理**：`User.assistant_id`，用户指定的自己的一个 Agent，默认是第一个创建的，可以换。

- 人进项目（创建项目、接受邀请）时，这个人的助理自动成为成员，群聊里记一条事件。
- 人在项目里时助理不能被移出；换助理后新助理在下次进项目或开会话时加入，旧助理留在已有项目里，去留由人决定。
- 人退出 / 被移出时这个人的 Agent 一并移出，在这个项目里的会话归档为只读（本人仍看得到）。

**项目会话**：`Conversation.kind = session`，带 `project_id`、`owner_id`（这个人）、`agent_id`（这个人的助理）。

- 一个人在一个项目里可以有多个，命名、归档；只有这个人看得到（共享项目里其他参与方看不到）。
- 每个会话是一个独立席位（独立会话、工作目录，不变量 7），能力和群聊席位一致：委托项目成员、登记用户任务、用档案工具。
- 影响共享状态的写入（决定、文件、纲要修改建议）在项目群聊里记一条事件，参与方不会被蒙在鼓里。
- 会话里登记的用户任务属于这个项目、照常上看板，可见性不变（下发人 + 接任务 Agent 的所有者）。

分工：**群聊是项目的公开记录**（要让大家看到的交代、讨论、结论），**会话是一个人的私下工作区**（了解细节、想清楚、让助理代办）。

## 3. 会话携带的上下文

1. 项目档案：和群聊席位一样按 `archive_rev` 推送，文件放在只读的 `project/`。
2. 有上限的现状快照：成员、没结束的用户任务、最近的群聊公开消息，条数与字节封顶，只在变化时重新推送
   （参照 xMatrix 启动时只给有界历史，research: xmatrix#context-isolation）。
3. 只读网络工具：`read_chat`（按关键词读群聊的一段）、`read_request`（用户任务与它的委托、交付说明）。

助理读到的一切按**它的所有者**在这个项目里的可见性过滤（不变量 18）：共享项目里别人 Agent 的过程、只给两端所有者的委托，助理同样读不到。
会话里只有自己在说话，但它能写档案、能委托，输出能到达项目里的每个人，所以私有目录按群聊同样的规则挂载（第 6 节）。

## 4. 去掉的东西

| 以前 | 现在 |
| --- | --- |
| 项目（汇总层）、方面、挂载 / 移出 | 没有；一个项目就是原来的一个群组 |
| 群组档案 + 项目档案、两段背景、“项目决定为准” | 一份项目档案 |
| 项目文件的提升、`publish_file target=group/project` | 只有项目文件 |
| 跨群组交接（依赖、替换、交回） | 项目内委托：协调的 Agent 依次委托、靠收件箱唤醒等交付 |
| 负责人统筹、停滞提醒 | 被 @ 的 Agent 协调，直接委托方验收（不变量 5）；委托链禁止成环（不变量 4），互等形成不了 |
| 项目文件共享给联合群组 | 共享项目全可见 |
| 内部 / 联合项目两种类型、私有目录挂载开关 | 邀请了别人就是共享项目；私有目录按来源场合挂载（第 6 节） |

接受的代价：中间环节不上看板（在任务详情里看）；协调的 Agent 需要 `delegate`；群聊噪音随成员增长；
委托次数默认不限制，需要时由所有者在 Agent 设置里设上限（`max_delegations`）；共享项目里合作方 Agent 能直接委托你的 Agent
（外溢审批仍找所有者）。

## 5. 旧数据迁移（`Store._load`，测试见 `tests/test_migration.py`）

- 迁移前的 `state.json` 原样另存为 `state.v1.json`。
- 没挂项目的群组 → 项目，无损；`groups/<id>/` → `projects/<id>/`。
- 挂了多个内部群组的旧项目 → 合成一个项目：成员取并集；纲要、决定、文件以旧项目为准，各群组的带上来源标注（文件重名加前缀）；
  最近活跃的群聊留作项目群聊，其余归档为只读。
- 挂在旧项目里的联合群组单独成为联合项目（不同信任域，不合并），带上原来共享给它的项目文件。
- 未完成的交接作废并在群聊里记事件；负责人设置丢弃；`UserRequest.project_id` 指向新项目，方面丢弃。
- 已有用户的助理取最早创建的 Agent；已有项目里不在加载时加 Agent，等人第一次开会话时再加并记事件。

## 6. 共享项目与信息流（不变量 22）

以前项目分内部和联合两种，建好不能转换；联合项目里私有目录默认不挂，要所有者按项目打开。结果是：跨用户协作时 Agent 什么经验都带不进来，
开关又是没人会去点的心智负担，从自己的项目邀请别人只能重建。

现在两件事一起改：

- **项目类型从事实推导**：有参与者或待接受的邀请就是共享的。任何项目都能邀请；第一次邀请时网络让群聊席位换新会话
  （旧会话里可能有只该你知道的东西），群聊记一条“开始与他人共享”。主持人第一次邀请前，界面写明对方会看到多少条消息、文件和决定。
  最后一个参与者走了，项目回到只有你。插件与 API 仍给推导出来的 `kind`。
- **信息只流向当时在场的人**（参照情境完整性，research: information-flow-control#contextual-integrity）：
  网络管住“说出去”，不管“知道什么”。

规则（`matrix/flow.py`，纯函数）：

| 概念 | 定义 |
| --- | --- |
| 场合 | 项目 id；私聊、项目会话、助理对话里写的算 `me`（只有所有者在场） |
| 场合在场的人 | 项目现在的参与者 + Agent 的所有者；`me` 与已删除的项目只有所有者 |
| 文件标签 | 写它的那些运行的场合与来源，加上写时有没有别人的输入（`mixed`）；没有标签的老文件按 `me` |
| 一轮的 reach | 在项目里（群聊、任务、项目会话）是项目的全部参与者，私聊只有所有者 |
| 挂载 | `skills/` 总是挂；其余文件在场的人包含 reach、或每个场合都有授权才挂；没挂的只列名字 |
| 会话来源 | `open_note` 读过的文件的场合，记进 `Seat` / `Task` 的 `session_sources`，跟着模型会话走，会话重开才清空 |
| 放行 | 输出给听众 A：每个来源场合 v 都要 A ⊆ 在场的人(v)，或有授权（`Project.flow_grants[agent] ∋ v`） |

流程：

1. 没挂上的笔记用 `open_note` 读。这一轮还能联网、执行命令、用连接器时（能把内容带出网络），内容排到下一轮交出，
   来源越界的会话之后都没有这三种能力（收窄，不记违规），参照 CaMeL / Dual LLM（research: information-flow-control#camel、
   research: information-flow-control#dual-llm）。
2. 群聊回复、委托交付不放行时拦成 `Held`：群聊里只留一条“回复要先给它的所有者确认”，正文不出去；交付时任务停在进行中，
   工作目录对受托方所有者以外的人隐藏。会让别人看到内容的网络工具（记录决定、发布文件、委托等）直接拒绝，提示写进回复由所有者确认。
3. 所有者在卡片上选：**发这一次**（会话仍带着来源，下次还会问）、**发出并以后在这里都能用**（写入授权，收窄随之解除）、
   **不用那些资料重写**（换新会话、清空来源，原来的问题重新送达）。没有超时。
4. 有别人的场合里 `skills/` 的改动不写回（免得合作方往以后每个场合都会加载的技能里投毒）；没挂上的文件在这一轮被同名写出，另存冲突副本。
5. 端侧 Agent 第一版没有来源标签：共享项目里私有目录不挂，没有 `open_note`。

取舍（也记在 [security.md](reference/security.md)）：

- **文件名会泄露**：没挂上的笔记的名字出现在提示词里，但不算来源。接受：名字通常不是要保护的内容，列出来才能让 Agent 知道去读。
- **读了没用也会拦**：按会话整体判定，不看回复里实际用了什么。故意的，判断要能不靠模型、不看内容。卡片会重复出现，所以有“以后都能用”。
- **读隔离**：云侧沙箱只管写不管读，被诱导的模型可以绕过 `open_note` 直接读磁盘。规则对“没被诱导的 Agent 不会说漏”有效，
  对主动绕路要等读隔离（REQUIREMENTS #34）。
- **在场的人按现在算**：项目后来加了人，以前在这里写的笔记对新来的人也算在场。邀请前的确认框写明这一点。
