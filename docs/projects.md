# 项目：目标与汇总层（设计）

> 状态：第一、二阶段已实现。第三阶段只是方向，动手前再细化。

## 1. 要解决的问题

一件大事（"新产品上线"）会拆成几个**方面**（市场调研、原型开发、合规审查），分别由不同的群组、不同的 Agent 承载。
现在群组之间没有任何联系：人看不到这件事整体进展到哪了，也说不清某张看板卡片属于哪件事。

## 2. 核心判断：项目不是"超级群组"

群组同时是**共享的对话空间**和**委托的边界**："只委托同组成员""上下文默认隔离""只有公开消息互通"都挂在群组上。
如果项目也共享上下文（项目内群聊互通、知识自动流动），会同时破坏不变量 7（上下文隔离）、9（知识只显式共享）、
13（可见性），在联合群组里还会跨信任域（16）。

所以：**项目汇总工作，不打通群组**。群组、委托、知识、可见性的规则一条不改；流向 Agent 的只有显式的项目背景与项目文件（第 7 节）。

```
项目「新产品上线」（所有者：你）
├─ brief：目标 / 范围 / 成功标准 / 当前阶段
├─ 方面：市场调研 · 原型开发 · 合规审查
├─ 挂载的群组：调研组 → 市场调研；开发组 → 原型开发；…
└─ 汇总：各方面的用户任务、状态、阻塞
```

## 3. 模型

- `Project`：所有者（`owner_id`）、名称、描述、brief、方面列表（`workstreams`）。
- `Workstream`：项目里的一个方面（名称、说明）。一个方面可以由多个群组承担。
- `Group.project_id` / `Group.workstream_id`：一个群组**最多属于一个项目**（否则推送背景时说不清推哪个项目）。
- `UserRequest.project_id` / `UserRequest.workstream_id`：**由网络按所在群组认定**，不让模型填（与下发人由网络认定同一原则）。
  - 群组挂上 / 移出项目、换方面时，它的**未结束**任务（`in_progress` / `in_review`）跟着改；已结束的保留当时的归属（历史）。
  - 私聊里的任务默认不属于任何项目，人可以手动归类（只能归到自己的项目）。
- 原来的 `Group.projects`（`ProjectRef`：仓库 / 路径的指针）改名为**资源引用** `Group.refs`（`ResourceRef`），
  避免和"项目"重名；`Store._load` 把旧的 `projects` 读成 `refs`。

## 4. 信任域与可见性

- 项目**只有一个所有者**。只有所有者看得到、改得了项目（无权限按"不存在"处理）。多方协作仍走联合群组。
- 只有群组的所有者 / 主持人能把群组挂进**自己的**项目；别人的内部群组不能挂（那是另一个信任域）。
- 第一阶段**只允许内部群组**挂项目。联合群组挂项目（第三阶段）要先回答：项目信息对其他参与方露出多少。
- 项目里的汇总按现有可见性过滤（`can_see_request`）：项目所有者看不到自己本来看不到的任务。
- 项目事件（`project.updated` / `project.deleted`）只推给所有者。

## 5. 分阶段

| 阶段 | 内容 | 提示词 / 不变量 |
| --- | --- | --- |
| 1 | Project 模型；群组、用户任务挂项目与方面；项目页；看板按项目 / 方面筛选 | 不改：纯组织层，Agent 不知道项目存在 |
| 2 | 项目 brief 摘要与"你所在群组负责 X 方面"推送给挂载群组的席位（按版本、有预算）；交付物显式发布到项目 | 改提示词；新增不变量："项目推送只到挂载群组" |
| 3 | 联合群组挂项目（推进联合群组 = 对那个群所有参与方公开）；Agent 提议跨群组任务，由人确认（同 `propose_agent`） | 新增网络工具 |

第一阶段用来验证"项目"这个维度对人是否有用。实际用一个多群组项目跑下来（PRD → 实现 → 验收 → 文档），第一个卡点是
**交付物不能跨群组**：产品组定稿的 PRD，开发组、测试组、文档组都要用，人只能各上传一份、之后还会版本漂移。于是做了第二阶段。

## 6. 第一阶段接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/projects` | 自己的项目列表（带群组数、任务计数） |
| POST | `/api/projects` | 新建（name、description） |
| GET | `/api/projects/{id}` | 详情：项目、方面、挂载群组、按方面分的任务 |
| PATCH | `/api/projects/{id}` | 改名称 / 描述 / brief |
| DELETE | `/api/projects/{id}` | 删除：群组与任务的归属清空，群组与任务本身不动 |
| POST | `/api/projects/{id}/workstreams` | 加方面 |
| PATCH / DELETE | `/api/projects/{id}/workstreams/{ws}` | 改 / 删方面（删除后引用它的群组、任务回到"未分方面"） |
| PUT | `/api/groups/{id}/project` | 挂载 / 换方面 / 移出（`project_id`、`workstream_id`，都可为 null） |
| PUT | `/api/requests/{id}/project` | 手动归类一张任务卡 |
| — | `/api/groups/{id}/refs` | 原 `/api/groups/{id}/projects`（资源引用） |

## 7. 第二阶段：项目背景与项目文件

- **项目背景**（`protocol.format_project`）：项目名、"群组「X」负责「Y」方面"、项目 brief、各方面与承担的群组。
  推送给挂载群组的席位与委托任务；只在 `Project.archive_rev` 或群组承担的方面变化时重新推送（`Seat/Task.project_seen`）。
  `archive_rev` 在名称 / 描述 / brief、方面、群组挂载、项目文件变化时 +1。背景里写明"别的方面的成员不在你的群组里，不能委托"。
- **项目文件**：`projects/<id>/files/`，每轮只读拷进挂载群组工作目录的 `project/`（运行后丢弃），端侧随 `materials` 下发。
  写入三条路：Agent `publish_file`（`target=project`，只能发到自己群组所属的项目，来源群聊记一条事件）；人上传；
  人把挂载群组的群组文件**提升**到项目（拷贝）。变更记入 `projects/<id>/log.jsonl`。
- **不变量 18：项目推送只到挂载群组**。私聊、未挂载的群组、联合群组拿不到；项目与挂载群组同一个所有者，不跨信任域。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/projects/{id}/files` | 上传（name、content） |
| POST | `/api/projects/{id}/files/promote` | 把挂载群组的文件提升到项目（group_id、name） |
| GET / DELETE | `/api/projects/{id}/files/{name}` | 下载（附件）/ 删除 |
