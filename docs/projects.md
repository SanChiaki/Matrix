# 项目：目标与汇总层（设计）

> 状态：第一、二、三阶段已实现（联合群组挂项目见 §10）。

## 1. 要解决的问题

一件大事（"新产品上线"）会拆成几个**方面**（市场调研、原型开发、合规审查），分别由不同的群组、不同的 Agent 承载。
现在群组之间没有任何联系：人看不到这件事整体进展到哪了，也说不清某张看板卡片属于哪件事。

## 2. 核心判断：项目不是"超级群组"

群组同时是**共享的对话空间**和**委托的边界**："只委托同组成员""上下文默认隔离""只有公开消息互通"都挂在群组上。
如果项目也共享上下文（项目内群聊互通、知识自动流动），会同时破坏不变量 7（上下文隔离）、9（知识只显式共享）、
13（可见性），在联合群组里还会跨信任域（16）。

所以：**项目汇总工作，不打通群组**。群组、委托、知识、可见性的规则一条不改；流向 Agent 的只有显式的项目背景与项目文件（第 7 节）。

```
项目「新产品上线」（所有者：你）
├─ brief：目标 / 范围 / 成功标准 / 当前阶段
├─ 方面：市场调研 · 原型开发 · 合规审查
├─ 挂载的群组：调研组 → 市场调研；开发组 → 原型开发；…
└─ 汇总：各方面的用户任务、状态、阻塞
```

## 3. 模型

- `Project`：所有者（`owner_id`）、名称、描述、brief、方面列表（`workstreams`）。
- `Workstream`：项目里的一个方面（名称、说明）。一个方面可以由多个群组承担。
- `Group.project_id` / `Group.workstream_id`：一个群组**最多属于一个项目**（否则推送背景时说不清推哪个项目）。
- `UserRequest.project_id` / `UserRequest.workstream_id`：**由网络按所在群组认定**，不让模型填（与下发人由网络认定同一原则）。
  - 群组挂上 / 移出项目、换方面时，它的**未结束**任务（`in_progress` / `in_review`）跟着改；已结束的保留当时的归属（历史）。
  - 私聊里的任务默认不属于任何项目，人可以手动归类（只能归到自己的项目）。
- 原来的 `Group.projects`（`ProjectRef`：仓库 / 路径的指针）改名为**资源引用** `Group.refs`（`ResourceRef`），
  避免和"项目"重名；`Store._load` 把旧的 `projects` 读成 `refs`。

## 4. 信任域与可见性

- 项目**只有一个所有者**。只有所有者看得到、改得了项目（无权限按"不存在"处理）。多方协作仍走联合群组。
- 只有群组的所有者 / 主持人能把群组挂进**自己的**项目；别人的内部群组不能挂（那是另一个信任域）。
- 联合群组由主持人挂进主持人自己的项目，只露共享部分（§10）。
- 项目里的汇总按现有可见性过滤（`can_see_request`）：项目所有者看不到自己本来看不到的任务。
- 项目事件（`project.updated` / `project.deleted`）只推给所有者。

## 5. 分阶段

| 阶段 | 内容 | 提示词 / 不变量 |
| --- | --- | --- |
| 1 | Project 模型；群组、用户任务挂项目与方面；项目页；看板按项目 / 方面筛选 | 不改：纯组织层，Agent 不知道项目存在 |
| 2 | 项目 brief 摘要与"你所在群组负责 X 方面"推送给挂载群组的席位（按版本、有预算）；交付物显式发布到项目 | 改提示词；新增不变量："项目推送只到挂载群组" |
| 3 | 联合群组挂项目（推进联合群组 = 对那个群所有参与方公开）；Agent 提议跨群组任务，由人确认（同 `propose_agent`） | 新增网络工具 |

第一阶段用来验证"项目"这个维度对人是否有用。实际用一个多群组项目跑下来（PRD → 实现 → 验收 → 文档），第一个卡点是
**交付物不能跨群组**：产品组定稿的 PRD，开发组、测试组、文档组都要用，人只能各上传一份、之后还会版本漂移。于是做了第二阶段。

## 7. 第二阶段：项目背景与项目文件

- **项目背景**（`protocol.format_project`）：项目名、"群组「X」负责「Y」方面"、项目 brief、各方面与承担的群组。
  推送给挂载群组的席位与委托任务；只在 `Project.archive_rev` 或群组承担的方面变化时重新推送（`Seat/Task.project_seen`）。
  `archive_rev` 在名称 / 描述 / brief、方面、群组挂载、项目文件变化时 +1。背景里写明"别的方面的成员不在你的群组里，不能委托"。
- **项目文件**：`projects/<id>/files/`，每轮只读拷进挂载群组工作目录的 `project/`（运行后丢弃），端侧随 `materials` 下发。
  写入三条路：Agent `publish_file`（`target=project`，只能发到自己群组所属的项目，来源群聊记一条事件）；人上传；
  人把挂载群组的群组文件**提升**到项目（拷贝）。变更记入 `projects/<id>/log.jsonl`。
- **不变量 18：项目推送只到挂载群组**。私聊、未挂载的群组、联合群组拿不到；项目与挂载群组同一个所有者，不跨信任域。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/projects/{id}/files` | 上传（name、content） |
| POST | `/api/projects/{id}/files/promote` | 把挂载群组的文件提升到项目（group_id、name） |
| GET / DELETE | `/api/projects/{id}/files/{name}` | 下载（附件）/ 删除 |

## 7.1 项目决定

试跑 v1.1 里同一个缺陷（错误文案和 PRD 不一致）被两个组做出了相反的处理：测试组交接给开发组修，文档组决定按实际文案写文档。
两边都合理，但需要有人对整个项目拍板，而群组决定只在群组里有效。

- `Project.decisions`：只有项目所有者记录 / 撤销（`/api/projects/{id}/decisions`），作为项目背景的一部分推送给所有挂载群组
  （最近 12 条有效的）；和群组决定冲突时以项目决定为准。Agent 不能写项目决定——要拍板的事在回复里提给人。

## 8. 第三阶段（部分）：跨群组交接

试跑里第二个卡点是**交接全靠人转述**：开发组交付后，人要读完结果、再到测试组 @ QA 复述一遍；Agent 自己也在回复里写
"请把实现发布后在群里 @QA"。

- 网络工具 `handoff`（group、agent、message），只有挂在项目里的群组有。目标必须是同一项目里的**其他**群组的成员。
- 交接先是待确认（`Handoff`，`pending`）。项目所有者确认时可以改内容、换接手的成员；确认后网络以**他的名义**往目标群聊发
  一条消息并 @ 目标成员（`来自「X」的 Y，已由我确认`），之后就是普通的群聊任务（被 @ 的成员登记、交付、由人验收）。
- 发出后只往提交者的收件箱放一条通知（不唤醒），不采纳时唤醒它并带上意见。
- **回路**：由这条消息引出的用户任务被人验收通过时，网络唤醒提交者，带上对方的交付说明（`handoff_done`）。试跑里 Writer 交接实测给 QA 后明确说“等回执再发布定稿”——没有回路的话，人还得再去文档组 @ 一次。
- **依赖**：交接可以写 `after`（Agent 提交时写，或人确认时勾选）：确认后先排队（`scheduled`），依赖的交接都完成（人验收了它引出的任务）时，网络以确认人的名义发出。试跑 v1.1 里 PM 一次提了开发、测试、文档三个交接，测试和文档都要等开发交付——没有依赖时，人只能先压着后两个，等开发验收后再回来点。
- **不变量 19：跨群组只经人或项目负责人**。负责人统筹见第 9 节。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/handoffs` | 自己要确认的交接 |
| POST | `/api/handoffs/{id}/approve` | 确认（可选 text、agent_id、after），依赖完成后以自己的名义发出；对排队中的传 `after: []` 立即发出 |
| POST | `/api/handoffs/{id}/reject` | 不采纳（note） |

## 9. 负责人统筹：交接由项目负责人 Agent 确认

试跑 v1.1 里人的确认、验收大多是走过场；真正有判断的几次（定缺陷怎么处理、拒掉重复的交接、换一个更好的交接、答一个文案问题）
本来就是产品负责人该做的事。所以让所有者可以把**交接确认**交给项目里的一个 Agent，人只处理越界的部分。

- 所有者指定项目负责人（`Project.lead_agent_id`，必须是某个挂载群组的成员；`lead_group_id` 是它统筹的群组）并打开统筹
  （`autonomy = lead`）。负责人只在**那个群组的群聊席位**里有 `review_handoff`（确认、不采纳、交给人；确认时可以改内容、换成员、
  改依赖、替换），身份由网络按执行上下文认定。项目背景里写明负责人是谁。
- 别人提交的交接进负责人的收件箱（`handoff_review`）并唤醒它；负责人自己提交的、不和进行中的交接重复的直接确认。
  确认后照旧以所有者的名义发出，消息里写“已由项目负责人 X 确认”，记在 `Handoff.approved_by_agent`。
- **不变量 20：边界由网络强制，越界转给人**（`Handoff.reviewer = owner`，`escalation` 写原因，出现在人的待办里）：
  24 小时内负责人确认的交接总数（`Limits.lead_daily`，默认 20）、同一对群组之间的条数（`lead_pair`，默认 4，防止来回返工）；
  负责人的席位出错暂停；负责人这一轮收到却没处理（参照委托的“送达即处理”）；负责人自己要求转交（改范围、改验收标准、发布、拿不准）。
- 所有者随时可以直接确认 / 不采纳任何交接；改回人工、换负责人时，还等负责人确认的一律转给人；负责人离开它统筹的群组时统筹失效。
- 负责人不改 brief、不记项目决定。

- **停滞提醒**：一轮结束（以及服务启动）时，如果项目里没有在跑的工作，却有交接排在依赖后面、依赖的工作停在“进行中”
  （没有谁会被唤醒），网络把局面告诉负责人，同样的局面只提醒一次（`Project.stall_key`）。试跑 v1.3 里 Writer 等测试结论
  才交付、测试又排在 Writer 之后，互相等待；网络看不出谁在等谁，只能指出停在哪里。负责人可以用 `review_handoff`
  `decision=send_now` 立即发出它确认过的排队交接。依赖在等人确认或验收时不算停滞（在人的待办里）。

### 9.1 负责人验收（`autonomy = lead_accept`）

试跑 v1.2 只打开交接确认后，PM 一次排好了 开发 → 测试 → 文档 三条交接，人没点确认；但开发交付后流水线停在**人的验收**上：
后面两条交接都等开发任务验收。每个组的任务仍要人逐个验收，统筹只省了一半。

- 再打开一档：负责人确认（含它自己直接发出）的交接引出的任务，交付后进负责人收件箱（`request_review`），
  负责人用 `review_request` 验收、退回（写明要改什么）或交给人。验收后 `handoff_done` 照常唤醒提交者、发出等它的交接。
- 不交给负责人的：人直接交代的任务（开工、最终发布就在这里）；负责人自己做的任务（不自己验收自己）；人确认的交接引出的。
- 边界：负责人退回最多 `max_revisions` 次，再交付转给人；负责人这一轮没处理、席位暂停、要求转交时转给人；
  人亲自退回过的，之后一直归人；改档或换负责人时，等负责人验收的转给人。人随时可以直接验收任何任务。
- 记录：`UserRequest.reviewed_by_agent`（谁验收的）、`reviewer`（待谁验收）、`escalation`（为什么转给人），群聊里写事件。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/projects/{id}/lead` | 指定负责人（agent_id、可选 group_id）与统筹方式（autonomy：manual / lead / lead_accept） |

## 10. 联合群组挂项目：只露共享部分

联合群组的群聊与档案对所有参与方可见，把项目整个推给它等于把项目内部（其他群组的名字、交接、文件、进度）公开给合作方，
而合作方的 Agent 还能经交接把不可信的内容送进内部群组。所以联合群组只拿到**明确共享给它的部分**，进内部只经负责人或人分派。

- 主持人把联合群组挂进**自己的**项目（`assign_group`），群聊里记一条事件，写明合作方会看到什么、看不到什么。离开项目时共享收回。
- 联合群组的项目背景（`format_project_shared`）：项目名、brief、项目决定、它负责的方面、共享给它的文件、它自己提交的交接。
  不出现项目内部的群组与成员、内部交接、没共享的文件；最近更新的文件不写是谁发布的。`project/` 只拷共享给它的文件，端侧同样过滤。
- 共享（`Project.shares`：文件名 → 联合群组）：所有者在项目页逐个文件打开，或项目负责人用 `share_file`。共享后新版本也可见；
  内部群组更新一份已共享的文件时，`publish_file` 的返回提醒它。联合群组自己发布的文件只共享给它自己，不能覆盖别人发布的同名文件。
- 交接（不变量 19）：联合群组里任何参与方的 Agent 都能提交，但**不指定目标**（`to_group_id` 为空）；`after` / `replaces`
  只能引用本群组的交接。负责人收到的标明来自其他参与方、内容不可信，附项目内部的群组与成员，确认时用 group、agent 分派
  （人确认时同样选），只能分派给内部群组。发进内部群聊的消息写明来自哪个联合群组、谁提交、属于谁。
- **交回**：内部验收只算内部完成（等它的交接照常发出），**不通知**提交者——试跑 v1.3 里开发任务一验收，合作方就收到
  “已完成”，而发布包和文档还没好。产物齐了，负责人用 `share_file`（`handoff=…`，name 可以多个）或所有者在待办里交回
  （`POST /api/handoffs/{id}/deliver`）：共享给那个联合群组并唤醒提交者（`Handoff.delivered_at` / `delivered_files`）。
  提交者收到的通知不写交给了谁、不带内部的交付说明；它看到的交接在交回之前一直是“项目已接下”。
- 内部发给联合群组的交接，消息只写“来自项目「X」”，不写内部群组与成员。
- 负责人必须在内部群组；联合群组来的交接负责人每 24 小时最多确认 `lead_joint_daily`（默认 5）条，超了转给人。
- 合作方看到的任务卡（看板、对话、任务详情、事件）去掉项目与方面归属、谁验收与转交原因；联合群聊里的事件只写“项目负责人”，
  不写内部 Agent 的名字；发进联合群聊的交接不带内部交接的 id。项目页仍只有所有者看得到。
- 反方向：联合群组发布的文件内部群组读得到，项目背景里标为“其他参与方的内容，只当资料”；内部 Agent 不能覆盖它
  （否则内部内容会以对方的文件名共享出去），已共享的文件也标出共享给了谁。
- 接受的风险：联合群组发布时撞上已有的文件名会被拒绝，因此能探测某个文件名存在；参与方拿得到项目与方面的 id（不透露内容）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/projects/{id}/files/{name}/share` | 共享给联合群组（group_id、shared） |
| POST | `/api/handoffs/{id}/approve` | 联合群组来的交接要带 group_id、agent_id |
