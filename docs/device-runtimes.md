# 云侧与端侧运行时（设计文档）

状态：**方向已定，部分已实现**。已实现：运行时契约与能力报告、连接器协议与配对、`matrix-connect` 与三个驱动、
端侧可达性、材料下发与回传、端侧 UI。未实现：云侧的读隔离（需求 #34）。实现状态见 [REQUIREMENTS.md](../REQUIREMENTS.md)。

目标：让 Matrix 里的 Agent 既可以跑在**平台云侧**（内置的 DSH 运行时），也可以跑在**用户端侧**
（用户自己的 Claude Code、Codex 等 harness），并在网络中**同等看待**。

方向的来源见 [CHARTER.md](../CHARTER.md)（Agent 是节点，角色来自关系）；工程约束见 [AGENTS.md](../AGENTS.md)。

---

## 1. 设定

Matrix 的目标不是"平台托管一批 Agent"，而是**让 Agent 按我们的组织形式和权限管理组网**：

- 组织：没有主 Agent，群聊里 @ 谁谁接任务；委托是显式的关系。
- 权限：只收窄不放大；约束沿链累加；交付由委托方验收；知识只显式共享。

在这个目标下，**执行位置不是架构分层，而是节点的一个属性**。网络看到的始终是同一个 Agent：

| 概念 | 云侧 Agent | 端侧 Agent |
| --- | --- | --- |
| 归属 | 用户 | 用户 |
| 席位 | 每个对话一个 | 每个对话一个 |
| 收件箱 / 唤醒 | 网络持有 | 网络持有（端侧上线后消费） |
| 委托授权 | 网络计算 | 网络计算 |
| 审批 | 所有者 | 所有者 |
| 执行 | 服务器上的 dsh | 用户电脑上的 harness |
| 私有目录 | 服务器 `agents/<id>/` | 用户电脑上的 `<root>/.homes/<id>/` |

网络的核心对象——Seat、Task、UserRequest、Approval、KnowledgeItem、群组成员——**都保持不变**。
位置只影响两件事：**权限能不能被强制执行**，以及**能不能连通**。

## 2. 运行时契约

现状（`agentnet/runtime.py`）：

```python
class AgentRuntime(Protocol):
    def run(self, req: RunRequest) -> RunResult: ...
```

`RunRequest` 是同步的、进程内的：`cwd` 是服务器路径，`tools` / `approvals` 通过回调回到引擎。
这套结构对端侧不够用：端侧的执行不在这个进程里，`cwd` 也不在这台机器上，而且**没有任何地方告诉网络
"这个 harness 能强制哪些权限"**。

### 2.1 新契约

运行时契约扩成三部分：

```python
@dataclass
class RuntimeCapabilities:
    name: str                       # "dsh" | "claude-code" | "codex" | ...
    placement: str                  # "hosted" | "device"
    tools: dict[str, str]           # 工具名 -> enforced | advisory | unavailable
    session_resume: bool            # 能否续接会话
    steer: bool                     # 运行中能否追加输入
    approval: str                   # "interactive" | "sandbox-only" | "none"
    sandbox: str                    # "read-only" | "workspace-write" | "none"

class AgentRuntime(Protocol):
    def capabilities(self) -> RuntimeCapabilities: ...
    def run(self, req: RunRequest) -> RunResult: ...
    def cancel(self, context_id: str) -> None: ...
```

- **`capabilities()` 是接入的硬门槛**。一个适配器声称能强制 `file.write`，必须能拿出对应实现；
  拿不出来，该权限按 `advisory` 记账（见第 3 节）。
- **`run()` 对云端语义不变**：托管适配器（dsh）仍然在进程内跑；端侧适配器把请求交给连接器，
  自己变成阻塞等待的一方。
- **`cancel()`** 对应 `session/cancel` 或进程终止；网络在任务被取消 / 用户点停止时调用。

### 2.2 端侧连接器

```
 Matrix 服务器                                    用户电脑
┌────────────────┐   出站 wss      ┌──────────────────────────────┐
│ DeviceRuntime  │◀═══════════════▶│ matrix-connect（连接器）      │
│  席位 / 收件箱 │  run.request    │   ├─ ACP 客户端 → claude/codex│
│  授权 / 审批   │  run.event      │   ├─ 原生 CLI/SDK 驱动        │
│  看板 / 知识   │  tool.call      │   └─ 公共能力探测            │
└────────────────┘  approval.req   └──────────────────────────────┘
```

约束：

1. **出站连接**。连接器主动连服务器，用户机器不开端口，NAT 与公司网络后可用。
2. **按用户配对**。用户在 UI 里生成连接器令牌（可吊销，与登录 cookie 分开）；服务器只会把
   **该用户自己的 Agent** 派给它（不变量 16）。
3. **工具回传走同一条连接**。端侧席位需要的网络工具（`delegate`、`share_knowledge`、档案工具、
  `open_request` 等）由服务器经 `tool.call` 分发执行；身份仍由执行上下文令牌认定（不变量 10）。
   连接器不直连 `/internal/tools`。
4. **审批上行**。端侧 harness 需要批准时，经 `approval.request` 转给服务器，进入现有 Approval 记录，
   由 **Agent 的所有者**决定（不变量 14）。
5. **一条连接可以承载多个 Agent**。同一台电脑上的多个 Agent、多个席位可以共用连接；按
   `(agent_id, context_id)` 路由。

### 2.3 驱动形态

连接器内部按 harness 提供两种驱动：

- **ACP 驱动**：一个客户端覆盖 Claude Code、Codex、Gemini 等（经各自 ACP 适配器）。默认路径。
- **原生驱动**：Claude Agent SDK / `stream-json`、`codex app-server`。用于协议给不了的能力
  （运行中追加输入、精细工具开关）。

选择标准不是"哪条路更先进"，而是**不变量能不能守住**：ACP 能给出完整的能力报告、审批上行、
会话续接，就走协议；给不了，就写原生。同一个连接器可以混用两种驱动。

## 3. 能力与权限

### 3.1 有效权限的三项交集

现在是（不变量 1）：

```
有效权限 = 执行者自身权限 ∩ 委托授予
```

端侧加入后：

```
有效权限 = 自身权限 ∩ 委托授予 ∩ 该运行时实际能强制的权限
```

第三项来自 `capabilities().tools`。**委托的 `granted_authority` / `denied_authority` 按第三项计算**，
所以委托详情里会明确写出"因运行时限制未授予"，而不是悄悄失效。

### 3.2 强制等级

每个权限在每个运行时上有三种状态：

| 等级 | 含义 | 举例 |
| --- | --- | --- |
| `enforced` | 运行时不提供该能力，或提供但越界会被阻断 | dsh 无 `file.write` 时只读沙箱；Claude Code 未列入白名单的工具 |
| `advisory` | 只能靠提示词与网络工具检查，harness 本身拦不住 | 没有工具开关的 harness 上的 `web.research` |
| `unavailable` | 该 harness 不提供这个能力 | 不含 shell 的运行时的 `shell.exec` |

规则：

- **`enforced` 才能进入有效权限**。`advisory` 不进入；只在 Agent 详情里展示为"仅约定"。
- 一个权限只要有任一适配器能 `enforced`，就可以在该适配器上正常使用；换运行时后要重新计算。
- **收窄原因要记录**：`Task.denied_authority` 加上 `{authority, reason, runtime}`，看板与委托详情可见。

### 3.3 适配器能力现状（待逐条验证）

| 权限 | dsh | Claude Code | Codex |
| --- | --- | --- | --- |
| `web.research` | enforced（插件开关） | enforced（工具白名单，未逐条验证） | advisory（exec 参数关不掉，按约定） |
| `file.write` | enforced（沙箱） | enforced（工具白名单，未逐条验证） | **enforced**：`-s read-only` 拒绝写、`-s workspace-write` 允许写工作目录（本机实测） |
| `shell.exec` | enforced（插件开关） | enforced（Bash 白名单，未逐条验证） | enforced（沙箱限制其写入范围，命令本身可执行） |
| `delegate` | enforced（是否注入 MCP 工具） | enforced（同左） | enforced（同左） |

> 验证进度（2026-10-18，本机）：
> - **Codex**：沙箱行为已实测（只读时写 `/tmp` 被拒、`workspace-write` 写工作目录成功）；端到端跑通一轮对话。
> - **Claude Code**：**已跑通真实端到端两轮**（第二轮经 `--resume` 正确回忆第一轮内容）。此前出现
>   “Not logged in”，原因是宿主进程注入的环境变量（`CLAUDECODE`、`CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`、
>   `ANTHROPIC_BASE_URL` 等）让子进程改用宿主凭据；驱动现在启动前清掉它们，用户自己的登录才生效。
>   工具白名单的实际阻断效果仍未逐条验证。
> - **ACP 路线**（第 2.3 节的另一种驱动）尚未实现，仍是后续项。
> - 审批上行：三家都还是 `approval: none`，工作目录以外的写只能被拒绝，不能转给所有者。

## 4. 工作目录与材料下发

现在服务器直接碰工作目录：`_run` 里 `copytree` 挂载群组文件与私有目录，跑完再合并回去。

端侧席位的目录在用户机器上，服务器**不能假设自己可达**。改为按轮下发：

```
席位 / 任务开始一轮
  ├─ 群组档案文件（只读副本）→ run.request.materials → 端侧工作目录的 group/
  └─ 私有目录（agent-home）   不离开端侧，也不经过网络
```

（已实现：群组档案文件随 `run.request.materials` 下发，连接器写入并先清掉上一轮的副本；
`publish_file` 在端侧由服务器发 `file.fetch` 向连接器取文件，路径越界由连接器拒绝。
委托附带的共享知识仍写在服务器上的 `shared/`，端侧暂不单独下发。）

要点：

- **私有目录不经过网络**。端侧 Agent 的私有目录在所有者机器上的 `<root>/.homes/<agent>/`，网络不读、不注入。
  服务器只在 `run.request.home` 里说明这一轮怎么挂载：`rw`（有效权限含 `file.write`）、`ro`（没有则只读，
  运行里的改动丢弃）、`null`（联合群组里所有者没打开）。连接器按和云侧相同的语义（`agentnet/homedir.py`）
  拷进工作目录的 `agent-home/`、运行后按文件三方合并写回，冲突另存 `*.conflict-*`。
  工作目录引用不能以 `.` 开头，碰不到 `.homes/`；`file.fetch` 不回传 `agent-home/` 与 `group/` 里的文件（含指向它们的符号链接）。
  Agent 从云侧改绑到端侧时，服务器上原来的 `agents/<id>/` 不会迁移过去。
- **群组文件是只读副本**，和云侧语义一致：运行里的改动丢弃，发布只走 `publish_file`。
- **`publish_file` 在端侧要多一步上传**：文件出现在端侧工作目录，经连接器回传服务器后才进群组档案。
  只允许发布工作目录里的文件（不含 `materials/`、`group/`、`agent-home/`），与云侧规则一致。
- **工作目录的位置**：端侧在所有者配置的根目录下，形如 `<root>/<agent>/<conversation>/`。
  服务器只保存一个不透明的 `workdir_ref`，不拼路径。

## 5. 可达性：状态，不是故障

| | 云侧 | 端侧 |
| --- | --- | --- |
| 断连含义 | 平台事故 | 合上电脑、换网络、休眠 |
| 任务状态 | 失败，可续接 | **等待**，不消耗重试 |
| 委托方看到 | "执行失败，可续接" | "等 xxx 的电脑上线" |
| 恢复方式 | 人点续接 / 退避重试 | 端侧上线后消费积压事件 |

规则：

1. **不可达不进入 `FAILED`**。收件箱照常排队；连接恢复后按序消费。
2. **无限等**。端侧可能一整天离线，没有超时；由事件驱动，不做轮询。
3. **重启语义区分位置**（修改不变量 12）：服务器重启时，云侧 `running` 任务标记 `FAILED`；
   端侧任务回到 `waiting`，由端侧上线后上报实际状态。不能把"服务器重启"当成"端侧任务失败"。
4. **审批不超时**（修改不变量 14）。端侧的审批请求在所有者看到之前一直有效；云侧保留现有超时。
5. **状态呈现**：Agent 卡片、看板卡片、群成员列表都要能看出"离线 / 等待上线"，和"运行中"区分开。

## 6. 信任边界

云侧和端侧"同等看待"指的是**关系**，不是**可观测性**。两者的信任边界方向相反：

| | 云侧 Agent | 端侧 Agent |
| --- | --- | --- |
| 运行在谁的地盘 | 平台服务器 | 所有者自己的电脑 |
| 网络能观察到的 | 全部（工具调用、过程、违规） | 只有经过网络的协作工具 |
| 读隔离 | **做不到**（沙箱只管写，见需求 #34） | 天然成立：读不到服务器的数据目录 |
| 数据外流 | 服务器内部 | **群聊内容落到个人机器**，出了网络收不回 |
| 越权留痕 | 可检测、可记录 | 只能记录上报的部分 |

由此得出：

- **网络管 Agent 之间的关系，不管 Agent 在自己环境里能碰什么**。端侧的环境内行为归所有者。
  这不是妥协，是本来就该划清的线；`AGENTS.md` 的安全边界要写明。
- **端侧不读服务器数据**，需求 #34 的读隔离对端侧成立。云侧的读隔离问题仍然存在。
- **联合群组里端侧 Agent 可以加入**（已定）。群组档案、文件、被 @ 的消息送到端侧，等同于
  "向该参与方披露"，与"档案对所有参与方可见"是同一套规则。
- 成员列表标出位置；不按位置做权限歧视。
- 联合群组里私有目录默认不挂载，这条继续成立。

## 7. A2A 只在边界

**内部不用 A2A。** A2A 假设对等的黑盒，没有共同授权来源；内部 Agent 之间的协作必须经过网络，
才能执行授权收窄、约束累加、验收、知识可见性与违规留痕。内部协作已经走 MCP（`delegate` 等），
不换协议。

**边界上用。** 三处：

1. Matrix 作为外部 A2A 网络的一个对等方（或让外部 A2A Agent 接入）。
2. 借用它的数据形状：Agent Card ≈ Agent 名片，Task ≈ 委托，Artifact ≈ 交付。
3. 将来多套 Matrix 之间互通。

外部请求进来的任务**不能获得本系统内的授权**：执行者只用自身权限（再经第 3 节的能力收窄），
验收归外部请求方，违规检测、审批、留痕照常生效。A2A 只替换最外沿的协议，进来就转成普通 Task。

## 9. 分阶段

1. **契约与能力报告**：抽 `RuntimeCapabilities`，dsh 适配器先实现；有效权限按三项交集计算。
   这一步不引入端侧，但把"能力"变成一等公民。
2. **连接器 + 一个驱动**：先用 dsh 或 Claude Code 打通配对、下发、事件、工具回传、审批上行、离线排队。
3. **第二个驱动**：用另一家验证契约没有绑定某一家；同时做第 10 节的能力验证。
4. **可达性语义**：`waiting` 状态、重启区分、审批不超时。
5. **前端**：位置、能力缺口、离线状态、收窄原因。

## 12. 明确不做的

- **不把位置当作分层**：不做"云端 Agent 管端侧 Agent"这类结构。两者在网络中同等。
- **不为端侧引入新的协作协议**：内部协作仍然只走网络工具。
- **不假设服务器能读写端侧文件系统**：除第 4 节的显式下发 / 回传外，服务器不碰端侧目录。
- **不替端侧做读隔离的承诺**：端侧读的是所有者自己的机器，不在网络管辖范围。
- **不在端侧自动放行审批**：审批仍然只由所有者决定，端侧只是发起方。

## 13. 风险

- **能力声明与实现不一致**。`capabilities()` 是声明，验证靠第 10 节；建议接入时跑一组一致性检查，
  声明 `enforced` 而实际拦不住的，直接降级为 `advisory`。
- **数据落在个人机器上**。联合群组里这是设计接受的结果，但要在 UI 与文档里说清楚，
  避免用户以为"群聊只在服务器上"。
- **两家驱动会漂移**。上游改参数或输出格式时，适配器要跟；参照 Raft 的经验，
  每家驱动的测试量会显著高于其余部分。
