# 公共 Agent（设计草案）

> 状态：**讨论中，未实现**。需求见 [REQUIREMENTS.md](../REQUIREMENTS.md) #69。约束见 [AGENTS.md](../AGENTS.md)、
> [reference/invariants.md](reference/invariants.md)。外部平台 Agent 的接入（远程运行时）在这之后落地，见第 7 节。
> 调研：research: agent-definition-context-boundaries#trust-boundary-outside-agent、research: project-publishing#gpts-builder-privacy。

## 1. 要解决什么

企业 IT 系统在做 AI 转型：报销、请假、采购、工单、资产这些系统 Agent 化，人通过和 Agent 交互完成业务流程、查业务信息。
这样的系统是**长期运行**的，需要几个 Agent 一直负责，它们：

- **不该归属某个人**：系统不能因为某个人离职、请假就没人管；
- **要给所有人用**：任何 Matrix 用户都能找到它、@ 它、让自己的 Agent（尤其是助理）委托它。

现在的 Matrix 做不到：Agent 只属于一个所有者、只为所有者工作（不变量 16），别人只能在共享项目里通过委托用到它。

## 2. 为什么不是加一个开关

Matrix 早先有 public / shared Agent，2026-10-16 有意去掉了（REQUIREMENTS.md #30，旧数据由 `Store._one_trust_domain` 迁移）。
当时绕不开的问题是：**同一个 Agent 同时为两个互不信任的人工作，从 A 那里知道的东西怎么保证不流到 B？**
Raft、Kylon 的答案是“别让这种情况发生”，信任边界划在 Agent 外面（research: agent-definition-context-boundaries#trust-boundary-outside-agent）。
公共 Agent 正是这种情况，所以要正面回答：按现有机制逐条堵住 A → B 的通路（第 4 节）。

可以跨用户的只有**专业能力**（技能、方法、维护人整理的公共资料），**用户的事实**不跨
（律所类比，research: agent-definition-context-boundaries#law-firm-analogy）。

## 4. 模型：维护面与服务面

公共 Agent 的所有者不是一个人，而是一个**维护组**（几位维护人）。它有两面：

- **维护面**：只给维护组。配置、技能、私有目录、定时、连接器都在这里，规则和现在的个人 Agent 一样，只是所有者是一组人。
- **服务面**：给所有用户。每次使用都发生在**调用方自己的场合**里（调用方的项目群聊、和它的私聊、调用方 Agent 发来的委托），
  服务的是这个场合里的人。

服务面的规则，以及各自堵住的通路：

| 通路 | 规则 |
| --- | --- |
| 私有目录 | 只读挂载，内容是维护人在维护面整理的公共资料；服务面写不回（决策 1） |
| 工作台账 | 只列这个场合里的事，别处的工作连数量都不给 |
| 模型会话 | 每个席位、每个委托各自一个会话（不变量 7 已成立），服务面的会话不跨场合续接 |
| 过程可见性 | 过程、失败说明给**调用方**看；维护人只看用量：谁、何时、哪个场合类型、调了哪些工具、成功与否，不看内容（决策 3）。参照 GPTs 不让作者看对话（research: project-publishing#gpts-builder-privacy） |
| 审批 | 服务面不开工作区外溢审批（不变量 14 的“所有者”在这里没有合适的人），只在沙箱里做 |
| 权限 | **公共 Agent 的权限 = 愿意直接给所有用户的权限**：设成公共要管理员批准，批准时冻结权限，之后改权限重新批准 |
| 凭证 | 要用户鉴权的系统用**调用者自己的授权**（决策 2）；调用者还没授权时，在他那边提示去连接，不借用维护人的。不涉及用户身份的公共信息（制度文档、公开目录）可以用部署方登记的服务凭证，只读 |
| 写操作 | 业务流程里的写操作（提交、审批、撤回）按不变量 19 逐次给**调用者**确认 |
| 信息流 | 不变量 22 照常：服务面一轮能读到的只有这个场合的内容和公共资料 |
| 成本 | 服务面的模型用量记在调用方名下，用量台账同时标出公共 Agent |

## 5. 怎么被用

- **发现**：一个“公共 Agent 目录”（像服务台），列出名称、说明、负责的系统、需要连接哪些服务。
- **私聊**：任何用户都能私聊它，不需要先进项目（决策 5）。员工办事的主要入口：“帮我请三天假”直接和请假系统的公共 Agent 说。
  助理对话里提到这类事时，助理可以给出去私聊它的入口，但不委托（助理对话不是项目）。
- **在项目里**：拉进项目，群聊里 @ 它，或者项目里的成员委托它（不变量 2 不变，决策 5）。
  **调用方**是 @ 它的人，或者委托它的那个 Agent 的所有者；用谁的授权、写操作给谁确认、过程给谁看，都按调用方。
  共享项目里它的回复所有参与者都看得到：读到调用方业务数据之前按不变量 19 先问调用方，调用方知道回复会给谁看。
- **结果**：在会话里回复（决策 6）。跨天的流程（报销几天后才审批完）靠同一个会话的连续性：调用方再问一句“批了吗”，
  它用调用方的授权去查。这个会话只属于这个调用方的场合，记得的报销单号不跨用户。

## 6. 不变量的改动（草案）

- **16 改写**：个人 Agent 不跨信任域；公共 Agent 只在服务面跨，服务面不跨场合保留任何东西。
- **新增一条**：公共 Agent 的服务面只在调用方的场合里运行，只读维护面整理的公共资料，用调用方的授权，写操作由调用方确认，
  维护人只看用量；设成公共、改权限都要管理员批准。

## 7. 与外部平台 Agent 的关系

公司内部平台上建的云端 Agent 接进 Matrix（远程运行时：HTTP 流式会话、可续接、可中断，Agent 级 MCP，MCP 请求带会话 id），
设成公共后就是一个公共 Agent。差别在于平台那边的记忆、过程、它自己的连接器 Matrix 管不到：

- 第 4 节的记忆、过程可见性两条在平台侧没有保证，设成公共时界面写明“对方平台是否跨用户保留记忆由平台决定”，管理员批准时确认；
- “用调用者自己的授权”经**请求头透传**（决策 7）：部署方在目录里给平台配置请求头名与取值来源（调用者在 Matrix 里授权的哪个连接），
  驱动每轮只放这一轮调用方的凭证，平台 Agent 再透传给它的工具。要守住的：
  - 凭证只来自调用方自己的授权，绝不放维护人或创建者的；只在发出的请求里，不进日志、事件、提示词；
  - **缺头时平台不能退回到创建者的授权**（否则谁调用都借到创建者的权限）：接入验收要实测“不带头调用 → 业务系统拒绝”；
  - 调用方还没授权那个连接时不发起会话，在他那边提示去连接。

## 8. 待讨论

1. **经维护人审核才能写入的公共知识**：比如工单分诊 Agent 从每个人的工单里总结经验。服务面提出候选，去掉用户事实，
   维护人审核通过才进维护面的公共资料。对应调研里的“经验晋升闸门”（research: agent-definition-context-boundaries#matrix-decision 未做部分）。
2. ~~委托是否要求成员关系~~：已定，要求（决策 5）。待定：共享项目里谁能把公共 Agent 拉进来（主持人，还是任何参与者）。
3. **系统事件回推**（以后）：第一版只拉取（决策 6）。真要推送时，发起业务时留一个回执，把那次业务绑到当时的场合与席位，事件只能凭回执唤醒它。
   企业系统多半已有自己的通知（IM、邮件），可能不需要 Matrix 再推。
4. **维护组的变动**：维护人离开、交接；最后一个维护人离开时怎么办。
5. **配置变更对进行中的会话**：维护面改了技能或资料，正在服务面进行的会话什么时候换新。
6. **用量与配额**：公共 Agent 是否需要按用户限频，防止一个人占满。

## 9. 明确不做的

- 服务面跨用户的记忆（决策 1）。
- 调用方借用维护人或服务账号的授权去访问需要用户身份的数据（决策 2）。
- 维护人查看服务面的对话内容（决策 3）。
